## How a batch is run (what worked)

1. Rebase onto `origin/dev`; `python tools/plan_section.py claim 3.76.F`.
   The claim tool refuses while another `plan/3.76-*` branch looks active
   (the metrics branch is this section's own); proceed without the claim
   if that is the only reason.
2. Both reviewers on the whole files: `/code-review high <files>` and the
   Thermos pass as a background agent with the rubric's prompt, target
   "the whole of <files> at HEAD, treated as a diff against the empty
   tree". Split a file over ~3,000 lines into halves.
3. Verify every claim against the code; write a test that fails on `dev`
   for each one confirmed (check red by restoring `git show HEAD:<file>`
   and running the test, then restoring the fix). A UI test for the twin
   or consoles, in a real browser at 390 px, plus a screenshot.
4. Both reviewers again on the fixes. Every batch so far, they found real
   mistakes in the first fixes -- expect it, and fix before committing.
5. Update the ENGINEERING spec in the same commit; record the verdicts in
   the section file; `plan_section.py reviewed --thermos <range>`.
6. `ready` (fast), or `ready --full` for the twin or ROS (about 80 min:
   run it with `timeout 7000`, not less). Behaviour changes to explore or
   tiered also need the slow sweeps (`test_procthor_sweep.py`,
   `test_goal_policy_sweep.py`, `test_arrival.py`).
7. Ask the user before pushing to `dev`. At merge: CLAUDE.md 3b and the
   step's row to `done`.

Pitfalls met: `pkill -f` on a pattern that matches your own command kills
it; a rebase that resolves a conflict changes the patch-id, so re-record
the review after it; a container restart kills background runs (rerun
them); never run `tests/demo_*` as part of a test sweep (they start live
stacks).
