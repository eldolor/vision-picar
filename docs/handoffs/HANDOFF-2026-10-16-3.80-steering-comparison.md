## A proposed design (write criteria BEFORE measuring; CLAUDE.md 7)

Steering = the action each tier would choose. Three sets, labels fixed
before any model runs:

1. **Real, target in view.** Frames sampled uniformly from the labelled
   walks' `target_visible_labels == true` (not from perception's
   detections, or YOLOE + CLIP is favoured), across walks. Label the
   target's horizontal third (left/center/right) by viewing each frame;
   write the labels to a file and commit it before scoring. Correct steer:
   LEFT / FORWARD / RIGHT. Score each tier's accuracy and its coverage (a
   tier that gives no steer on a frame is "no answer", reported apart):
   * YOLOE + CLIP: perception's bearing (detected; and the band candidate,
     F-b) -> `_steer_to`'s rule (STEER_BAND_DEG 3 deg; the thirds for the
     comparison);
   * Qwen (VE and full): the direction question, and separately the
     identity question's box (`box: true`) -> its third;
   * Opus 4.5: the deployed `/navigate` (`action` and `target_direction`).
2. **Real, target out of view.** No single-frame truth: report each
   tier's answer distribution (the forward bias) and the mirror test
   (`f4b_mirror.py`'s statistic) for the VLMs.
3. **Simulator, target out of view (the search question criterion 2
   failed on).** Renders from the 21 houses at poses where the target is
   not in view; truth = the first step of the shortest floor path to the
   target, as LEFT / RIGHT (> ~30 deg off heading) or FORWARD. Chance
   about 1/3. VLMs only (YOLOE + CLIP is not run on renders in this
   project, and has no search answer by design). The cloud may read the
   target's caption in renders; with the target out of view that matters
   less, but say so.

Report per tier: accuracy with counts, coverage, latency (board p90 for
Qwen, the cloud's round trip), cost per frame, memory (Qwen full vs VE
beside the stack; 3.81's budget: ~500 MB in normal running, ~0 MB at a new
target's first frame, floor 0.5 GB).
