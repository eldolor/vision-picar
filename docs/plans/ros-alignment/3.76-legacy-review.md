# 3.76 Review of the risky files written before the review rule

*`PLAN-ros-alignment.md` section 3.76; index: [README.md](README.md).*

**Why.** CLAUDE.md section 6's "Code review" rule (`/code-review` on every
change, plus the Thermos bug pass on a risky one) dates from 2026-10-09.
Both reviewers are diff-scoped, so nothing written before then has been
through them, apart from the six commits behind
`docs-review/THERMOS-BUG-PASS.md` (their live bugs fixed in 3.64). The
reviewer comparison found 18 real bugs in six commits; the code written
before the rule is about 27,500 lines of risky files alone.

**Scope (the user, 2026-10-12).** *Depth:* the files `RISKY_PREFIXES` in
`tools/plan_section.py` names, and nothing else (`sim/` and the rest are
out). *Severity:* every confirmed bug is fixed, cosmetic ones included.
CloudFormation templates for the stacks deleted 2026-09-05 (`admin`,
`brain`, `cdn`, `network`, `recordings`, `service`, `teleop-*`, `twin`) are
out: nothing deploys them. Live templates are `serverless.yaml`,
`recordings-s3.yaml` and `deploy-bucket.yaml`.

**Method.** Each batch is a few related files reviewed whole: `/code-review`
with the files as its target, and the Thermos bug pass on the same files as
a diff against the empty tree. Batches group files that call each other, so
seams are inside one review. A whole-file review has no "what changed" to
anchor on and raises more claims than a diff review; every finding is a
claim to verify, as CLAUDE.md section 6 says.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Coverage.** Every in-scope file appears in the coverage table below
   with the date both reviewers ran on it and its finding count.
2. **Every finding gets a verdict**, recorded in the batch's findings
   table: *confirmed* (a test reproduces it), *not a bug* (a written
   reason: the path traced and why it cannot happen), or *cannot
   reproduce* (what was tried). A finding raised by only one reviewer is
   verified the same way.
3. **Every confirmed bug is fixed red-first:** a test that fails on `dev`
   for the reason in the table, and passes with the fix. A UI test in a
   real browser for the twin and the console (CLAUDE.md section 1), run in
   its module's real order.
4. **The fixes are reviewed** by both reviewers (every file here is risky),
   and recorded with `plan_section.py reviewed --thermos`.
5. **No neighbour broken:** `ready` before each batch is offered for
   merge; `ready --full` for a batch that changes the twin or the ROS
   stack.
6. **Safety-path fixes are judged on ground truth**
   (`tests/footprint_sweep.py`), never on the readings the veto uses.
7. **A twin or console fix is shipped only when deployed**
   (`service/static/sync.sh`, invalidation `Completed`, `app.js` parity),
   with a phone-size screenshot of any changed page state.

Each batch merges to `dev` on its own, with the user's go-ahead, so a
safety-path fix is not held behind the twin.
