# 3.53 Arrived, unconfirmed: a warning in the twin, and asking again when the cloud returns

*`PLAN-ros-alignment.md` section 3.53; index: [README.md](README.md).*

**Why.** 3.47 made a tiered mission whose arrival holds but whose identity
check cannot reach the cloud end `arrived_unconfirmed`. Two gaps were left,
both approved by the user on 2026-10-09:

1. The twin shows that outcome as an error: no colour class on the Remote
   brain panel's Mission line, a red error toast that says only "Mission
   arrived_unconfirmed", and on the Guide tab's Drive via brain an `ERR
   LINK` telemetry block, as if the brain had been lost.
2. Nothing ever asks again. The robot is parked at what the local tier took
   for the target, the cloud comes back a minute later, and the question
   that would settle it is never put.

**Design.**

* **The outcome is never rewritten** ("first outcome wins"). The answer to
  the late question is recorded BESIDE it, as `status.late_confirmation`,
  and never turns the outcome into `found`; `memory.found` stays false.
* **The frame.** A confirmation that raises already carries its arrival
  readout (3.47); it now carries the frame too (`arrival_frame`), held with
  the readout for the current run of failures and kept by `_finish` with
  the outcome. The question is asked of THAT frame, which is what the robot
  saw where it stopped -- the robot is not consulted again.
* **Probing is free.** While waiting, the brain sends `GET
  <vision_url>/health`: the vision service's existing route, which does no
  Bedrock call, already routed by the gateway and CloudFront (no new route,
  no route-guard change). Only after a probe answers 200 does it make the
  ONE paid call: the policy's `confirm_arrival(frame)` under B3.2's
  `vision_timeout_s`.
* **Bounded.** One probe every `reconfirm_probe_s` (default 15 s) for at
  most `reconfirm_window_s` (default 600 s; 0 turns the feature off). At
  most two paid attempts per arrival: a cloud whose health answers but
  whose `/navigate` still fails gets one retry, then the state is `failed`.
  Worst case per arrival: 41 free probes and 2 paid calls.
* **States** (`late_confirmation.state`): `waiting` (probing), then one of
  `confirmed` (the cloud sees the target), `refused` (it does not),
  `failed` (two paid attempts both raised), `not_asked` (the policy's call
  cap was spent: no call made), `expired` (the window ran out with the
  cloud still down), `dropped` (a new mission started first). Each carries
  `probes`, `paid_calls`, the reason and the time.
* **Never moves the robot and never sends a stop.** The loop calls only the
  cloud. `robot` is not touched; the runner has already ended and stopped
  the car, and a stop from it now would halt whoever drives next (3.47's
  fourth review).
* **A new mission first:** `POST /mission/start` cancels the loop and marks
  the old runner `dropped` before the new runner exists. **Stop** also
  cancels it (marked `dropped`): an operator pressing Stop means stop
  everything, and the question can be asked again by hand later.
* **A brain restart** loses the loop and the frame (in memory only); the
  mission's metrics row keeps the outcome `arrived_unconfirmed` with no
  late verdict, which is what happened.
* **Metrics.** The mission's row is re-sent with the same `run_id` and
  `finished_at`, so it overwrites the same object (one row per mission,
  never two), with `stats.late_confirmation` added. `stats` is free-form,
  so the walks Lambda needs no change and no deploy.
* **Twin.** A warning token (`--accent-warn`, yellow); `arrived_unconfirmed`
  gets it on the Mission line and as a `warn` toast that says what was
  checked and what was not; the Guide tab shows it as an outcome, not as a
  lost link; and the late verdict, when it lands, is shown on both.

**Criteria (written before building; CLAUDE.md section 7):**

1. **It asks once when the cloud comes back.** Through `MissionRunner`
   (scaled house, the 12 clear starts, async tier), a cloud that is down
   until the mission has ended `arrived_unconfirmed` and then comes back:
   `late_confirmation.state` is `confirmed` on 12 / 12 with a cloud that
   sees the target and `refused` on 12 / 12 with one that does not; exactly
   1 paid call each (24 / 24); the outcome stays `arrived_unconfirmed` and
   `memory.found` false on 24 / 24.
2. **Probing is free and bounded.** While the cloud is down: 0 paid calls;
   probes `<= window / interval + 1`; at the end of the window the state is
   `expired`. A cloud whose health answers but `/navigate` keeps failing:
   exactly 2 paid calls, state `failed`.
3. **Never touches the robot.** During the late phase, 0 calls to any robot
   method (move, stop, action) across every run of criteria 1-2.
4. **A new mission or Stop drops it.** Started while waiting: 0 paid
   confirmation calls after the start, old runner `dropped`. Stop while
   waiting: same.
5. **Twin, at 390 px.** On the Remote brain panel, `arrived_unconfirmed`
   carries the warn class and its toast is `warn`, not `err`; on the Guide
   tab it is not rendered as an error (`ERR LINK`); a landed late verdict
   is shown on both. A UI test that fails with the change reverted, run in
   module order; a 390 px screenshot as evidence.
6. **Metrics stay one row per mission:** the re-sent row has the original
   `run_id` and `finished_at`, and carries `stats.late_confirmation`.
7. **Live.** Robot server and brain over HTTP on this section's ports, with
   `VISION_URL` pointed at a local stand-in that is down and then comes up:
   the mission ends `arrived_unconfirmed`, and `GET /mission/status` shows
   `late_confirmation.state` `confirmed` within `reconfirm_probe_s + 5` s
   of the stand-in coming up, with the robot's pose unchanged.
8. **No regression:** the fast tier and `tests/test_arrival.py` pass.
