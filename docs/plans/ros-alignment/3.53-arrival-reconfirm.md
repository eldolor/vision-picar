# 3.53 Arrived, unconfirmed: a warning in the twin, and asking again when the cloud returns

*`PLAN-ros-alignment.md` section 3.53; index: [README.md](README.md).*

**Why.** 3.47 made a tiered mission whose arrival holds but whose identity
check cannot reach the cloud end `arrived_unconfirmed`. Two gaps were left,
both approved by the user on 2026-10-09:

1. The twin shows that outcome as an error: no colour class on the Remote
   brain panel's Mission line, a red error toast that says only "Mission
   arrived_unconfirmed", and on the Guide tab's Drive via brain an `ERR
   LINK` telemetry block, as if the brain had been lost.
2. Nothing ever asks again. The robot is parked at what the local tier took
   for the target, the cloud comes back a minute later, and the question
   that would settle it is never put.

**Design.**

* **The outcome is never rewritten** ("first outcome wins"). The answer to
  the late question is recorded BESIDE it, as `status.late_confirmation`,
  and never turns the outcome into `found`; `memory.found` stays false.
* **The frame.** A confirmation that raises already carries its arrival
  readout (3.47); it now carries the frame too (`arrival_frame`), held with
  the readout for the current run of failures and kept by `_finish` with
  the outcome. The question is asked of THAT frame, which is what the robot
  saw where it stopped -- the robot is not consulted again.
* **Probing is free.** While waiting, the brain sends `GET
  <vision_url>/health`: the vision service's existing route, which does no
  Bedrock call, already routed by the gateway and CloudFront (no new route,
  no route-guard change). Only after a probe answers 200 does it make the
  ONE paid call: the policy's `confirm_arrival(frame)` under B3.2's
  `vision_timeout_s`.
* **Bounded.** One probe every `reconfirm_probe_s` (default 15 s) for at
  most `reconfirm_window_s` (default 600 s; 0 turns the feature off). At
  most two paid attempts per arrival: a cloud whose health answers but
  whose `/navigate` still fails gets one retry, then the state is `failed`.
  Worst case per arrival: 41 free probes and 2 paid calls.
* **States** (`late_confirmation.state`): `waiting` (probing), then one of
  `confirmed` (the cloud sees the target), `refused` (it does not),
  `failed` (two paid attempts both raised), `not_asked` (the policy's call
  cap was spent: no call made), `expired` (the window ran out with the
  cloud still down), `dropped` (a new mission started first). Each carries
  `probes`, `paid_calls`, the reason and the time.
* **Never moves the robot and never sends a stop.** The loop calls only the
  cloud. `robot` is not touched; the runner has already ended and stopped
  the car, and a stop from it now would halt whoever drives next (3.47's
  fourth review).
* **A new mission first:** `POST /mission/start` cancels the loop and marks
  the old runner `dropped` before the new runner exists. **Stop** also
  cancels it (marked `dropped`): an operator pressing Stop means stop
  everything, and the question can be asked again by hand later.
* **A brain restart** loses the loop and the frame (in memory only); the
  mission's metrics row keeps the outcome `arrived_unconfirmed` with no
  late verdict, which is what happened.
* **Metrics.** The mission's row is re-sent with the same `run_id` and
  `finished_at`, so it overwrites the same object (one row per mission,
  never two), with `stats.late_confirmation` added. `stats` is free-form,
  so the walks Lambda needs no change and no deploy.
* **Twin.** A warning token (`--accent-warn`, yellow); `arrived_unconfirmed`
  gets it on the Mission line and as a `warn` toast that says what was
  checked and what was not; the Guide tab shows it as an outcome, not as a
  lost link; and the late verdict, when it lands, is shown on both.

**Criteria (written before building; CLAUDE.md section 7):**

1. **It asks once when the cloud comes back.** Through `MissionRunner`
   (scaled house, the 12 clear starts, async tier), a cloud that is down
   until the mission has ended `arrived_unconfirmed` and then comes back:
   `late_confirmation.state` is `confirmed` on 12 / 12 with a cloud that
   sees the target and `refused` on 12 / 12 with one that does not; exactly
   1 paid call each (24 / 24); the outcome stays `arrived_unconfirmed` and
   `memory.found` false on 24 / 24.
2. **Probing is free and bounded.** While the cloud is down: 0 paid calls;
   probes `<= window / interval + 1`; at the end of the window the state is
   `expired`. A cloud whose health answers but `/navigate` keeps failing:
   exactly 2 paid calls, state `failed`.
3. **Never touches the robot.** During the late phase, 0 calls to any robot
   method (move, stop, action) across every run of criteria 1-2.
4. **A new mission or Stop drops it.** Started while waiting: 0 paid
   confirmation calls after the start, old runner `dropped`. Stop while
   waiting: same.
5. **Twin, at 390 px.** On the Remote brain panel, `arrived_unconfirmed`
   carries the warn class and its toast is `warn`, not `err`; on the Guide
   tab it is not rendered as an error (`ERR LINK`); a landed late verdict
   is shown on both. A UI test that fails with the change reverted, run in
   module order; a 390 px screenshot as evidence.
6. **Metrics stay one row per mission:** the re-sent row has the original
   `run_id` and `finished_at`, and carries `stats.late_confirmation`.
7. **Live.** Robot server and brain over HTTP on this section's ports, with
   `VISION_URL` pointed at a local stand-in that is down and then comes up:
   the mission ends `arrived_unconfirmed`, and `GET /mission/status` shows
   `late_confirmation.state` `confirmed` within `reconfirm_probe_s + 5` s
   of the stand-in coming up, with the robot's pose unchanged.
8. **No regression:** the fast tier and `tests/test_arrival.py` pass.

**Amendment 1 (2026-10-09, before the run it affects; from `/code-review`
on the first build).** Criterion 4's "Stop while waiting: same" is
withdrawn. A Stop after the mission has ended (the Guide tab sends one on
every Stop tap and page close) would drop the check the HUD had just said
would run, and the late path never moves the robot, so Stop has no safety
reason to drop it. Criterion 4 now reads: **a new mission drops it (0 paid
confirmation calls after the start, old runner `dropped`); a start that is
refused (400/403) does not; a Stop after the ending does not, and the check
still asks.** The design bullet "Stop also cancels it" is superseded.

**Found while building:** the Guide tab's HUD reset to "Deciding..." over
any terminal caption: a tick scheduled at dispatch fired after the run had
paused and dispatched anyway (seen in the first screenshot). `guidanceStep()`
now returns while paused; the Guide UI test holds the caption past the next
tick and fails without the guard. It also affected `max_steps`/`failed`
endings, not only this one.

**Review** (`/code-review` on the first build; the Thermos rubric applied
by hand, since this section ran as a sub-agent that could not start
another). Applied, each with a test that fails when the bug is put back
(mutation-checked): a cancel between the probe and the paid call
(`late_ask()` now refuses a final record under the lock, and the cancel
records before setting its flag); Stop after the ending dropping the check
(amendment 1); a refused start dropping it (cancel moved after the runner
is built); `paid_calls` counting a cap refusal; a timed-out call retried
beside the one still in flight (`failed` at once). Also applied: a 0 probe
interval is off, not a spin; the twin's watcher stops when the check is off
and never doubles its toast; a page connecting after the ending still
watches; the old dead `wasPausedAtDispatch` guard removed; a generation
counter so a mission loop finishing after a start or stop cannot start a
check for a stale mission (reasoned, not pinned: the window is inside
`create_app`). Rejected: reusing `_guarded_confirm()` for the late call --
it maps a timeout into B3.2's `VisionUnavailable`, and the late path must
know a call is still outstanding.

**Known gaps:** the check lives in memory (a brain restart loses it); the
deployed twin is not synced (no S3/CloudFront deploy in this section);
`docs/guides/FEATURES.html` is a hand-made copy of `FEATURES.md` and was
not updated.

**Second review** (`/code-review` on the final tree). Both applied and
mutation-checked:

1. **`/health` is shallow.** It answers while Bedrock is down or throttling,
   so in a server-side outage both paid attempts went out 15 s apart and the
   600 s window was never used. After a failed paid call the next now waits
   `window / 2` (300 s): `test_2_..._pays_twice_then_stops` pins the spacing
   and `test_2_a_server_side_outage_that_clears_in_the_window_is_confirmed`
   pins a four-minute Bedrock outage ending `confirmed`. Worst case is
   unchanged (41 probes, 2 paid calls).
2. **A Stop in the loop's post-tick sleep** cancelled the loop before it
   started the check, losing it without a trace -- against amendment 1. Stop
   now decides on the runner (`is_running()`), not the task, and starts the
   check itself when the mission had already ended
   (`test_4_amended_a_stop_in_the_loops_last_sleep_still_starts_it`).

Measured after: `tests/test_arrival_reconfirm.py` 16 / 16.

**Third review** (`/code-review` on the second review's two fixes). All
three applied and mutation-checked:

1. The retry after a failed paid call could fall past the window and be
   lost, ending `expired` ("unreachable") although the cloud had been
   reached. The retry is now capped inside the window, and a window that
   runs out after a failed call ends `failed` with the real reason.
2. A later Stop (the Guide tab's close) could start a check that an earlier
   Stop had forbidden, if the in-flight tick ended the mission first. A Stop
   that lands while the runner is running now marks it `operator_stopped`.
   The interleaving is not reproducible through TestClient; the test sets
   the mark by hand and pins that the later Stop honours it.
3. The Stop path could start the check while `_finish` was still closing
   the policy and building the metrics row. `MissionRunner.finished` is set
   as `_finish`'s last act; `late_confirmation_pending()` requires it, and
   the Stop path waits for it (at most 5 s).

Measured after: `tests/test_arrival_reconfirm.py` 20 / 20.

**Fourth review: the coordinator's Thermos bug pass** (run as a separate
reviewer on `origin/dev...plan/3.53-arrival-reconfirm`). Nothing could move
the robot. All four findings verified against the code and fixed, each
with a test that fails on `a480cef`:

1. `stop_mission` checked the slot, awaited, then started the check with
   the generation read after the awaits: (a) two Stops inside the post-tick
   sleep both started one (the first orphaned, both able to pay at once);
   (b) a Start landing during a Stop let the Stop start a check for the OLD
   runner. Now the Stop reads the generation and claims the slot before its
   first await. `test_review_two_stops_at_once_start_one_check`,
   `test_review_a_start_during_a_stop_never_checks_the_old_mission` (both
   driven concurrently over an async ASGI client).
2. A cancel landing while the paid call was out shipped `paid_calls: 0`.
   The count is now committed in the same locked step as the check
   (`test_review_a_cancel_while_the_call_is_out_ships_the_call`).
3. The late row copied the counters frozen at `_finish` and could land
   before the original row (same key). It now takes the policy's current
   counters and waits for the original's ship
   (`test_review_the_late_row_lands_after_the_original_and_counts_the_late_call`).
4. The twin's watch was not stopped by a Drive-via-brain start, so a GET in
   flight could draw the old verdict over the new session, and it polled a
   dead brain forever. A watch token, a stop on that start, and a bound of
   5 failed polls (`test_the_late_watch_stops_on_a_guide_start`,
   `test_the_late_watch_stops_on_a_dead_brain`). No visual change, so the
   screenshots stand.

Noted, not changed (it predates 3.53): `stop_mission` sets
`state["task"] = None` after its await, which would also clear a task a
concurrent Start had just set.
