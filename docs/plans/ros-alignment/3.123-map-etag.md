# 3.123 The map is sent only when it has changed (an ETag on /world/map)

*`PLAN-ros-alignment.md` section 3.123; index: [README.md](README.md).*

**Why.** Explore reads the whole map every tick (`brain/explore.py`
`_note_seen()`), and ticks back to back (`tick_interval_s` 0). Measured on the
board 2026-10-29 on the six live 0.05 m SLAM maps (318 x 285, 0.23 MB): the
robot server encodes each reply in 11-12 ms -- C `json.dumps`, holding the
GIL beside the 20 Hz wheel loop (3.87 left a thin margin: worst tick 99 ms)
-- and the brain decodes it in ~8 ms, though SLAM changes the map about once
a second. 3.120's evaluation ranked it first among the per-tick costs; the
user took the recommendation on 2026-10-30.

**The change (written before building).**

* `GET /world/map` (`robot/server.py`) answers a usable map with an
  `ETag` of its `map_id` and `map_version` and `Cache-Control: no-cache`. A
  request whose `If-None-Match` names that same tag gets `304 Not Modified`
  and no body. The world is still asked for its map on every request (the
  simulator's `MockWorld.get_map()` observes as it is read), so the answer is
  always today's; only the encode and the transfer are skipped. The last
  encoded body is kept for its tag, so a client that does not send the tag
  (the twin) is not encoded again for an unchanged map. An unusable map has
  no tag and is never answered 304 or reused.
* `control/remote_world.py` `get_map()` sends the tag of the last map it
  received and, on a 304, returns that map. This is revalidation, not a
  cache: the server confirms each time that the map has not changed, so it
  is never stale, and `map_version`'s contract ("bumps whenever `cells`
  changes") is what makes the tag honest. Its docstring changes to say so.
* Nothing else changes: explore, the in-process sweeps (no HTTP) and the
  ROS bridge's own `/slam/map` (the robot server still reads it each
  request; out of scope, it needs an image rebuild).

**Criteria (written before building; CLAUDE.md section 7):**

1. **Never stale.** Tests through the real route and `RemoteWorld`: a
   changed `map_version`, a changed `map_id` (another house or SLAM
   session), and a map gone unusable each return the new map in full; a 304
   comes only for the same tag; the twin's plain fetch gets the same bytes as
   before; the world contract suite passes through `RemoteWorld`.
2. **Fewer encodes and decodes, live.** One explore mission on the ROS stack
   (`tests/demo_explore.py`, `home_first_floor`, this desktop, quiet): at
   least 80% of `/world/map` replies are 304s (counted from the robot
   server's access log), and the mission ends `found` with 0 contacts.
3. **Cheaper per fetch:** on this desktop, a 304 round trip through
   `RemoteWorld` on a live-size map costs at most a quarter of a full one
   (median of 200, one of the six live maps behind the real route).
4. **Nothing else moves:** `ready` passes; the explore and survey sweeps
   are unchanged (they do not cross HTTP).
