# 3.47 An arrival the cloud could not check: arrived_unconfirmed

*`PLAN-ros-alignment.md` section 3.47; index: [README.md](README.md).*

**Why.** Since handoff 2026-10-02 1a, a tiered mission ends `found` only
once a cloud call on the arrival frame says the target is in it
(`TieredVision.confirm_arrival()`). That guards against a local false
positive ending the mission on the wrong object, and it stays. But when the
cloud is *unreachable* rather than *disagreeing*, the confirmation raises,
B3.2's budget counts it, and the mission ends `failed` -- the same outcome as
a dead brain, though the robot did its job and is parked at what the local
tier believes is the target. Asked 2026-10-07 after a comparison with
XPENG/Banma's "on-device first, cloud-assisted" cockpit; the user chose to
build option 1: a distinct outcome that says what was and was not checked.

**Baseline, measured 2026-10-07 before building** (scratchpad probe,
`MissionRunner` -> `TieredVision` -> `MockRobot`, scaled house, the 12
`CLEAR_STARTS`, a cloud that raises `ConnectionError` on every call):

| mode | reached the target (<= `ARRIVED_CELLS`) | outcome |
|---|---|---|
| sync cloud | 12 / 12 | `failed` 12 / 12 |
| `async_cloud` | 12 / 12 | `failed` 12 / 12 |

Each ended "vision unavailable 3 times in a row", the last failure being the
arrival confirmation in most runs and a trigger call in one.

**The rule.** `arrived_unconfirmed` is the outcome when, and only when, B3.2's
budget runs out on a run of failures that includes an arrival (the lidar
rule, `brain/arrival.py`) whose identity confirmation raised, and the
failure that spends the budget is the cloud's. *(Tightened 2026-10-09 after
review, before the re-run below; the first version read a field left on the
agent, so a local fault after a failed confirmation was reported as an
outage.)* It is **not** `found`:
`memory.found` stays false, and nothing downstream may treat it as success.
A cloud that answers "no", or a call cap already spent, is a refusal, not an
outage, and keeps today's behaviour. Transient failures still retry within
the budget, so one dropped call does not downgrade a `found`.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Offline arrival is named:** with the cloud raising on every call, over
   the 12 clear starts in both sync and async mode, every mission that
   reaches the target (truth <= `ARRIVED_CELLS`) ends `arrived_unconfirmed`
   (bar: 24 / 24; baseline 0 / 24). Progress pair: every one of them ends
   within `ARRIVED_CELLS` of the target by ground truth, read by the test
   only.
2. **Never `found` without a cloud yes:** across the same sweeps, 0 missions
   end `found` with a dead cloud; `memory.found` is false on every
   `arrived_unconfirmed`.
3. **A refusal stays a refusal:** with a cloud that answers
   `target_visible: false`, 0 missions end `arrived_unconfirmed` (today's
   `test_arrival_confirmation.py` refusal tests unchanged), and a spent call
   cap is not reported as an outage.
4. **A blip does not downgrade:** a cloud that fails the first arrival
   confirmation (fewer failures than the budget) and then answers yes ends
   `found` on all 12 clear starts.
5. **A failure away from arrival stays `failed`:** a dead cloud under the
   `vision` policy (no local arrival) still ends `failed`.
6. **No regression:** 3.11's arrival sweep (`tests/test_arrival.py`) and the
   full suite pass unchanged.
7. **Live:** one tiered mission through the brain's HTTP API on the
   simulated robot, with `VISION_URL` pointed at a dead port, ends
   `arrived_unconfirmed`, read from `GET /mission/status`.

**Found by the live run, fixed:** the first live run's `status.tier.stats`
did not count the confirmations that raised -- the runner holds the last
SUCCESSFUL tick's `_tier`. On `arrived_unconfirmed` it now takes the stats
from the policy's own counters; criterion 1's test pins it (and fails
without it).

**Not done here, deliberately:**

* **The twin.** `web-twin/app.js` shows the new outcome as plain text with
  no colour class, and the end-of-mission toast is the error style (only
  `found` / `room_reached` are "ok"). A warn style needs a UI change, a UI
  test and a phone-size screenshot (CLAUDE.md section 7); left for the user
  to ask for.
* **What the operator does next.** The robot stays parked. Re-asking the
  cloud when the link returns (e.g. a `POST /mission/confirm`) is a
  separate decision.
* **`searched` was missing** from `brain_view._OUTCOME_LEVEL` (it falls
  through to WARN) and from the outcome lists in AGENT-HARNESS and the
  mission ARCHITECTURE spec. The two docs now list it; `brain_view` is
  untouched for it.

**Review, 2026-10-09** (`/code-review` and the Thermos bug pass on
`origin/dev...plan/3.47-offline-arrival`, CLAUDE.md section 6). Both found:

1. **The outcome came from a field left on the agent**, not from the
   failure that spent the budget: a failed confirmation followed by a LOCAL
   fault (perception wedged) ended `arrived_unconfirmed` with no error. Fixed:
   the confirmation's error carries that tick's readout; the runner holds it
   for the current run of failures only, and ends `arrived_unconfirmed` only
   if the last failure is the cloud's (`TieredVision._ask_cloud()` marked its
   calls -- superseded by the second review below; that method is gone). A strictly-the-confirmation version was tried first and failed
   criterion 1 (the sync sweep failed at its first start whose last
   failure was a trigger call to the same dead cloud; the count over all
   starts was not taken). Pinned by
   `test_review_a_local_fault_after_a_failed_confirmation_still_fails`.
2. **A failure landing after `stop()` rewrote the finished status.** Fixed:
   the writes happen under the lock, only while running. Pinned by
   `test_review_a_failure_after_stop_never_rewrites_the_status`.

Both new tests fail on the first version and pass now. Also from the
reviews: `brain_view` maps `searched` (OK), says why for
`arrived_unconfirmed`, and its outcome test reads the runner's `_finish`
calls instead of a hand list; the engineering spec describes the stats
refresh; criterion 4's sweep runs the second blip length on one start.
Rejected: the explore-policy staleness finding (explore gets no cloud
vision function from `brain_server`, so it never confirms; the new design
also uses only readouts from the current failure run). Deferred to the
follow-up section the user approved: the twin's warn style.

Re-measured on the fix: criteria 1-5 as above (24 / 24, 0 `found`, refusals
unchanged, blips `found`, `vision` dead cloud `failed`); criterion 7 live
again: `arrived_unconfirmed` at step 10, lidar 0.355 m, 4 cloud calls of
which 2 `arrival_confirmation`.

**Second review, 2026-10-09** (both reviewers on `1658596`). The first fix
marked every exception from the tier's cloud function as the cloud's, so a
local error inside it (a frame with no image), a wrong secret (401) or a
local error inside `confirm_arrival` read as an outage; and the arrival
was written, the lock released, then `_finish` called, leaving a window for
`stop()`. Fixed: `brain/navigate.py` raises `CloudUnavailable` for a
transport error or a 5xx only, the runner looks for it anywhere in the
cause chain, and `_finish` sets outcome, arrival and stats in one locked
step; a failure after `stop()` returns at once. Pinned by
`test_review_a_local_error_inside_the_cloud_call_is_not_an_outage` (fails
on `1658596`) and `test_review_navigate_raises_cloud_unavailable_only_for_outages`.
Criterion 4's sweep is back to all 12 starts at both blip lengths, so the
recorded 24 / 24 is pinned.

**Known limits, recorded rather than built around:**

* **A hanging cloud under the SYNC tier** (`tier_async_cloud: false`, not
  the shipped mode): the HTTP timeout and the runner's are the same 20 s
  (`vision_timeout_s`), so a hung trigger call ends as whichever fires
  first -- httpx's (`CloudUnavailable`, `arrived_unconfirmed`) or the
  runner's (unattributed, `failed`). Nondeterministic run to run. Under the
  shipped async tier the worker's own error is `CloudUnavailable` and a hung
  confirmation is attributed, so both forms of outage end the same way.
  Giving the HTTP call a total deadline under the runner's would close it;
  not done here.
* **A 5xx from our own deployment.** The vision service answers 502 for
  every error it catches, a Bedrock misconfiguration or an IAM error
  included, so that reads as unavailable; the reason carries the status
  and body. Separating them needs a change in `service/vision_analyze/`.
* **A confirmation that times out is put down to the cloud**, true of
  today's tiered policy (`confirm_arrival` waits only on cloud calls); a
  future policy that does local work there would need its own timeout type.
* **A person driving during the failure run.** Failed ticks send nothing,
  so a D-pad move is not a preemption, and the held readout would then be
  a pose the robot has left. Not observed; it needs the person and the
  outage at the same moment.

**Third review, 2026-10-09** (both reviewers on `91109d2`). Fixed: the
"vision failure" line is logged under the lock, so a `stop()` cannot put
its end line first, and a late failure still sends a stop; 408 and 429
count as unavailable; the cause check follows explicit causes only
(`__cause__`), so a local error raised while handling a cloud error is not
the cloud's; a confirmation's readout is kept only when that confirmation
itself failed because the cloud was unreachable (a 401 followed by outage
errors ends `failed`); the silent attribute guard logs. Pinned by
`test_review_only_a_confirmation_the_cloud_failed_is_kept` and the widened
navigate test (both fail on `91109d2`), and
`test_review_finish_writes_the_arrival_with_the_outcome_or_not_at_all`.
The rest are the known limits above. Criteria 1-5 re-measured on the
final code (13 tests in the module, the sweeps unchanged: 24 / 24
`arrived_unconfirmed`, 0 `found`, 24 / 24 blips `found`).
