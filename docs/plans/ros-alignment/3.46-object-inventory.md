# 3.46 Object inventory: record every object seen during a search (2026-10-07): criteria, written before building -- confirmed by the user 2026-10-07

*`PLAN-ros-alignment.md` section 3.46; index: [README.md](README.md).*

**Why.** A search walks most of the house and looks at most of what is in
it, then forgets all of it but the target. Asked "find my keys" tomorrow,
the robot starts from nothing even if it drove past them today. An
inventory -- every object seen, where it is on the map -- would let a
later search start where the thing was last seen, and lets a person ask
"what did you see?" after a walk. Raised by the user 2026-10-07.

**Today the robot cannot see anything but the target, by construction.**
`brain/perceive.py` prompts YOLOE with the target alone
(`set_classes([text])`, P22), so every other object in the frame is
invisible to the detector, not merely discarded. `MissionMemory.sightings`
(`brain/memory.py`) can hold any name, but a tiered mission fills it with
the target and only when the cloud confirms. So this needs a second way of
seeing, a way to place what is seen, and a store -- not a logging change.

## Scope

**In:** phases A-D below. The inventory is **recorded and reported only.**
No policy reads it; search behaviour is unchanged on every path.

**Out, and why:**
* **Keeping the inventory between missions** needs a map that survives a
  restart, which is open question 6 (map save and reload, decided in
  principle 2026-10-01, not built). An inventory in the coordinates of a
  map that is gone is noise. Phase E is written down so it is not lost,
  not built here.
* **Using it to search** (go to where the keys were last seen) needs E and
  `brain/planner.py`, which does not exist.
* (Uploading was out of scope in the first draft for privacy; the user
  decided 2026-10-07 to upload it -- see D.)

## Design

**A. Observation and landmark (`brain/inventory.py`, new).**
* An *observation* is one detection in one frame: class, detector
  confidence, source (`local` / `cloud` / `sim`), the capture stamp, the
  robot's map pose at that stamp (`WorldInterface.get_pose()`), the
  body-relative bearing (pan-corrected, as `Perception.bearing_deg`) and a
  range **or None**.
* **Range comes from the lidar scan at the detected bearing**, the same
  move 1.8 made for the target ("the detector points, the lidar
  measures"), with the same caveat: the scan sees the nearest surface at
  the D500's height, which for a low or small object can be what is behind
  it. A range the scan cannot vouch for (no return within the box's
  angular width, or a return far beyond what the box size implies) is
  None. A bearing-only observation is kept but never placed alone.
* A *landmark* is observations of one class fused into one place: placed
  observations of the same class within `MERGE_M` (0.5 m,
  `[PLACEHOLDER]` until criterion 4's sweep) join; a landmark carries the
  mean position, count, first/last seen, best confidence, and the
  observations' ids. Bearing-only observations of a class are attached to
  a landmark whose bearing they cross within 10 deg, else held unplaced.
* **Weight: repeated sightings raise belief, looking and not seeing
  lowers it** (asked by the user 2026-10-07). Each landmark carries a
  log-odds score, the occupancy grid's rule applied to objects, reported
  as `belief = sigmoid(score)`:
  * **A hit counts only from a new viewpoint**: the robot has moved
    >= 0.5 m or turned >= 30 deg since that landmark's last counted hit.
    Ten frames from one pose are one look; a detector that errs on an
    image errs the same way on the next one, so counting frames would
    give a stationary robot full confidence in its own mistake. Time
    alone never makes a new hit.
  * **A miss**: the landmark lies inside the field of view, within 3 m,
    the scan at its bearing is not shorter than its range minus 0.3 m
    (not occluded), the inventory pass ran on that frame, and it did not
    report the landmark's class nearby. Same new-viewpoint rule.
  * `L_HIT` +0.85 (one hit reads 0.70), `L_MISS` -0.4, prior 0, score
    clamped to +/-4: `[PLACEHOLDER]`s, set on the sim sweep's first half
    and judged on its second (criteria 3-5). Detector confidence is not
    used as the increment, because it is uncalibrated across classes (the
    same reason the target gate moved to `probability`, P-series).
  * **Repetition shows the answer is consistent, not that it is
    correct.** A detector that calls a mug a "vase" every time would earn
    a confident vase. So a landmark keeps a class vote (counts per label
    over its counted hits), reports the majority, and is flagged
    `disputed` when the runner-up has 1/3 or more of the votes. Merging
    (`MERGE_M`) is by position over related labels, not exact class, or
    a vote could never form.
  * **Reported vs held:** landmarks at `belief >= 0.8` (two independent
    hits and no misses) are the inventory; the rest are kept as
    candidates, not dropped, because a small object seen once is still
    worth a look in phase E. Both are in `GET /mission/inventory`,
    labelled.
  * Misses matter most in phase E (things move between missions); here
    they stop one false hit from surviving a walk that passes it again.
  * Cloud `important_objects` (C) are room-level and never change a
    landmark's score.
* **Loop closure is measured before it is handled.** A landmark is placed
  in the map pose at capture time. SLAM's pose jumps on a closure; since
  3.40 two tours of the furnished home agree within 4.2 cm, so the error
  this leaves may be below the placement bar. Criterion 4 decides: if it
  fails because of closures, re-projection (store odometry pose plus the
  `map->odom` transform per observation and re-place on correction) is
  built then, not speculatively now.

**B. The simulator as the measuring instrument.**
* 1.12 forbids running a real detector on a raycaster render, so the sim
  measures the **geometry and fusion**, not the detector. It already
  publishes `detections` (every object in the picture with bearing and
  range, R1/3.32) for `FrameReportedPipeline`. Phase B feeds ALL of them
  -- not just the target's -- into the inventory, with injected noise
  (bearing sigma 3 deg, a 10% per-frame miss rate, 5% of frames with one
  wrong-class label) so fusion is tested against a detector that errs.
* **Range is taken from the scan, not from the sim's ground-truth
  distance**, so the measurement goes through the path the car uses.
* **Ground truth** is per *instance*: the connected cells of one name in
  `OBJECTS`. `home_first_floor` has 24 classes but only one small object
  (the red backpack); the rest is furniture. A **new map variant,
  `complex_house`**, adds about 15 small objects (shoes,
  mug, keys, bag, toy, laptop...) on the floor in plausible places, so
  the inventory is tested on objects the size of real search targets.
  **The user asked (2026-10-07) for the new house to be complex as
  well**, so it is a new house, `complex_house`, not a variant: more
  rooms, an L-shaped hall, a long corridor, a dead-end room, a second
  route round a loop (so SLAM sees a loop closure, which criterion 4
  needs), furniture, and about 15 small objects. Doors 0.9 m like
  `scaled_house`, so the Rover fits (`tests/chassis_fit.py`).
  **The existing map is not edited**: 3.43/3.44's stall criteria and
  3.40's SLAM bars are measured on it, and small solid objects (3.9) would
  change its navigation.

**C. A detector that names everything (on board).**
* YOLOE's prompt-free weights (`yoloe-11s-seg-pf.pt`; a built-in
  vocabulary of a few thousand classes, the exact count to be read off the
  weights) as a **second model**. The target pass is untouched: same
  weights, same prompt, same 0.8 gate. Cheaper alternatives (one model
  with a large text prompt) change the target pass P23 measured, so they
  are not the first try.
* **On keyframes only**: when the robot has moved 0.5 m or turned 30 deg
  since the last inventory frame, or 2 s have passed. The target pass
  keeps every frame.
* **Cloud answers count too**, at no extra cost: a cloud call the tier
  already makes can return `important_objects` (`brain/vision.py`'s
  field). Those are names without boxes, so they are bearing-free and
  stored as room-level observations ("seen in the kitchen"), not placed.

**D. Mission wiring and reporting.**
* `MissionRunner` owns one `Inventory` per mission and feeds it from
  `_perception` / the frame's detections after the step.
* `GET /mission/inventory` on the brain (route guard entries, per section
  6's rule); the mission log gets one summary line at the end.
* **Uploaded to S3 (decided by the user 2026-10-07).** At mission end the
  brain writes the inventory to the recordings bucket under the same
  rules as question 6's map backup: a private, encrypted, versioned
  prefix `inventory/<robot>/<mission_id>.json`, labels, positions,
  beliefs and votes only -- **no image crops**. An upload failure is
  logged and never fails the mission.
* The twin is **not** changed in this section.

**E. Not built here:** persist with the saved map (`map_id` keyed, beside
`slam_toolbox`'s pose graph, on the NVMe), age out landmarks not re-seen,
and let a search start at the last-seen landmark of its target.

## Criteria (written before building; CLAUDE.md section 7)

Stability and progress are paired: 3-4 are the progress half (it finds
and places things), 1-2 and 5's precision the stability half (it does not
break or invent).

1. **The search is unchanged.** With the inventory on and off, the same
   tiered and frontier sweeps (`scaled_house` and `home_first_floor`,
   same seeds, in process through `MissionRunner`) produce **identical
   action sequences and outcomes**. Pinned by a test that fails if any
   policy reads the inventory.
2. **The budget holds on the Jetson (15 W).** Target pass p90 within 10%
   of today's 110 ms on frames where the inventory pass does not run;
   **p90 of target + inventory pass under 250 ms** on keyframes; 0 late
   wheel-loop ticks over a 10-minute run with both passes live (3.37's
   headroom measure).
3. **It finds what it saw (sim, `complex_house`, 20 missions
   from spread starts; `L_HIT`/`L_MISS` set on missions 1-10, every bar
   below judged on 11-20).** Of the instances seen from at least 2
   distinct viewpoints (A's rule) within 3 m during a mission, **>= 90%
   are reported** (`belief >= 0.8`) with the right majority class; small
   objects scored separately and **>= 80%**.
4. **It places them (same runs).** Distance from a landmark to the
   nearest cell of its true instance: **median <= 0.20 m, p90 <= 0.50 m**.
   Duplicates: **<= 1.2 landmarks per true instance**. Reported split by
   whether a loop closure occurred during the mission (decides A's
   re-projection question).
5. **It does not invent, and the weight earns its place (sim, same
   runs, injected wrong-class labels on).** **>= 95%** of REPORTED
   landmarks lie within 1.0 m of a true instance of their majority
   class. The same precision over ALL landmarks (candidates included) is
   recorded beside it; if the two differ by under 5 points the weighting
   is not doing work, which is written down as such. A unit test pins
   the independence rule: 50 frames from one pose give one hit (red on a
   per-frame count).
6. **The real detector is good enough to be worth storing (rig walks).**
   300 keyframes from the valid rig walks, labelled for every object with
   `label_assist` candidates adjudicated by hand (written to a separate
   `inventory_labels.json`; `labels.json` is the target reference and is
   not touched). Confidence threshold chosen on half the frames, measured
   on the other half: **label precision >= 70%** at that threshold, and
   recall reported per class. If this fails, phase C does not ship and
   the cloud-only inventory (C's last bullet) is what remains.
7. **One live mission.** A tiered mission on the live local stack (this
   section's ports, `complex_house`) through the brain's HTTP
   API ends with a non-empty `GET /mission/inventory` whose entries match
   the map within criterion 4's bars, and the log line says so.

## Order and cost

A + B first (in process, no models, no Jetson), which settle 3-5 and
decide re-projection. Then D and criterion 7. C last: it needs the
weights, a labelling session for criterion 6 (about two hours of
adjudication), and a Jetson run for criterion 2. Specs: a new
`docs/perception/` section for the inventory's what/why and its
ENGINEERING counterpart, in the same commit as the code (decision 0001).

## Decided by the user (2026-10-07)

2. The inventory is uploaded to S3 (D), labels and positions only.
3. A fourth `SIM_MAP`, `complex_house`, complex in layout as well as
