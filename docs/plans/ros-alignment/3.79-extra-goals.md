# 3.79 Why explore sends more goals since 3.77

*`PLAN-ros-alignment.md` section 3.79; index: [README.md](README.md).*

**Status: measured 2026-10-14; criterion 2's rule says speed explains it.**
Planned 2026-10-13 (the user: "Yes" to investigating 3.77's open item).
Criteria written before any run.

**Why.** 3.77's three live `home_first_floor` runs (rule) sent 28 / 28 / 31
goals; 3.65's three rule runs on the same house the day before sent
21 / 21 / 22. 3.77 changed no answer (its criterion 1: identical choices
for the same map and pose), only how fast a choice is made (laptop ~500 ms
-> ~60 ms). 3.77 left one untested explanation: a faster choice is made
sooner after a goal ends, on a map the lidar has had less time to fill.

**What the logs already say** (`/tmp/vision-picar-3.65`, `-3.77` brain
logs, `explore {json}` events; read before planning):

| | 3.65 rule (3 runs) | 3.77 (3 runs) |
|---|---|---|
| goals sent | 22 / 21 / 21 | 28 / 28 / 31 |
| goals succeeded | 16 / 16 / 15 | 23 / 25 / 28 |
| goals timed out or aborted | 4 / 3 / 4 | 3 / 1 / 2 |
| goals refused before nav2 | 18 / 18 / 17 | 25 / 27 / 30 |
| travel m | 45.8 / 44.0 / 44.0 | 58.9 / 64.6 / 68.8 |
| mission s | 775 / 586 / 679 | 698 / 621 / 642 |

The extra goals are **successful** ones, not failures, and the robot
travelled about 40% further in about the same time. **The two sets are not
the same code apart from 3.77:** between them `dev` took 3.70 E1-E6 (end
states, room goals and their wedge rule), 3.74 B (the floor band in
`robot/safety.py`), 3.76 A-B (arbitration and driver fixes) and 3.74's
creep events, with brain identities 041888b vs 29414ca. Any of those can
change goal counts without 3.77.

**The experiment: speed only, on today's `dev`.** Both arms run the same
code (`dev` at 3.77's merge or later, with 3.76 E); one is slowed back to
the old choice time and nothing else:

* **F (fast, as shipped).** `tests/demo_explore.py one`, rule policy.
* **S (slow).** The same, with a delay of 450 ms added inside every call to
  `find_frontiers` (after the pose and map are fetched, before the
  decision), from an evaluation-only `sitecustomize.py` loaded by the brain
  process; no product code changes. 450 ms is the old laptop choice time
  (~500 ms, 3.65 amendment 3) minus the new (~60 ms, 3.77).
* Three runs each, **interleaved F S F S F S**, so that load from parallel
  sessions falls on both arms alike. Machine load (1-minute average) is
  recorded at each run's start.

## Criteria (written before any run; CLAUDE.md section 7)

1. **Valid runs.** Every run `found`, 0 contact samples (as 3.77
   criterion 3). A run that fails this is recorded and repeated once; the
   comparison uses the valid runs.
2. **The decision rule** on median goals sent (the gap to explain is 3.77
   minus 3.65 = 28 - 21 = 7):
   * **Speed explains it** if median(S) <= median(F) - 4 (more than half
     the gap closes by slowing the choice alone).
   * **Speed does not explain it** if |median(S) - median(F)| <= 2. Then
     the extra goals come from the other changes on `dev`, and this section
     says so; finding which one is a further step, not done here.
   * **Otherwise inconclusive:** three more runs per arm, once,
     interleaved; the same rule on all six a side, then recorded either way.
3. **Reported, not judged:** goals succeeded / failed / refused, travel,
   mission seconds, `choice_ms` per arm.

## Amendment 1 (2026-10-13, after one invalid run, before any counted run)

The first run (arm F, started 20:09 at a 1-minute load of 8.4 on 8 cores:
another session's 3.70 ROS stack had been running for 13 h, the Neural
Engine compiler and Spotlight were busy) did not finish: 1,800 s, 25
goals, 14 failed, 28.6 m travelled (3.77's runs: ~640 s, ~60 m). The
simulator and ROS do not keep real time under that load, so the run says
nothing about goal choice. It is kept in `runs.jsonl`, marked invalid,
and not counted. Another session's live run took the heavy-run lock the
moment it was released.

* **Before every run** the runner now waits until no other live run holds
  the heavy-run lock **and** the 1-minute load has been under 4.0 for
  three checks a minute apart; the load at start is recorded.
* **Criterion 1 also requires** a run to start under that gate; runs that
  did not are invalid. The decision rule (criterion 2) is unchanged.
* If the machine is not quiet for long stretches, the runs wait; this
  section does not lower the bar to get them done.

**What this does and does not say.** Slowing only the choice, on today's
code, brought the median back from 29 to 22 goals (3.65's rule runs: 21).
So the extra goals follow from 3.77's speed, not from the other changes on
`dev`. It did not cost or save time to find: median mission seconds F 758,
S 752. The fast arm is also the noisier one (21 to 36 goals; S 20 to 26).
Its extra goals are ordinary frontier goals (median size 0.8-1.0 m, path
1.7-1.9 m, like S), and it is refused before nav2 more often. **Why** a
faster choice sends more goals is not established here; one candidate, not
tested: a goal chosen ~450 ms sooner after the last one ends is chosen on a
map the lidar has filled less, so it more often picks a frontier the next
scans would have closed. Three runs a side; the rule was met by 3 goals
over its margin.

**What to do with it** (open, for the user): goals are cheaper than they
look (time unchanged, 0 contacts), so nothing needs fixing to keep 3.77. If
fewer goals matter in their own right (wear, battery on the Rover), the
choice could wait for a fresh scan after a goal ends -- a behaviour change
needing its own section and criteria.
