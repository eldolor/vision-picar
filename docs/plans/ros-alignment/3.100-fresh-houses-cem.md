# 3.100 The evolutionary (CEM) goal policy on 3.65's 613 fresh houses

*`PLAN-ros-alignment.md` section 3.100; index: [README.md](README.md).*

**Why.** The user, 2026-10-25: "We never evaluated the new set of 600+
homes using the Evolutionary model. We only used the Gradient model ... and
never compared the fresh set of results against what the Evolutionary model
would have shown."

3.65 phase 2 learned explore's goal choice twice:

* **The evolutionary model:** `explore_goal_policy: learned`, ten linear
  weights trained by the cross-entropy method (`brain/explore_goal_weights.json`).
  On the 200 reused test houses it found 196 with median goals -18.2% and
  metres -10.7% (bar 20%): criterion 1 FAILED, so it was never carried
  further.
* **The gradient model:** `explore_goal_policy: network`, linear + MLP
  trained by PPO (`brain/explore_goal_net.json`). On the same 200 houses
  -27.3% (met); then on 613 fresh houses (amendment 3 A, ProcTHOR `test`)
  only -11.1% goals, +9.3% metres, 608 found vs the rule's 606: FAILED.

Only the rule and the network ran on the fresh houses
(`evaluations/explore-365/fresh-{rule,network}.json`); there is no
`fresh-learned.json`. So it is unknown whether the gradient model's drop on
unseen houses (-27% -> -11%) is the same for the evolutionary one, or
whether the simpler model generalises better and would have beaten the
network there. This section runs the missing arm. Nothing is retrained; the
committed weights are run as they are.

**What is run.** `evaluations/explore-365/evaluate.py 0 613 <arm> OUT.json test`
(3.65's harness, `FakeNav`, in process, no cloud call) on every usable
`procthor:test` house, three arms on today's `dev`:

* `learned` (the evolutionary model) -> `fresh-learned.json`;
* `rule` and `network` again -> `fresh-{rule,network}-3100.json`, because
  explore has changed since 2026-10-12 (3.69's later fixes, 3.76's batches,
  3.85's escape and approach counting). The 2026-10-12 files are kept as
  recorded and never overwritten.

**Criteria (written before measuring; CLAUDE.md section 7):**

1. **Clean:** every arm ends 613/613 missions cleanly.
2. **The evolutionary model against the rule** (amendment 3 A's bars,
   unchanged, n = 613): learned found >= rule found - 4; median goals per
   found mission >= 20% lower, **or** median metres >= 20% lower. Judged
   against today's rule run.
3. **The evolutionary model against the gradient model** (the comparison
   the user asked for; reported, no bar): found, median and mean goals and
   metres per found mission, mean reward (3.65's), per-house wins and
   losses on the houses both find, and the houses each loses that the rule
   finds.
4. **Generalisation gap** (reported): each model's median-goal saving on the
   200 test houses against its saving on the 613 fresh ones (learned
   -18.2% -> ?, network -27.3% -> ?).
5. **Reproducibility** (reported): today's rule and network rows against
   the 2026-10-12 files, house by house. If they differ, today's runs are
   the comparison and the difference is recorded with its likely cause.

**What follows from the result.**

* Criterion 2 met: the evolutionary model becomes a candidate default. The
  default stays `rule` until the user decides, and a change would still owe
  amendment 3's B (5 + 5 live runs in `home_first_floor`, median goals no
  more than the rule's) and C (goal-choice time on the Jetson; since 3.77
  the rule's p90 is 90 ms, and the linear model scores the same features)
  and a re-pin of 3.69's ProcTHOR sweep.
* Criterion 2 failed: recorded as failed; the default stays `rule`. Either
  way the numbers join 3.96's baselines (its test arms are the rule and
  3.65's network; the evolutionary model can be added beside them).

**Cost.** No cloud call, no board. Laptop CPU: three arms of 613 houses
(3.65's amendment 3 ran two arms of the same set in one session). One heavy
run at a time per `PARALLEL-SESSIONS.md`.

**Machine check (2026-10-25, before the runs were read).** 3.65's runs were
on the user's MacBook (ARM); these are in a Claude Code cloud container
(x86_64, Python 3.13.17, numpy 2.5.4). The harness runs on simulated time
(`clock=lambda: grid.sim_time`) and scores outcome, goals and metres, never
seconds, so the machine should not matter unless floating point differs.
Checked directly: amendment 3's own commit (`4cd6eb7`) re-run here on the
first 40 fresh houses.
* `network` (the float-heavy MLP): **40/40 identical** to `fresh-network.json`
  (outcome, goals, metres, steps).
* `rule`: 39/40 identical. House 39, a miss, reads `exhausted` here and
  `searched` in the file, with 173.7 m vs 178.5 m (same goals and steps):
  the file was written before the rebase onto 3.70 (merged two minutes
  before `4cd6eb7`), which renamed the end states. Code, not machine.

So the cloud's numbers are comparable with the MacBook's; criterion 5's
differences, if any, come from code that changed on `dev` since.

## Results (2026-10-25): criterion 2 FAILED; the evolutionary model matches the gradient one

Three arms on `dev` at `9a5b40e` (one run each, ~10 min an arm in the cloud
container; `fresh-learned.json`, `fresh-{rule,network}-3100.json`;
`compare_3100.py` prints every number below).

| 613 fresh houses | Rule | Evolutionary (CEM) | Gradient (PPO) | Bar (CEM) |
|---|---|---|---|---|
| Found | 606 | **608** | 608 | >= 602 -- met |
| Median goals per found | 9 | **8 (-11.1%)** | 8 (-11.1%) | >= 20% lower -- **missed** |
| Median metres per found | 25.8 | **27.0 (+4.7%)** | 28.2 (+9.3%) | or >= 20% lower -- **missed** |
| Clean | 613 | 613 | 613 | 100% -- met |
| Mean goals / metres per found | 12.06 / 39.72 | 11.12 / 41.06 | 10.96 / 40.64 | (reported) |
| Mean reward | 0.320 | 0.348 | 0.356 | (reported) |

1. **Clean: met** (613/613 for every arm).
2. **Against the rule: FAILED.** Found met (608 vs 602); median goals -11.1%
   and metres +4.7%, so neither 20% half is met. The default stays `rule`.
3. **Against the gradient model** (reported): **almost the same policy.**
   Both find the same 608 houses; they gain the same 6 over the rule (39,
   259, 358, 499, 560, 675) and lose the same 4 (221, 247, 289, 961). Of the
   608 both find, 559 take the same number of goals, the evolutionary model
   fewer in 24 and the gradient model fewer in 25. The gradient model's
   reward is 0.007 higher; the evolutionary model drives 1.2 m less at the
   median. Against the rule each sends fewer goals in ~316 houses and more
   in 156.
4. **Generalisation gap** (reported): evolutionary -18.2% on the 200 test
   houses -> -11.1% fresh; gradient -27.3% -> -11.1%. The gradient model's
   extra 9 points on the test houses did not carry over; on unseen houses
   the two land on the same median.
5. **Reproducibility** (reported): today's rule and network **summaries
   equal the 2026-10-12 files** (network mean reward 0.3555 vs 0.3556).
   House by house, the rule differs in 19 and the network in 21, none
   changing found/not found: 7 + 5 misses renamed `searched` -> `exhausted`
   (3.70), 12 + 15 metres only, and one network house's goal count.

**What it means.** The gradient model's network adds almost nothing over
its own starting point: amendment 2 started its linear part at the CEM
weights with the MLP's output at zero, and on fresh houses the two send the
same number of goals in 92% of the houses both find (559 of 608). Both learned models beat the rule on finds (+2)
and reward, and both save about one goal at the median, half the bar. So
3.65's result was not "the gradient method generalises worse": both methods
reach the same ~11% on unseen houses, which points at the ten features as
the limit (3.88 B's and 3.96's reading), not the learner. For 3.96: the
evolutionary model is an equal baseline and cheaper (10 weights, no MLP;
its Jetson choice time since 3.77 is not measured here).
