# 3.81 Rover memory budget: measure where memory goes, then trim

*`PLAN-ros-alignment.md` section 3.81; index: [README.md](README.md).*

**Why.** The user, 2026-10-13: "Should we plan to optimize the code that
runs on the rover, garbage collection etc to free up more memory? If so,
let's add this to the plan." This serves 3.80, the tiered identity with
Qwen resident on the Jetson. 3.78.F measured 191 MB free beside the
whole stack with TensorRT Qwen loaded (T), and 606 MB with the shrunk
engine VE, which is the model 3.80 uses. The floor is 0.5 GB (the user,
2026-10-14), so VE's margin is about 100 MB.

**What is known already (3.78, Jetson Orin Nano Super, 15 W, desktop off),
from the board's `MemAvailable` (one 7.6 GB pool shared by CPU and GPU):**

| state | `MemAvailable` | step |
|---|---|---|
| idle board | about 6.0 GB | -- |
| + robot server, brain, split simulator, ROS container (SLAM, nav2), mapped | 5.6-5.8 GB | about 0.3 GB |
| + one YOLOE + CLIP pipeline at 4 Hz (its own torch process) | about 4.5 GB | **about 1.1 GB** |
| + Qwen2.5-VL-3B under TensorRT, answering | 0.19-0.26 GB | **about 4.3 GB** |

Under T, zram swap also held 0.7-0.85 GB.

So most of the memory is in **two GPU processes** (perception and the
VLM), not in the Python services. Each GPU process carries its own CUDA
context, CUDA/cuDNN/cuBLAS libraries and allocator caches, on top of its
weights. Garbage collection belongs on the list, but the evidence says
it is not where most of the memory is. 3.37 already tuned the robot
server's GC, for latency.

## Approach: measure first, then trim the largest items

1. **Account for every megabyte** with the whole stack running and T
   resident (3.78.F's conditions):
   * per process: PSS and RSS (`/proc/<pid>/smaps_rollup`), split into
     anonymous, file-backed and GPU-mapped (`/sys/kernel/debug/nvmap` per
     client, or `jtop`);
   * per GPU process: weights, CUDA context, library code, and allocator
     cache (`torch.cuda.memory_stats` for perception; Edge-LLM's own
     report for T);
   * the ROS container per node; zram, and what it holds;
   * the kernel, the page cache and the reserved carve-outs.

   The result is a table that adds up to the 7.6 GB.
2. **Candidates, ranked by that table** (none is chosen before step 1's
   numbers):
   * **One GPU process instead of two:** run YOLOE + CLIP inside the VLM
     service, or the reverse, to drop one CUDA context and its libraries
     (usually several hundred MB on Jetson). The cost: a crash takes both.
     3.80's isolation rule (the VLM is the OOM victim) has to survive it.
   * **The perception models under TensorRT,** for memory this time:
     3.41 measured 165 MB less (one pipeline) and rejected the change for
     drift and speed, not memory.
   * **Allocator caches:** cap PyTorch's caching allocator
     (`PYTORCH_CUDA_ALLOC_CONF`) and trim it after load; size TensorRT's
     execution context to the real input (3.78's KV 1024 trim saved 90 MB).
   * **Python services:** import only what each process uses (the robot
     server and brain import graphs), `gc.freeze()` after start-up,
     `malloc_trim`, and fewer uvicorn workers. The likely gain is tens of
     MB per process; measure it.
   * **The ROS container:** nav2 and slam_toolbox parameters that size
     costmaps and the scan buffers (the map grows with the house); drop
     any node the rover does not use.
   * **The OS:** the desktop stays off (it already is for the stack),
     services the rover does not need are disabled, and zram is sized on
     purpose.
3. **Re-measure 3.78.F's loaded window** after each accepted trim.

## Criteria (written before measuring; CLAUDE.md section 7)

1. **Accounting:** step 1's table explains >= 95% of the 7.6 GB with the
   whole stack and VE resident.
2. **Freed memory:** the accepted trims raise 3.78.F's loaded-window
   `MemAvailable` minimum by **>= 1.0 GB** from VE's 606 MB (amended
   2026-10-14, before any measurement: the baseline was T's 191 MB, and
   VE is now the model in use).
3. **Nothing else gets worse:** perception p90 <= 250 ms; VE p90 to the
   decision <= 1.6 s under load; 0 late wheel-loop ticks in the loaded
   window; nav2 goals all succeed; the suite passes.
4. **Progress, paired with 2:** a mission in `home_first_floor` with VE
   resident still ends `found`.

## Measured 2026-10-14: A, where the memory is

**How.** 3.78.F's loaded window under VE, re-run
(`tools/jetson/headroom_identity.sh` with `RUNTIME=trt ACCOUNT=1`,
`ENGINES=~/bench-378/ws91/q25VE/engines`, image
`vision-picar-ros:plan-3.78`, 12:18-12:31 CDT, rev `af6151d`). `ACCOUNT=1`
adds `tools/jetson/memory_account.py`, run as root every 5 s for the whole
run: `/proc/meminfo`, the GPU's allocations per process (nvmap's
`iovmm/clients`; CUDA allocates from the one RAM pool through nvmap),
nvmap's page pool, zram's `mm_stat`, and every process's `smaps_rollup`.
Perception logs torch's allocator (`PERCEPTION_TORCH_LOG`). The table is
taken at the window's lowest `MemAvailable`. Records:
`evaluations/memory-381/A1/`.

* **The first attempt is void.** The board's new worktree had no YOLOE
  weights, so perception's first frame downloaded 572 MB inside the
  window. The harness now waits for perception's first frame before the
  window opens (3.78's own warm-up rule), and the rerun is the one below.
* **The rerun repeats 3.78.F under VE:** `MemAvailable` minimum **664 MB**
  (F2: 606; median 683 vs 635), VE p90 1.33 s (F2: 1.32), 0 failed calls,
  0 OOM, 0 late wheel ticks of 6,841, nav2 18/18, perception p90 181 ms
  over 1,728 frames, 64.4 C. So run-to-run noise in the minimum is about
  60 MB. Criterion 2's baseline stays F2's 606 MB, as written.

**Criterion 1, accounting: met.** At the minimum, the kernel's categories
explain **97.7%** of MemTotal (7,620 MB; bar 95%). The per-process sums
match the kernel's totals exactly: anonymous memory 2,233 MB = `AnonPages`,
GPU memory 4,046 MB = nvmap's total.

**The VLM driver, split.** Its 3,382 MB of GPU memory hold the engines
(on disk: LLM 1,450 MB, visual encoder 1,293 MB, FP8 embedding 306 MB;
3,049 MB together) plus 333 MB of TensorRT activations, the KV cache
(about 36 MB at 1,024 tokens) and its CUDA context (a bare `cudaFree(0)`
costs 65 MB of GPU and 12 MB of heap, `tools/jetson/cuda_context_probe.py`).
Its 519 MB host heap is not split further here (TensorRT's and the
plugin's runtime); the visual encoder at FP16 is the largest single item
on the board.

**Perception, split** (the window's allocator log;
`tools/jetson/perception_memory_probe.py` and two probes on the quiet
board, `perception_probe.jsonl`):

| perception | MB |
|---|---:|
| GPU: torch tensors (CLIP RN50 389, of which its text tower 241; YOLOE 52; activations) | 478 |
| GPU: torch's allocator cache (reserved - allocated) | 72 |
| GPU: CUDA context, cuDNN, cuBLAS | 114 |
| heap: `import torch` + CUDA + cuDNN initialised, before any model (probe: 348) | ~350 |
| heap: importing ultralytics and open_clip | ~134 |
| heap: loading YOLOE and CLIP (YOLOE also keeps a 52 MB CPU copy beside its GPU copy) | ~96 |
| heap: **left behind by YOLOE's text encoder on the first frame** | **~410-480** |
| heap: the rest (kernels loaded on first use, frames) | ~50 |

* **The text-encoder residue.** On its first frame, YOLOE builds
  MobileCLIP (`mobileclip_blt.ts`, a 572 MB TorchScript file) to encode the
  prompt, then drops it. Alone on the board: building it on the GPU and
  encoding one prompt adds 412 MB of heap and 582 MB of GPU; after it is
  dropped, the heap stays (761 MB vs 349) and torch keeps the GPU part
  cached. In the pipeline, the first frame adds 483 MB of heap and
  `malloc_trim(0)` gives back 17 MB, so it is held, not fragmented. The
  GPU part does come back in the pipeline (reserved 550 MB in the window).
* **A torch GPU process costs about 0.6 GB before any model** (probe:
  `import torch` 405 MB PSS, + CUDA + cuDNN 599 MB, of which GPU 107).
  That is the price of the second GPU process.

**What this says for B (not chosen here; B ranks them against the table):**
* The two GPU processes hold 5.9 of the 7.6 GB. The Python services are
  about 0.2 GB together, and the ROS container 0.25 GB: GC or import trims
  there are worth tens of MB at most.
* The largest items are, in order: VE's weights (3.05 GB), perception's
  heap (1.1 GB, of which ~0.45 GB is the text-encoder residue), VE's heap
  (0.52 GB), perception's GPU (0.66 GB, of which CLIP's text tower is 0.24
  GB and used once per target).
* **nvmap's page pool is not hidden headroom.** At idle it holds 952 MB
  (freed GPU pages, left from earlier runs; `MemAvailable` does not count
  them), but it drains to 0 as soon as perception loads, so the window's
  minimum is not understated by it.
* `MemAvailable` before anything ran, desktop off: 5,996 MB; with the stack
  mapped and perception loaded: 4,672 MB (median); with VE answering: 683
  MB (median).

**Related, recorded in 3.78:** under a brain `explore` mission on the
Jetson, the robot server's wheel loop was late on 8.8% of moving ticks
(worst 0.39 s), with no VLM loaded. That is a safety-loop question, not a
memory one, and is its own section.

## Amendment 1 (3.81.B, 2026-10-14): the trims, ranked, and their criteria

Written before any trim is built or measured. **The user's decision
(2026-10-14): build and measure T1-T3 now; choose T4 or T5 only after C
has measured what T1-T3 free.**

**Ranked by A's table** (memory freed for the risk taken; every saving is
an estimate read off A's table, not a measurement):

| rank | trim | estimate | risk |
|---|---|---:|---|
| T1 | YOLOE's prompt embedding without building MobileCLIP in perception's process | ~0.45 GB heap, and no 0.58 GB GPU spike on a new target | none to the answers if the embedding is the same |
| T2 | CLIP's text tower freed once the mission's texts are encoded | ~0.24 GB GPU | none to the answers; a new target must re-encode |
| T3 | small: YOLOE's CPU copy, torch's allocator cache, `foxglove_bridge` off by default | ~0.1-0.15 GB together | low; Foxglove becomes opt-in |
| T4 | perception inside the VLM's process (one CUDA context and one set of libraries) | ~0.4-0.6 GB | breaks 3.80's rule that the VLM is the OOM victim |
| T5 | VE's visual encoder at INT8/FP8 instead of FP16 (1.29 GB on disk) | ~0.6 GB | needs a paid GPU-host export and an accuracy re-run |
| -- | GC, import trims, uvicorn workers in the Python services | tens of MB | not worth a step: the services hold ~0.2 GB together |

T1-T3 together are about 0.8 GB, short of criterion 2's 1.0 GB, which is
why T4 or T5 is decided after C (step D).

**Every trim's shared bars**, measured in 3.78.F's loaded window
(`headroom_identity.sh RUNTIME=trt ACCOUNT=1`, VE, same image and
engines as A1), on top of criteria 3 and 4:

* **Same answers.** On the pinned frame set
  (`tools/jetson/bench_perception.py`'s `FRAMES_FILE`), every frame's
  boxes and CLIP probability equal the untrimmed pipeline's (max |dP| <=
  1e-4, same box count on every frame), on the board.
* **Its own saving is measured,** from the accounting table at the
  window's minimum (`memory_account.py table`), in the component and
  column it targets. A trim that saves less than its bar below is
  recorded as failed and not kept.
* **No new peak.** With VE resident and the stack running, starting a
  mission with a new target never takes `MemAvailable` below 0.5 GB (the
  floor), sampled every 1 s through the start.

**T1, YOLOE's prompt embedding.**
1. The embedding YOLOE is given equals `get_text_pe([target])`'s on the
   same device (max abs difference <= 1e-5).
2. Perception's heap (anon PSS) at the window's minimum drops by **>= 350
   MB** from A1's 1,113 MB.
3. A second target in the same process gets its own correct embedding
   (bar 1 again), and the time from a new target to its first perceived
   frame is no longer than today's (measured before and after, same board).

**T2, CLIP's text tower.**
1. Every text the pipeline encodes for a mission (target, distractors, the
   soft gate's label names) has features equal to today's encode (max abs
   difference <= 1e-5).
2. Perception's GPU memory at the window's minimum drops by **>= 200 MB**
   from A1's 664 MB.
3. Bar 3 of T1, for CLIP's texts.

**T3, the small ones.** Each is kept only if it saves **>= 10 MB** on its
own and changes no answer; together they must save **>= 80 MB**.
* YOLOE's 52 MB CPU copy beside its GPU copy dropped.
* torch's allocator cache bounded or released after load (72 MB reserved
  beyond allocated in A1); perception p90 must still meet criterion 3.
* `foxglove_bridge` started only when asked (an env flag in the launch
  file), so the Rover runs without it by default (14 MB in A1). Its
  read-only setting stays when it is on.

**Then (step D, the user's choice): T4 or T5,** with what C measured in
hand. Criterion 2 (>= 1.0 GB over 606 MB) is judged after D, on the trims
that were kept; if T1-T3 reach it alone, D is skipped.

**T1, YOLOE's prompt embedding: bars 2 and 3 FAILED.**
1. Met: the embedding is bit-identical to `get_text_pe`'s (max difference
   0.0, two targets; YOLOE's model is on the CPU when its prompt is set, and
   the child runs the same operations on the CPU).
2. **Failed:** perception's heap fell 151 MB (bar 350), and that includes
   T3's 52 MB copy. **A's attribution was wrong.** In a fresh process,
   building MobileCLIP does leave 577-674 MB of heap, but in the pipeline
   YOLOE's first `predict` alone adds 416 MB of heap (with cuDNN off, 272 MB:
   cuDNN's share is about 140 MB), and the allocator reused MobileCLIP's
   freed heap for it. Without MobileCLIP the predict's 416 MB is still paid.
3. **Failed (kept by the user before C1, 2026-10-14):** a target never seen
   before reaches its first frame in 11-36 s (old 5-17 s), because each
   text needs a child that imports torch (2.6 s) and clip (2.0 s). A target
   seen before: 3.8-5.0 s, faster than the old code. The one-time cut of the
   text tower: 9.1 s; a miss 6.7 s (quiet board).

**T2, CLIP's text tower: bar 2 met.**
1. Met: CPU features differ from the old GPU ones by at most 3.7e-7 (bar
   1e-5; 7, 80 and 1 texts).
2. **Met:** perception's GPU fell 252 MB (bar 200).
3. Failed, as T1's bar 3: the CLIP texts of a new target are new children.

**T3, the small ones: the together bar FAILED (66 MB, bar 80).**
* YOLOE's CPU copy: 52 MB freed, measured alone on the board (`meta` after

* torch's cache emptied once after the first frame: reserved minus

* `foxglove_bridge` opt-in (`PICAR_FOXGLOVE=1`): 14 MB; kept.
