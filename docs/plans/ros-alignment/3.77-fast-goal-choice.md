# 3.77 Fast goal choice on the Jetson

*`PLAN-ros-alignment.md` section 3.77; index: [README.md](README.md).*

**Status: built and measured 2026-10-13; criteria 1-3 met, 4 at `ready`.**
Planned the same day (the user: "Yes" to a section for the finding of 3.65
amendment 3, check C). Criteria written before building.

**Why.** 3.65 amendment 3 timed explore's goal choice on the Jetson at 15 W,
on six maps from live `home_first_floor` runs at SLAM resolution (0.05 m,
about 316 x 285 cells): **the rule's own choice takes 1,296 ms p50 and
1,435 ms p90** (laptop 509 / 563 ms). The robot is stopped while it runs and
it is inside B3.3's 30 s tick deadline, so it is not a safety problem; but a
20-goal search stands still for about 30 s choosing, and the map only grows
as the house gets bigger. The time is pure-Python grid work in
`brain/frontier.py`.

**Where the time goes** (laptop, map 1, five poses; `find_frontiers` found
89 frontiers on this end-of-run map):

| Part | ms | Runs per choice today |
|---|---|---|
| `_clearance` (distance to the nearest wall, every cell) | 48 | once inside each `reachable` |
| `reachable` (BFS from the robot, ~21,000 cells) including `_clearance` | 113 | up to 3: `find_frontiers`, `find_view_gaps`, the boxed-in check in `_next_frontier` |
| `frontier_cells` | 23 | 1 |
| `find_frontiers`' goal search (a (4r+1)^2 window around every frontier cell) | ~210 | 1 |
| `find_view_gaps` (its own `reachable`, a full sort of every reachable cell per patch, camera rays) | 170 | 1, when no frontier is free |

**The approach: same answers, less work.** This section does not change
what explore chooses; it changes how long it takes.

1. **Compute `reachable` once per choice** and pass it to `find_frontiers`,
   `find_view_gaps` and the boxed-in check (an optional argument; callers
   that pass nothing behave as today).
2. **numpy (already in `requirements.txt`; no scipy, which is only in the
   perception extras)** for the whole-grid passes: `_clearance` as a capped
   Chebyshev distance (repeated 3x3 minimum), `frontier_cells`, the unseen
   mask.
3. **`reachable`'s BFS level by level in numpy, keeping the BFS tree
   exactly.** Today's path lengths are BFS-tree lengths, not shortest
   paths: a cell takes its first discoverer's length plus 1 or sqrt 2. A
   level's candidates generated in queue order (parent, then today's
   `dx`/`dy` loop order) and de-duplicated by first occurrence give the
   same parent and the same next queue order, so the same lengths.
4. **The goal search and the view-gap ranking as array operations** with
   today's tie-breaks reproduced (first in today's iteration order wins;
   a stable sort over cells in BFS order for the ranking).

If exact answers cannot be had at the speed bar, a coarser search grid is
the fallback. It changes the answers, so it would need its own amendment,
written before measuring, with behaviour criteria (sweeps and live runs).

**Benchmark maps.** The six end-of-run maps of 3.65's live runs, copied
from `/tmp` into `evaluations/goal-choice-377/maps/` (gzipped, 24 KB) so
the benchmark can be repeated. End-of-run maps have many unreachable
frontiers outside the walls, which is the slow case for the goal search.

## Amendment 1 (2026-10-13, written before any live run): what `choice_ms` measures

Criterion 3 said "`choice_ms`, the wall time of the whole `_next_frontier`
call". As built and reviewed (the bug pass on 3.77 B), precisely:

* **Every choice is timed**, including those that send nothing (no map
  yet, a refused goal, cooling, boxed, exhausted) -- the slowest choices
  scan everything and send nothing, so timing only sent goals would bias
  the numbers low. The mission status reports `explore.choice_ms` = count,
  p50, p90 and max over the mission; criterion 3's p50 / p90 come from
  there, from the last status of each run.
* **The span** runs from the start of `_next_frontier` to its decision:
  it includes the brain's HTTP fetches of the pose and the map (so it is
  not comparable to criterion 2's map-work-only bench) and excludes what
  follows the decision -- the navigator call that sends a goal, or the
  escape move a boxed-in choice starts. A `goal_sent` event's `choice_ms`
  is the same number.
* Criterion 3's bars (3/3 found, 0 contacts, median seconds <= 747) are
  unchanged; `choice_ms` stays reported, not judged.

**`choice_ms` live (laptop, amendment 1's span, every choice):** p50
58.3/58.5/57.8 ms, p90 62.1/65.4/69.8 ms, max 95/95/109 ms over 52-57
choices a run. The map work alone is ~25 ms on the laptop (criterion 2),
so most of a live choice is fetching the pose and the 0.05 m map over HTTP.
Not measured on the Jetson live (no Rover yet); expect the map work there
at about criterion 2's 90 ms plus the fetch.

**Reported, not judged: more goals per run.** Goals sent 28/28/31 (failed
3/1/2), travel 58.9/64.6/68.8 m; 3.65's three rule runs on the same house
sent 21/21/22. The choices are the same for the same map and pose
(criterion 1), so the difference must come from the maps and poses the
choices were made on. One untested explanation: a choice that takes 60 ms
instead of ~500 ms is made sooner after a goal ends, on a map the lidar has
had less time to fill. Three runs a side is also a small sample of a noisy
mission. Not investigated here. Time to find fell (median
642 vs 679 s) and nothing touched anything. Worth watching on the Rover;
not a reason to slow the choice down.

**Development history (for the record):** first numpy pass 72 ms laptop /
152 ms Jetson p90. Then: grid array built once (fromiter, 2.5 vs 5.2 ms),
camera rays batched with a padded grid, ties resolved only when they can
change an answer, frontier goal boxes batched by size with slices, an
integral image for clearance. Tried and dropped on Jetson data: a
sort-free BFS (38 ms vs `np.unique`'s 30) and a pure-Python queue (49 ms).
