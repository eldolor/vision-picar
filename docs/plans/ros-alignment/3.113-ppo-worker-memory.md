# 3.113 PPO's worker processes stop growing

*`PLAN-ros-alignment.md` section 3.113; index: [README.md](README.md).*

**Why.** 3.111's check 2c filled this desktop's 15 GB at PPO iteration 96
(2026-10-27 07:31) and was stopped; resumed with 6 workers, each worker grew
510 -> 1,430 MB in 43 minutes (`evaluations/goal-learn-3111/run/mem.log`).
The user, 2026-10-27: "Yeah, fix the PPO memory leak."

**Diagnosis (measured before these criteria were written, so recorded
here, not tested):**

* One process running `mission()` in a loop does not grow: 50 missions
  under W32's sampled spec, +10 MB, flat after 30; the rule's 40, flat
  (one +200 MB step when the `train` split's file loads, once).
* Two workers on PPO's own job stream (the large house set, random modes,
  new weights each round, 10 missions a worker a round) grow 300 -> 362 MB
  in 14 rounds. The same with `gc.collect()` after every mission: flat at
  302 MB (`malloc_trim` changes nothing after it). So it is garbage in
  reference cycles that Python 3.14's collector reaches too late, not a
  reference anyone keeps.
* The learned specs set `agent._learned_goal = types.MethodType(...)`, a
  bound method on the agent that holds the agent. Deleting it at the
  mission's end: 309 -> 325 MB in 14 rounds, flat from round 7. But with
  the collector off, even a rule mission's house survives it: the runner,
  agent, safety controller and navigator hold bound methods and closures
  of each other (`brain/`, `control/`; by design, and out of scope here).
  So no one deletion frees a mission; a collection does.
* A full `gc.collect()` in a worker costs ~230 ms against missions of
  0.2-8 s: nearly all of it re-scans the two house files' ~1.06M objects,
  which are never garbage. `gc.freeze()` after it moves the survivors out
  of later scans: the next collections took 0 ms.

**The fix.** `evaluations/goal-learn-396/train.py` `_job` (the pool's job
for every stage of 3.96's trainer, and so for 3.101, 3.103's pool and
3.111's PPO, which all run `T.stage_ppo`) collects after the mission and
freezes what survives. A frozen object is still freed when its count drops
to zero; only a later reference cycle among frozen objects would stay, and
between missions the survivors are the house files and module state.
Harnesses with their own `_job` (3.103's `pool_run.py` test, 3.111's
checks) are short runs and keep theirs.

**Criteria (written before the verifying run; CLAUDE.md section 7):**

1. **Bounded:** two workers on PPO's job stream for 40 rounds (400
   missions a worker), through the committed `_job`: each worker's memory at
   round 40 is within **20 MB** of its round 10 (before the fix the
   14-round run gained about 4.5 MB a round, so ~135 MB over 30), and the
   40 rounds take no more than **5%** longer than the same jobs without
   the fix.
2. **Freed at once:** a test: with the automatic collector disabled, a
   pool job under a learned spec leaves no reference to its house (a weak
   reference to the built world is dead on return); red without the fix.
3. **Same answers:** the collection runs after the row is complete; the
   fast tier passes, and 3.96's pinned test rows still score as recorded
   (`tests/test_goal_policy_rooms.py`).

**Out of scope:** PPO's budget, any chooser's numbers, `brain/`.
