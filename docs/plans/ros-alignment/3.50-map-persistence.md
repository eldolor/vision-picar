# 3.50 Saving and reloading the map: options for the user

*`PLAN-ros-alignment.md` section 3.50; index: [README.md](README.md).*

**A decision document. No code.** Written 2026-10-09 because idea 4
("remember where things were seen, across missions") cannot be built
until the map outlives a session. The user chose "decide map save/reload
first". Idea 4 then builds on this decision plus 3.46's phase C.

Each claim below is marked **[code]** (read in this repo at `origin/dev`
`54b6c4e`), **[upstream]** (slam_toolbox's Humble README or the pinned
source), or **[inference]** (my reasoning, not yet measured).

## The question

When the robot restarts, should it come back on the **same** map, and if
so, how is that map kept honest as the house changes?

## Why idea 4 needs it

* **Every restart is a new map today.** `map_id` is `slam-<session>`
  (`world/ros_world.py:121`), and the session is a random id the bridge
  makes when the container starts (`picar_bridge/bridge.py:123`) **[code]**.
  Nothing is saved: `slam.yaml` runs `mode: mapping` with no
  `map_file_name`, and no serialise or `map_saver` call exists anywhere
  in the repo **[code]**.
* **3.46's inventory is keyed on `map_id` and refuses to mix maps**
  (`brain/inventory.py:283-287`) **[code]**. So, correctly, nothing it
  records survives a restart. A sighting's position means nothing outside
  the map frame it was taken in.
* **3.46's phase E** ("persist with the saved map, `map_id` keyed, beside
  slam_toolbox's pose graph") is exactly idea 4, and it names this as its
  dependency **[code]**.
* In the in-process sim world, `map_id` is a fixed `sim-grid`, so the
  dependency never shows up there. It shows up only under `WORLD_MODE=ros`
  and on the car **[code]**.

## What is already decided (open question 6, 2026-10-01)

* Save slam_toolbox's serialised pose graph and nav2 `map_saver` files to
  a disk that survives restarts (a Docker volume in the sim, the NVMe on
  the car).
* Back them up to a private, encrypted, versioned S3 prefix
  `maps/<robot>/<map_id>/`. This is a floor plan of a home, so the design
  is driven by privacy, not cost.
* **Reload the pose graph and keep mapping on top of it**, so a moved
  sofa fades as it is re-seen, with a fresh map as the fallback. The user
  said "let's go with your recommendation".
* Lifelong mode is ruled out unless pose-graph growth becomes the
  measured problem.

Still open there: where the robot starts on a reloaded map, the
fallback's trigger, and the N/M thresholds. This document closes those,
and asks whether the 2026-10-01 choice still holds now that 3.38-3.40
have measured the furnished house.

## Facts about the tools

* **The pin is slam_toolbox 2.6.10** (`SLAM_TOOLBOX_SHA=1729c0f`,
  `service/slam/Dockerfile:48`) **[code]**. It is built from source for
  `restamp_tf` **[code]**.
* **Serialise and deserialise services exist in the pin**
  **[upstream]**. `DeserializePoseGraph.srv` takes a filename, an
  `initial_pose` and one of four `match_type` values: `UNSET`,
  `START_AT_FIRST_NODE` (the "dock"), `START_AT_GIVEN_POSE`, and
  `LOCALIZE_AT_POSE`. Parameters `map_file_name`, `map_start_pose` and
  `map_start_at_dock` load a graph at start-up.
* **Correction to question 6's text.** It says deserialise offers "a
  whole-map localise". The service definition does not: every mode
  starts from the first node or from a given pose **[upstream]**. So
  **[inference]** the robot must start at a known place or a known pose.
  There is no global relocalisation from nothing.
* **Localisation mode** loads a graph and keeps "a rolling buffer of
  recent scans ... after expiring from the buffer scans are removed and
  the underlying map is not affected" **[upstream]**.
* **Lifelong mode** is described upstream as "**highly** experimental".
  Upstream advises continuing to map until the map is complete, then
  switching to localisation mode "until node decay is implemented"
  **[upstream]**.
* **The serialised format changed in 2021** for 360-degree lidars
  **[upstream]**. Our pin postdates that change. A future slam_toolbox
  bump (question 12, leaving Humble) could orphan saved maps
  **[inference]**.
* **The executables in the image are not verified.** Docker could not be
  run from this session's isolated worktree. **[inference]** The pinned
  build should include `localization_slam_toolbox_node` and
  `lifelong_slam_toolbox_node` alongside the `async_slam_toolbox_node`
  that `picar.launch.py:81` runs. A first step must list them.
* **nav2 takes its static layer from slam_toolbox's `/map`.** No
  `map_server` runs **[code]**. So whatever slam_toolbox publishes after
  a reload is what nav2 plans on.
* **The bridge is at its route cap**: 13 of `MAX_BRIDGE_ROUTES = 13`
  (`tests/test_wall_linters.py:71`) **[code]**. A "save the map" route
  raises the cap. **[inference]** That can be avoided: the bridge already
  polls the brain's `/mission/status` (`bridge.py:186`), so it could
  serialise when a mission ends.
* **The ground-truth error readout depends on the session.**
  `RosWorld._ensure_session()` anchors SLAM's frame to the truth at the
  session's start (`start_truth`) **[code]**. After a reload the map
  frame starts where the first session started, not this one. **[inference]**
  So `start_truth` must be saved with the map, or `/world/error` and
  every criterion measured with it read wrong.

## What 3.38-3.40 add to the risk

* In the furnished house, an 8 m loop-search window closed loops to the
  wrong place in 3 of 3 runs, 1.6-2.5 m off, and never recovered.
* Narrowing the window to 2 m ended that: 0 of 9 runs jumped (3.38).
* Lowering the smear from 0.10 to 0.03 m fixed a 2.5-6 degree bend (3.40).

These are the numbers for ONE session. **[inference]** With the map
reloaded and mapping continued, a wrong closure would be saved and
reloaded every session after, rather than lost at the next restart. The
2 m window bounds how far one closure can move things, but continued
mapping turns an occasional transient error into a permanent one. Every
option that keeps mapping on a saved graph needs a check on this.

## The options

### A. A fresh map every session (today)

* **Gives:** nothing new. Zero risk, zero work. Each mission explores
  from scratch.
* **Costs:** idea 4 cannot exist beyond one mission. The inventory stays
  per-mission. Every mission re-explores the house.
* **Inventory / nav2:** unchanged.

### B. Reload and keep mapping (the 2026-10-01 decision)

* **Gives:** one frame across sessions, so `map_id` and inventory
  positions persist. A moved sofa fades from `/map` as it is re-seen, and
  new rooms get added.
* **Costs:**
  * Saving: a volume, plus a bridge save trigger (on mission end, or one
    new route).
  * Saving `start_truth` and a stable `map_id` with the map.
  * The S3 backup.
* **Risks:**
  * **[inference]** A wrong loop closure becomes permanent (above).
  * **[inference]** The graph grows every session, so Ceres time and
    memory on the Jetson rise. This is what lifelong mode exists to fix.
  * Starting away from the dock or the given pose matches badly.
* **Inventory:** positions persist. A landmark that moved is a 3.46 belief
  question (looks from new viewpoints, decay when not re-seen).
* **nav2:** the static layer heals as the robot re-sees the spot.

### C. Save once, then localise against a frozen map

* **Gives:** one frame, bounded compute (a rolling buffer), and no
  growth. A bad closure cannot enter the saved map after the first save.
* **Costs:** as B, plus a deliberate "re-map" action when the house
  changes.
* **Risks:**
  * **Rejected 2026-10-01 for this reason:** a moved sofa stays a phantom
    obstacle in nav2's static layer, because the obstacle layer cannot
    clear it. A phantom across a doorway makes a room look unreachable.
  * A new room is never added.
* **Inventory:** positions persist, and are steadiest of all options.
* **nav2:** plans on the frozen map plus live obstacles. Phantoms remain.

### D. Localise by default; re-map on a trigger (B and C combined, upstream's advice)

* **Gives:**
  * C's stability most of the time.
  * B's healing when it is needed. Continue-mapping on the same graph
    keeps the same frame, so `map_id` and inventory positions survive.
  * Then save a new version, and keep the previous one as a rollback.
* **Costs:** as B and C, plus a trigger. **[inference]** Three candidates:
  * a share of scans contradicting `/map` beyond a bar;
  * nav2 calling a known-reachable area unreachable;
  * the user asking for a re-map.
* **Risks:**
  * The trigger can be wrong.
  * Re-map sessions carry B's closure risk, but only in those sessions,
    and with a version to roll back to.
* **Inventory / nav2:** as C between re-maps, as B during one.

### E. Lifelong mode

**Not recommended.** It is "highly experimental" upstream, and our pin's
behaviour with it is unmeasured. Kept as the fallback if B's or D's
growth is measured as the problem (the 2026-10-01 rule).

## Recommendation

**D, starting from the dock (`START_AT_FIRST_NODE`), with versioned
saves and a fall-back to a fresh map.**

* B's healing is real. But its weak point is the furnished house's
  measured weak point: a loop closing to the wrong place. B writes that
  error into the saved map. D confines it to re-map sessions, each with a
  rollback.
* **Start from the dock.** Since no mode relocalises from nothing, the
  simplest honest start is a fixed spot: the robot begins every session
  where the first mapping session began. On the car that is a marked
  spot or a dock.
* **Use the last saved pose only as a hint**, never as the start. A
  robot carried while off would start from a wrong pose silently.
* **Fall back** to a fresh map, with a new `map_id`, whenever the reload
  matches badly. The inventory then ignores the old map's landmarks
  (3.46 already refuses mixed `map_id`s).

If the user prefers to keep the 2026-10-01 choice (B), the same criteria
apply. Criterion 5 is then the one to watch.

## Criteria (written now, before any build or measurement)

All in the sim under `WORLD_MODE=ros`, on this section's own ports and ROS
domain. Truth comes from `/world/truth`, read by the measurement only.
Unless a criterion says otherwise, each runs on `scaled_house` and on
`home_first_floor`. Stability and progress are paired: 1, 4 and 5 are
stability; 2, 3 and 7 are progress.

1. **The frame persists.** Three sessions, the container restarted
   between them. Each session reloads from the dock.
   * `map_id` is identical in all three.
   * At rest, within 5 s of the first scans, the pose is within **10 cm
     and 3 degrees** of the truth.
2. **A reload costs nothing when nothing changed.** On 3.14's lap after
   a no-change reload, the final error is within **2 cm** of a fresh
   map's on the same lap.
3. **A moved object heals** (B, or D's re-map). Move one object across a
   doorway between sessions (`move_object`).
   * On session 2 the doorway reads free on `/map` within **3 passes**
     (N = 3).
   * A nav2 goal through it succeeds in **3 of 3** tries.
   * Under D this is measured in a re-map session, triggered as D
     specifies.
4. **Localisation survives clutter.** With **3 objects moved** (M = 3),
   the error stays within criterion 1's bars at rest.
5. **No permanent wrong closure.** Over **5 consecutive sessions** in
   `home_first_floor`:
   * **0** jumps over 0.5 m (3.38's metric);
   * the session-5 map's walls still **100%** true (3.40's metric).
6. **Growth is bounded.** After **10 sessions**:
   * p90 scan-processing time and container memory at most **1.5x**
     session 1's;
   * the saved graph at most **50 MB**;
   * reload time on the Jetson at most **10 s**.
7. **Sightings carry over.** A 3.46 landmark recorded in session 1 lies
   within **15 cm** of the same object's truth-mapped position when read
   back in session 2. After a fall-back to a fresh map, **0** old
   landmarks are used.
8. **A bad start is caught.**
   * The robot is started at least 1 m and 30 degrees away from the dock.
     The reload is detected as a bad match within **10 s** and falls back
     to a fresh map in **5 of 5** trials.
   * It never runs a mission on the mismatched frame.
9. **Safety is untouched.** No change to `robot/safety.py` or the
   collars. 3.18's ground-truth sweep is unchanged.

The thresholds above are this document's proposal and are the user's to
amend **before** the first run. A failed criterion is recorded as failed.

## The decision the user needs to make

1. **D (recommended) or B (as decided 2026-10-01)?** C alone is not
   offered: its phantom-obstacle problem stands.
2. **The start rule: a fixed dock spot (recommended), or the last saved
   pose?** The dock means the robot must be put back on the same spot to
   start. The last saved pose means it must not be moved while off.
3. **Approve the criteria' numbers** (or amend them) before any build.

Smaller choices, defaulted unless the user says otherwise:

* Saving is triggered by the bridge at mission end, with no new route
  (the cap stays 13).
* Three versions are kept locally, matching the S3 lifecycle already
  decided.
* `start_truth` and `map_id` are saved in `meta.json`.

## Decided by the user, 2026-10-09

* **Option D**: localise against the saved map by default; re-map only on a
  trigger, with versioned saves that can be rolled back. This replaces the
  2026-10-01 choice of B (reload and keep mapping).
* **Start rule: a fixed dock spot** (where the first mapping session began);
  the last saved pose is a hint only, and a failed reload falls back to a
  fresh map with a new `map_id`.
* **The nine criteria above are approved as written**, before any build or
  measurement. Building and measuring D is the next section's work; idea 4
  (sightings across missions) builds on it and on 3.46's phase C.
