# 3.95 The tiered trees on py_trees

*`PLAN-ros-alignment.md` section 3.95; index: [README.md](README.md).*

**Why.** The user, 2026-10-23: "Switch over to py_trees." 3.94 built the
tiered policy's three trees on a small module of our own (`brain/tree.py`)
to avoid a dependency on the Jetson. It used py_trees' semantics so that
moving later would be mechanical. What py_trees brings:
* nodes that span frames (RUNNING with proper stop and terminate);
* a library of decorators (timeouts, retries, one-shot, inverters);
* a blackboard, and drawing the tree as a diagram;
* since 2.5, loading trees from BehaviorTree.CPP's XML format, which is
  the format nav2's trees and the BTGenBot dataset are written in.

This is the base the richer trees (the approach, close-in and recovery)
will be built on. **No behaviour changes here.**

**What changes.** `brain/tree.py` keeps its names (`Sequence`, `Fallback`,
`Condition`, `Action`, `Decorator`, `describe`, `find`, `walk`), but
each becomes a py_trees class, ticked by py_trees:
* `Sequence` and `Fallback` become `py_trees.composites.Sequence` and
  `Selector`, both `memory=False`, so every tick starts from the first
  child, as today.
* `Condition` and `Action` become `py_trees.behaviour.Behaviour`.
* `Decorator` becomes `py_trees.decorators.Decorator`. py_trees ticks the
  child itself and then calls the decorator's `update()`, so the spin
  guard is rewritten from "tick the child, then decide" into "decide
  after the child". The order and effect are the same.
* The policy's blackboards (`_FrameDecision` and the rest) stay the
  objects the nodes read and write. They are handed to the tree for each
  tick. Moving to py_trees' own blackboard is not part of this section.
* Pinned: `py_trees==2.6.0` (BSD-3-Clause, pure Python, needs only
  `pydot`; released 2026-09-10).

**Criteria (written before building; CLAUDE.md section 7):**

1. **py_trees does the ticking.** Every node in the three trees is an
   instance of a py_trees class: `composites.Sequence`,
   `composites.Selector`, `behaviour.Behaviour` or `decorators.Decorator`.
   No composite logic of our own remains in `brain/tree.py`. A test
   checks this over every node of the three trees.
2. **Exactly the old decisions.**
   * **2a.** The 3.94 equivalence tests (`tests/test_tier_tree.py`
     against the frozen `tests/tiered_reference.py`) pass unchanged, with
     0 differences. The only tests that may be edited are those of
     `brain/tree.py`'s own API (the decorator's signature); each edit is
     listed in the results.
   * **2b.** 3.94's mission sweep (`evaluations/tier-tree-394/`, the same
     harness, 5 arms on 21 houses) shows 0 differing frames and 0
     differing mission rows against `dev` before this section.
3. **Errors still surface.** An exception raised in any node reaches the
   policy's caller unchanged. A test plants one in each tree. The
   policy's own raises are unchanged: "the rungs chose no direction" and
   "who to ask: no route answered".
4. **It stays cheap.**
   * On the laptop, each tree's p90 is under 1 ms a frame, 3.94's bar.
   * On the Jetson at 15 W (under the board lock, in a bench directory
     with its own venv, the service untouched), the three trees' p90
     together is under 5 ms a frame. That is under a tenth of
     perception's 61 ms median.
5. **The full suite passes**, with py_trees in `requirements.txt`.
6. **Live.** One tiered mission through the live local stack
   (`home_first_floor`, the brain's HTTP API, 3.94's `live.py` with its
   free stand-ins) ends `found` with 0 contacts.

**Not in this section:**
* loading borrowed XML trees;
* the approach and close-in trees;
* py_trees' blackboard;
* installing py_trees into the Jetson's running brain. That waits for the
  next update of the board's stack, and is flagged at merge.

## Results

**3.95.A and B, 2026-10-23.** Every criterion met.
* **Criterion 1: met.** `brain/tree.py`'s five node kinds subclass
  py_trees 2.6.0's `composites.Sequence` and `composites.Selector` (both
  `memory=False`), `behaviour.Behaviour` and `decorators.Decorator`.
  py_trees ticks them. A test walks all three trees (more than 40 nodes)
  and checks each node's class and that no composite has memory.
* **Criterion 2a: met.** The 3.94 equivalence tests pass unchanged: 0
  differences against `tests/tiered_reference.py` on 10,000, 10,000 and
  2,500 random states. Tests of the tree's own API that were edited, as
  allowed:
  * `test_a_decorator_wraps_its_child...` now takes `after(bb,
    child_status)`.
  * `test_tiered.py`'s rung-order test reads `children` (a py_trees
    list), not `children()`.
* **Criterion 2b: met.** `dev` before 3.95 (`8741dbbf`) against the
  branch, 3.94's harness, 21 houses an arm:

  | Arm | Frames | Differing | Mission rows differing |
  |---|---|---|---|

  | pace 1 | 6,403 | 0 | 0 |

  That makes 41,585 frames, the same counts and outcomes as 3.94's run.
  The traces are in `evaluations/tree-395/traces.tar.gz`.
* **Criterion 3: met.** An exception planted in the first action of each
  tree reaches the policy's caller, one test per tree. The policy's own
  two raises are unchanged and still tested.
* **Criterion 4: met.** `evaluations/tree-395/timing.py`, 20,000 frames
  in the policy's own loop. The what tree is ticked inside the who tree,
  so a frame's total is when + who.

  | | what p90 | when p90 | who p90 | all trees, a frame, p90 (max) |

  The board's test file also passes there (47 tests), in its own bench
  venv. The service was not touched.
* **Criterion 5: met.** The full suite passes (`ready`), with
  `py_trees==2.6.0` in `requirements.txt`.
* **Criterion 6: met.** Live in `home_first_floor` through the brain's
  HTTP API (3.94's `live.py`, free stand-ins): `found` at 651 s, 0
  contacts, the one arrival check at 0.52 m (`live.jsonl`).
* **Reviews.** `/code-review` and the Thermos pass found no behaviour
  difference. Done on their notes:
  * `walk()` and `find()` are parent-first again (py_trees' `iterate()`
    yields children first);
  * the trees are documented as not re-entrant (one thread ticks a tree;
    no worker job ticks one);
  * nodes drop the blackboard after each tick, so none holds a frame
    between ticks.
* **Borrowing trees (the user's question), a probe:**
  `evaluations/tree-395/nav2_probe.py` loads all 12 of the behavior
  trees nav2 ships (in our ROS image) with py_trees' XML parser, every
  tag given a stand-in class: 12 of 12 parse (4 to 25 nodes,
  `nav2_probe.txt`).
  * Loading is the easy part. A tree only behaves once every leaf (for
    example `ComputePathToPose`, `Spin` or `BackUp`) and nav2's own
    control nodes (`RecoveryNode`, `PipelineSequence`, `RoundRobin`,
    `RateController`) are written as real py_trees classes over our
    verbs.
* **For the board:** `control/brain_server.py` imports `brain.tiered` at
  start, so the Jetson's brain needs `py_trees` before it runs this code.
  `tools/jetson/README.md`'s update step already runs `pip install -r
  requirements.txt`. The board's stack has not been updated here; that is
  a deploy.
