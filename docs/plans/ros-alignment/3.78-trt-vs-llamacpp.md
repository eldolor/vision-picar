# 3.78 TensorRT Edge-LLM vs llama.cpp for the local VLM, on JetPack 7.2

*`PLAN-ros-alignment.md` section 3.78; index: [README.md](README.md).*

**Why.** The user, 2026-10-13: "Qwen perception will be on the critical
path. I want to rely more on perception at the edge vs Cloud VLM.
Therefore, perception speed is extremely important", and asked for TensorRT
against llama.cpp to be evaluated soon.

What we know about Qwen2.5-VL-3B on the Jetson today, all under llama.cpp
(`Q4_K_M` + `mmproj` Q8_0, JetPack 6.2.1, 15 W):

* 3.48: the best accuracy of any local model (precision 97.1%, 0/34
  teal-bin YES, recall 89.2%).
* 3.58: time to the decision 2.95 s p90 idle, **3.64 s p90 with the robot
  stack running** (bar 3.6 s). The model alone takes 3.37 GB, and the
  stack's `MemAvailable` minimum falls to **296 MB** (floor 1 GB).
* About 2.7 s of a call is prefill (the image and the prompt), and decode
  runs at about 13 tokens/s (3.48's smoke test).

llama.cpp is the only runtime ever measured for it. 3.41 measured TensorRT
for YOLOE and CLIP only. This section measures the other runtime on the
same model, the same frames and the same prompt.

## JetPack 7.x on this board (researched 2026-10-13, not yet measured)

* **JetPack 7.2 (Jetson Linux 39.2, current 7.2.1, 2026-08-11) supports
  the whole Orin family, the Orin Nano Super included.** It brings Ubuntu
  24.04, kernel 6.8, CUDA 13.2.1, cuDNN 9.20 and TensorRT 10.16.2. JetPack
  7.0 and 7.1 were Thor-only.
* **TensorRT Edge-LLM (NVIDIA's LLM/VLM runtime for Jetson) supports Orin
  only on JetPack 7.2**, at FP16, INT8 and INT4 (no FP8 or FP4 on Orin).
  It lists Qwen2.5-VL-3B (original and AWQ INT4) and Qwen3-VL among its
  models. **So this comparison needs JetPack 7.2.** The older TensorRT-LLM
  Jetson branch (JetPack 6) never supported Qwen2.5-VL.
* **Install traps found so far:**
  * TensorRT is not installed by default on 7.2.1:
    `apt install nvidia-tensorrt nvidia-tensorrt-dev`, and a venv made
    with `--system-site-packages`.
  * PyTorch comes from upstream (`download.pytorch.org/whl/cu132`). It is
    built for sm_80, and on Orin (sm_87) it warns but runs. NumPy is
    pinned at 1.26.4 for OpenCV.
  * There are no SD-card images; the board is flashed from a USB stick.
  * Isaac ROS is "coming soon" on 7.2. We do not use it (3.41 closed it).
  * Super mode is the flashed default on the Orin Nano devkit.
* **Edge-LLM's export step needs an x86-64 Linux host with an Ampere or
  newer NVIDIA GPU** (CUDA 12/13, RAM and VRAM several times the
  checkpoint). It cannot run on the Jetson or on the Mac. The ONNX then
  goes to the Jetson, which builds the engine on the board.
* **Prediction, written before measuring:** TensorRT should be clearly
  faster at prefill and image encoding, which is most of today's 2.95 s,
  and only a little faster at decode. Decode is bound by memory bandwidth,
  and both runtimes read about the same bytes at 4 bits. **It should not
  be smaller:** Orin cannot run an FP8 vision encoder, so the encoder runs
  at FP16 (about 1.3 GB for its ~0.67 B parameters) against llama.cpp's
  Q8_0 projector (0.84 GB). Memory may come out worse.

## What is compared

Every arm runs on the same Jetson Orin Nano Super at 15 W, with 3.58's
pinned 299 frames, `labels.json` as the reference, 3.48's prompt verbatim,
greedy decoding, the YES gate at score >= 0.5, and 3.58's stopping rule
(time to the deciding token, client-side, image encoding included).

| arm | OS | runtime | model files |
|---|---|---|---|
| **L6** (record) | JetPack 6.2.1 | llama.cpp `e60eff9`, CUDA | 3.58 run I, not re-run |
| **L7** | JetPack 7.2.1 | llama.cpp, newest release, CUDA 13.2, commit recorded | the same `Q4_K_M` + `mmproj` Q8_0 files |
| **T7** | JetPack 7.2.1 | TensorRT Edge-LLM, newest release, version recorded | Qwen2.5-VL-3B-Instruct-AWQ (INT4) LLM; visual encoder at FP16 |

L7 is what keeps the comparison honest. L7 against L6 shows what the
operating system and CUDA change alone did; T7 against L7 shows what the
runtime did. The two are never mixed in one number.

**JetPack 6.2.1 stays bootable.** 7.2 goes on a second drive (the devkit
has a second M.2 Key M slot, or a USB SSD), and the current NVMe, which
runs `picar-stack` and `picar-ngrok`, is not touched. Moving the robot
stack itself to 7.2 is a separate decision after this section.

## Criteria (written before measuring; CLAUDE.md section 7)

Idle board, desktop off, the twin's services stopped
(`tools/jetson/README.md` sections 4-5).

1. **Accuracy holds under T7** (3.48 criteria 1-3, unchanged):
   precision >= 95%, 0 YES on the 34 teal-bin frames, recall >= 50%. This
   is judged on the task, not on per-frame parity: 3.41 showed a parity bar
   can reject a change that alters no decision. Decisions flipped against
   3.48's record and the largest score difference are reported.
2. **Speed: T7's time to the decision, p90, <= 0.70 x L7's** on the same
   board, the same frames and the same prompt (3.41's 30% adoption bar).
3. **Memory: T7's `MemAvailable` drop <= L7's + 256 MB.** It must not
   trade the blocker (memory, 3.58) for speed.
4. **No failed calls** in either arm.

**Reported, never criteria:** the p50 and max; prefill and decode broken
out (image encoding plus prompt in ms, decode in tokens/s); cold start (from
process start to the first answer, which is the cost of loading the model
only at arrival, 3.58's first variant); the engine build time (once per
board and TensorRT version); L7 against L6; and the maximum temperature.

**T7 is adopted as the local VLM runtime only if 1-4 all hold.** A pass
does not by itself put Qwen on the critical path. That still needs it to
fit beside the stack (3.58's criterion 6) under load. Step 3.78.F measures
that with the robot stack on 7.2.
