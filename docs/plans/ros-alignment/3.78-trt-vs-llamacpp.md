# 3.78 TensorRT Edge-LLM vs llama.cpp for the local VLM, on the board as it is (JetPack 6.2.1)

*`PLAN-ros-alignment.md` section 3.78; index: [README.md](README.md).*

**Why.** The user, 2026-10-13: "Qwen perception will be on the critical
path. I want to rely more on perception at the edge vs Cloud VLM.
Therefore, perception speed is extremely important", and asked for TensorRT
against llama.cpp to be evaluated soon.

What we know about Qwen2.5-VL-3B on the Jetson today, all under llama.cpp
(`Q4_K_M` + `mmproj` Q8_0, JetPack 6.2.1, 15 W):

* 3.48: the best accuracy of any local model (precision 97.1%, 0/34
  teal-bin YES, recall 89.2%).
* 3.58: time to the decision 2.95 s p90 idle, **3.64 s p90 with the robot
  stack running** (bar 3.6 s). The model alone takes 3.37 GB, and the
  stack's `MemAvailable` minimum falls to **296 MB** (floor 1 GB).
* About 2.7 s of a call is prefill (the image and the prompt), and decode
  runs at about 13 tokens/s (3.48's smoke test).

llama.cpp is the only runtime ever measured for it. 3.41 measured TensorRT
for YOLOE and CLIP only. This section measures the other runtime on the
same model, the same frames and the same prompt.


**The user, 2026-10-13, on scope:** "Could we first compare the two on the
existing setup? We can eventually upgrade to the latest later." So both
runtimes are measured on the board exactly as it runs today, and JetPack
7.2 is a later section.

## The board and the runtimes (checked 2026-10-13)

* **The board:** JetPack 6.2.1 (L4T R36.4.4), CUDA 12.6, TensorRT 10.3.0.30
  (`libnvinfer` already installed), booting from the 500 GB NVMe (380 GB
  free). The 119 GB microSD holds the older fallback install. `lsblk`
  shows no other drive. Nothing is reflashed for this section.
* **TensorRT Edge-LLM v0.6.0** (2026-03-19) is NVIDIA's runtime for LLMs and
  VLMs on Jetson. Its own docs list "NVIDIA Jetson Orin, JetPack 6.2.x" as
  **compatible, experimental** (official Orin support moved to JetPack 7.2
  in later releases). Qwen2.5-VL-3B-Instruct is the model in its VLM
  example. INT4 AWQ runs on every platform; FP8 needs SM89+, so it is out
  on Orin (SM87).
  * Known build issue on JetPack 6.2: `ENABLE_CUTE_DSL=ALL` fails on CUDA
    12.6 (issue #183). Those kernels are for Blackwell/Thor only, so build
    with them off.
  * If v0.6.0 cannot build or run Qwen2.5-VL on this board, that is
    recorded as this section's result, and the comparison moves to the
    JetPack 7.2 section.
* **Export needs an x86-64 Linux host with an Ampere-or-newer NVIDIA GPU**
  (Ubuntu 22.04/24.04, CUDA 12/13, Python 3.10+). It cannot run on the
  Jetson or the Mac. The ONNX files then go to the Jetson, which builds
  the engines itself (`llm_build`, `visual_build`). Plan: a short-lived EC2
  GPU instance, with the cost estimate shown to the user before launch.
* **Prediction, written before measuring:** TensorRT should be clearly
  faster at encoding the image and the prompt (prefill, most of today's
  2.95 s), and only a little faster at decode. Decode is bound by memory
  bandwidth, and both runtimes read about the same bytes at 4 bits. It
  should not be smaller: Edge-LLM's visual encoder runs at FP16 (about
  1.3 GB for ~0.67 B parameters), where llama.cpp's projector is Q8_0
  (0.84 GB). Memory may come out worse.

* 3.58's pinned 299 frames, with `labels.json` as the reference;

* 3.58's stopping rule: time to the deciding token, client-side, image

| arm | runtime | model |

* **Image tokens are matched:** T's visual engine is built so a 640 x 480

## Criteria (written before measuring; CLAUDE.md section 7)

Let **B** be the faster of L and Ln by p90 time to the decision.

1. **Accuracy holds under T** (3.48 criteria 1-3, unchanged):
   precision >= 95%, 0 YES on the 34 teal-bin frames, recall >= 50%.
   Judged on the task, not on per-frame parity: 3.41 showed a parity bar
   can reject a change that alters no decision. Decisions flipped against
   3.48's record and the largest score difference are reported.
2. **Speed: T's time to the decision, p90, <= 0.70 x B's** (3.41's 30%
   adoption bar).
3. **Memory: T's `MemAvailable` drop <= B's + 256 MB.** It must not trade
   the blocker (memory, 3.58) for speed.
4. **No failed calls** in any arm.

**Reported, never criteria:** the p50 and max; prefill and decode broken
out (image plus prompt in ms, decode in tokens/s); cold start from process
start to the first answer (the cost of loading the model only at arrival,
3.58's first variant); the engine build time; L against 3.58's run I; and
the maximum temperature.

**T is adopted as the local VLM runtime only if 1-4 all hold.** A pass
does not by itself put Qwen on the critical path. That still needs it to
fit beside the robot stack (3.58 criterion 6). 3.78.F measures that.

## Amendment 1 (2026-10-13, before any run): how arm T is driven and scored

Found while reading Edge-LLM v0.6.0's runtime. `LLMInferenceRuntime::
handleRequest()` returns only the generated token ids and text: **no
logprobs and no streaming.** That changes two things for T only.

* **The score.** L and Ln score P(`{`) / (P(`{`) + P(`]`)) from
  `top_logprobs` (3.48). T has no probabilities, so T's decision is read
  from its greedy tokens with the same rule (`p_localised` fed a one-hot
  distribution): YES if the token after the list opens is `{` (or a merged
  `[{`), NO if it is `]` (or `[]`), and whitespace defers (3.48 amendment
  2). Under greedy decoding this is the same decision whenever `{` or `]`
  is the most likely token. It can differ only where a third token wins
  and the two are compared below the top. Criteria 1-4 read decisions, so
  they are unchanged. "Largest score difference" is not reported for T.
* **Stopping at the decision.** With no stream to close, T stops by
  length. Pass 1 (untimed) generates up to 64 tokens per frame (3.58's cap) and
  records the index of the deciding token. Pass 2 (timed) runs each frame
  with `maxGenerateLength` set to that index + 1, so the deciding token is
  generated. So T, like L, generates exactly
  up to its decision. A frame whose pass 2 decision differs from pass 1 is
  counted and reported.
* **The driver** is a copy of `examples/llm/llm_inference.cpp` with three
  changes: the wall time of each `handleRequest()` (stream synchronised,
  JPEG decode and image preprocessing included) in each response; the
  output token ids; a per-request `max_generate_length`; and each frame
  decoded inside its own timed request, not all 299 while parsing the
  input (found in review: stock `llm_inference` decodes every image up
  front, which would leave the decode out of T's time and hold every frame
  in T's memory). The model is
  loaded once, and the 299 frames run back to back after 3 warm-up
  requests. That matches L's resident server.

## Amendment 3 (2026-10-13, before any arm T run): v0.9.1 streams and gives logprobs, so T is measured as L is

Found while reading v0.9.1's runtime. Unlike v0.6.0, it has:

* per-request top-K logprobs (`numLogprobs`, up to 50), computed as
  log(softmax(logits)) before sampling, with no temperature: the same
  quantity llama-server's `top_logprobs` returns;
* a `StreamChannel` that delivers each token as it is generated and can be
  cancelled mid-request (`channel->cancel()`).

**So amendment 1's two workarounds are dropped for v0.9.1.** Arm T is
measured exactly as L:

* the reply is streamed with the top-20 logprobs, scored by 3.48's
  `p_localised` unchanged;
* generation is cancelled at 3.58's deciding token (`decision_reached`);
* `ms` is client-side, from sending the request (whose parsing decodes the
  JPEG) to receiving the deciding token.

Criterion 1's flips against 3.48, and the largest score difference, are
reported for T as for L. Amendment 1 applies only if the comparison
falls back to v0.6.0.

**The driver** (`tools/jetson/edgellm_identity.cpp`, built inside
Edge-LLM's `examples/llm`): it is modelled on v0.9.1's `llm_stream.cpp`.

* It loads the runtime once and captures the decode CUDA graph.
* It then reads one request-file path per line on stdin. Parsing that file
  is what decodes the frame. For each token it writes the id and the
  top-20 (id, logprob) to stdout, and it cancels when stdin says `C`.
* `bench_identity_trt.py` holds the decision logic (the same functions
  as L's), so the stopping rule is one piece of code for both runtimes.
* Token texts come from the model's own `tokenizer.json`, decoded one id
  at a time, as llama-server's per-token `token` is.

## Measured 2026-10-13

All runs: Jetson Orin Nano Super, JetPack 6.2.1, 15 W, the pinned 299
frames, 3.48's prompt, greedy, 3.58's stopping rule. Jetson rows only
(P24). Records are in `evaluations/identity-378/`.

**Runtimes.**
* L: llama.cpp `e60eff9`.
* Ln: llama.cpp `b11588` (2026-10-13).
* T: TensorRT Edge-LLM v0.9.1, with the LLM at INT4 AWQ and the visual
  encoder at FP16.

**Getting T to run here** took four local patches. v0.9.1 lists
"JetPack 6.2+" as compatible, but it needs TensorRT 10.7+/10.8+ in two
places, and two of its prebuilt sm87 attention kernels were built by CUDA
12.8+. The patches are `tools/jetson/patch_edgellm_trt103.py` and
`build_edgellm_identity.sh`:

1. **Engine loader:** `IStreamReaderV2` (TensorRT 10.7) is replaced
   below 10.7 by reading the engine into memory.
2. **FP4 type:** `DataType::kFP4` (10.8) is guarded in the Blackwell-only
   NVFP4 plugin.
3. **Attention kernels:** two `custom_mask` head-dim-256 FMHA cubins with
   ELF ABI 8 are skipped. The 12.6 driver returned
   `CUDA_ERROR_INVALID_IMAGE` on one and segfaulted on the other. Neither
   model uses head dim 256.
4. **Plugin library:** the plugin `.so` was added to the build.

The LLM engine builds hit the OOM killer at 8 GB and needed a temporary
8 GB NVMe swapfile, removed before any measured run.

**Exports** were done on the GPU host, about $3.91 for 4 h: Qwen2.5-VL-3B
and Qwen3-VL-4B succeeded. **Qwen3.5-4B's export failed**: its tar was
empty, and the log was lost when the host terminated at its 4 h cap. It
has no T arm.

**Engine build on the board:** Qwen2.5-VL-3B LLM 179 s, visual 94 s.
Qwen3-VL-4B LLM 240 s, visual 80 s.

## Amendment 4 (2026-10-13, before measuring): two free trims, then 3.78.F under T

The user approved this on 2026-10-13 ("Yes"), after the memory profile
above.

**Trims to T, neither of which changes an answer:**

1. **The engine is memory-mapped, not copied.** The JetPack 6.2 loader
   patch reads the engine file into a heap buffer before deserialising it,
   which caused the 0.85 GB load spike. It now `mmap`s the file read-only.
   The pages are file-backed and reclaimable, and are unmapped after
   deserialisation.
2. **The LLM engine is rebuilt with `--maxKVCacheCapacity 1024`** (was
   4096). A frame needs about 455 prompt tokens plus at most 64 generated;
   `maxInputLen` stays at 1024. The cache is about 36 KB per token (36
   layers x 2 KV heads x 128 x 2 x FP16), so this saves about 0.11 GB.

Their effect is the same 19-frame memory probe, re-run, and reported
only.

**3.78.F, the loaded window under T:** 3.58's run L harness
(`tools/jetson/headroom_identity.sh`, with `RUNTIME=trt` choosing T's
client). The conditions are 3.58's:

* the split simulator body and sensors;
* the robot server's 20 Hz wheel loop on the fake ESP32;
* the brain;
* the ROS container (`ros2_control`, `slam_toolbox`, nav2, bridge) as
  `vision-picar-ros:plan-3.78`, built from this branch on the board, since
  the board's `:latest` predates 3.67's nav2 change;
* nav2 goals round the scaled house for the whole window;
* ONE YOLOE + CLIP pipeline at 4 Hz;
* desktop off, 15 W;
* T answering all 299 frames back to back, stopping at the decision.

The twin's `picar-stack` and `picar-ngrok` are stopped after the
multi-user isolate (the deviation above).

**Criteria (3.58's, with the user's waiver):**

1. Precision >= 95%.
2. Teal-bin YES: **waived by the user**, reported only.
3. Recall >= 50%.
4. Precision >= the cloud's 67.9%.
5. **Time to the decision, p90 <= 3.6 s** (3.58's bar). The idle 1.13 s
   is reported beside it.
6. **`MemAvailable` minimum >= 1024 MB** over the window, with 0 OOM
   events and 0 failed calls.
7. 0 late wheel-loop ticks.
8. Every nav2 goal succeeds, and perception p90 <= 250 ms.
9. No thermal throttling.

**Also reported:** decisions flipped against T's clean-session record,
and the load spike's minimum during the window's first 30 s.

**Local Qwen under T is recommended as a replacement for the cloud
identity call only if 1 and 3-9 all hold.** Wiring it in is a separate
decision for the user.

## Amendment 5 (2026-10-13, before measuring): shrink T (B), and revisit the floor (C)

**The user, 2026-10-13:** "B and C." They also set the goal this serves:
"replace the cloud VLM with Qwen running locally on the rover",
**tiered**: perception first, then local Qwen when perception cannot
answer, then the cloud after a set number of local failures. That design
is its own section. This amendment covers only B and C.

**B: two variants of T, from the same INT4 AWQ checkpoint (re-quantised;
the first host is gone):**

* **V, reduced vocabulary.** The output layer keeps the merged vocabulary
  from `tools/jetson/edgellm_vocab_map.py`:
  * Edge-LLM's `input_aware` selection of 16,384 tokens (cnn_dailymail);
  * a forced list (`evaluations/identity-378/forced_ids.json`, 1,663 ids):
    the 22 special tokens, 1,552 JSON-structure / digit / whitespace
    tokens, and every token of the 4,822 recorded replies;
  * padded to a multiple of 128 from a 32,768-token selection.

  The input embedding table and the transformer are unchanged. Kept
  tokens' logits are unchanged, and the probabilities are renormalised
  over the kept set. The arrival score is a ratio of kept tokens'
  probabilities, so it cannot move. Expected saving: the FP16 output
  layer shrinks from 151,936 to about 17,000 rows, about 0.55 GB.
* **VE, V plus an FP8 input-embedding table** (`--fp8-embedding`: a
  storage format, dequantised on lookup). Expected saving: about 0.31 GB
  more. Inputs are rounded, so answers can move.

**Criteria, for each variant against T's clean session
(`clean/T-Qwen2.5-VL-3B-Instruct.json`), on the idle board:**

* **V: 0 flipped decisions** of 299 (the arithmetic says identical).
  The largest score difference is reported.
* **VE:** precision >= 95% and recall >= 50% (3.48's bars; teal bin
  waived by the user). Flips are reported.
* Both: steady and peak use from the 19-frame memory probe, and p90 to
  the decision. These are reported.

The smallest variant that passes then runs 3.78.F's loaded window again,
with perception warmed before the VLM starts (the load-picture rule).
Criterion 6 is judged against the floor C sets.

**C: the floor.**

* The 1 GB was written down on 2026-10-02 (3.33 criterion 6) as a round
  number with no derivation.
* Measured since:
  * Within a loaded window, `MemAvailable` swings about 65 MB below its
    median (T: median 255, min 191; llama.cpp: median 361, min 296).
  * Under T, zram swap held 700-851 MB (llama.cpp: up to 430 MB). zram is
    compressed memory inside RAM, so pressure is higher than
    `MemAvailable` alone shows.
* Not measured yet: the transients a real mission adds that the scaled
  house does not:
  * a larger map (SLAM and the nav2 costmaps grow with the house);
  * a target change (a second perception pipeline);
  * the inventory;
  * the recording uploads.
* The floor is the user's call. Claude will propose a value from a
