# 3.106 Explore in the approach band, the target in sight but never found: bounded, not a livelock (house 1395)

*`PLAN-ros-alignment.md` section 3.106; index: [README.md](README.md).*

**Why.** 3.96's criterion 5 failed on one mission: house `train:1395`
(mode R, a box) under F-large never ended; the 5,000-tick cap stopped it.
The user picked it from the open list (2026-10-26). Traced on `dev`
(`371edb6`): explore stands 0.64 m from the box, dead ahead (0.2 deg),
inside its approach band (`_at_target`, 0.70 m), with a dining-table leg
0.44 m off. The simulator's detector reports the box (any visible part,
`sim/grid_world.py` `_detections`), but its found rule (`objects_visible`,
the renderer's one ray to the object's centre) does not: the table hides the
centre. So every tick explore sees the target, has no close-in (that is the
tiers' perception path only, 3.80.G), and falls to `_back_to_sighting`'s
"here and not seeing it" branch, which clears the sighting and queues a
FACE that answers "already facing it". Nothing counts a failure, the
retry rule never lets go, and a WAIT passes no simulated time, so the time
limit never ends it either. On the car the wall clock would end it
`out_of_budget` at 1,200 s; plain explore's frame sightings exist only in
the simulator (3.76 E's open item), so this is a sweep-and-sim bug, but it
stops a sim mission dead.

**The change.** In explore, count consecutive ticks that are in the band,
see the target this tick, have no goal live and nothing to close in with.
At `CLOSE_IN_REFUSED` (3) such ticks the sighting counts one retry failure
and the robot backs off, as close-in does at its own refusal limit. The
first of those ticks still turns to face it (a target at the frame's edge
is found once faced). Explore then moves on; the retry rule (3 failures,
30 s cooldown) bounds the returns.

**Criteria (written before building; CLAUDE.md section 7):**

1. House `train:1395`, mode R, under F-large (3.96's harness,
   `evaluations/goal-learn-396/train.py` `mission`) and under the rule ends
   under the tick cap with an outcome (`found`, `exhausted` or
   `out_of_budget`), not `capped`. Red on `dev` first for F-large. A test
   in the fast tier pins the bound itself (in sight, in the band, never
   found: a failure and a back-off within 3 ticks; a target at the frame's
   edge is still faced first).
2. No found mission lost: the rule arm on 3.96's 588 test houses (`train`
   1000-1999, modes R and U, `c.py`'s houses) finds at least as many as
   recorded there (R 570, U 582), median goals no higher (R 7, U 9).
3. The explore sweeps' pinned numbers hold (`test_procthor_sweep`,
   `test_goal_policy_sweep`, `test_frontier_fast_sweep`,
   `test_survey_sweep`, `test_inventory_mission`); a pin that moves is
   explained house by house or this fails. The fast tier passes.

## Review round 1 (2026-10-26, Sonnet, both passes)

Taken, red-first where a behaviour changed:

* (Thermos, medium) found is recorded after `_choose`, from the scene it
  already holds: the bound could back off and book a failure on the very
  tick the target was found. Now no count on a tick whose scene names the
  target.
* (both) the count carried over between places and across early-return
  ticks: it is now kept at one place (a sighting over `APPROACH_MOVED_M`
  off starts again) and any goal sent starts it again, as close-in's does.
* (`/code-review`) one helper for both give-ups (`_give_up_sighting`), and
  the policy ENGINEERING spec now says how (rule 6; the first commit
  missed it).

Recorded, not changed:

* With `SIM_MOVERS`, a mover that hides the centre for three ticks makes
  the bound give up -- but WAIT ticks pass no simulated time, so the mover
  never moves during them; before, that state looped for ever.
* A refused FACE whose backed retry also fails (`retry.fail` in the FACE
  path) and then the bound can book two failures for one visit; criterion
  2's sweep reads whether it costs a find.
* Altitude: making the simulator's detector and its found rule agree
  (`sim/grid_world.py`) would fix house 1395 at the source, but moves every
  policy's pinned sim numbers; not this section's. On the car the branch
  never runs (real frames carry no `detections`; perception always gives
  close-in a bearing).

## Review round 2 (2026-10-26, Sonnet, both passes)

Thermos: nothing above low. `/code-review`, taken: the found tick's match
is `MissionMemory.names_target()`, the found rule's own (it was copied by
hand, and a drift would bring the livelock back); the count restarts on a
goal ACCEPTED (where close-in's does), not on any send, and its place is
cleared wherever the count is; one guard instead of three; the spec's
wording; the sweep script closes its files and keys rows by split and
index. One claim did not hold: "a frame that misses the target restarts
the count, so a flickering detector loops for ever" -- traced, a missed
frame finds the sighting already let go and sends a frontier goal, so it
leaves (pinned as a guard, not red on `dev`). A missed frame now neither
counts nor restarts the count anyway (reversed in round 3: ticks in a row).

## Review round 3 (2026-10-26, Sonnet, both passes)

Both: round 2 made the count sticky. Not restarting it on uncounted ticks
(round 2's answer to a flicker claim that did not hold) let a count carry
over a queued look, a goal refused, close-in acting or a return to the same
place, and fire after one tick. Fixed red-first: the count is ticks in a
row (`_in_sight_tick`) at one place; any tick between starts it again, and
`_give_up_sighting()` clears it for both give-ups. Also: a stale partial
sweep file (`test-rule/rule-R.json`, round 1's code) had been committed in
`cc1ccfa`; removed -- criteria 2 and 3 are run once, on the final code.
House 1395 unchanged by this round (found, 26 goals).

## Review round 4 (2026-10-26, Sonnet, both passes)

Nothing above low-medium. Taken: the run is anchored where it starts (it
was re-anchored every tick, so a drifting estimate never restarted it);
`_give_up_sighting()` clears close-in's refusals too, and an accepted goal
resets the run again (as close-in's count; a goal tick is never counted,
so a guard); one `_reset_in_sight()`; the restart test also shows a full
run afterwards still fires.

**Known limits** (recorded, not fixed):

* A target the detector misses one frame in three never completes a run of
  three; the loop is still left, because a missed frame finds the sighting
  let go and explore sends a frontier goal -- if that goal is refused, or
  no frontier is left, it waits until the time or step budget.
* Deeper fix, not done: one bound on any run of WAITs with no pose change
  (this, close-in's refusals and the glimpse give-up are three special
  cases of it), or making the simulator's detector and found rule agree.
