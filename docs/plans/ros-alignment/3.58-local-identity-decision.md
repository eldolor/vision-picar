# 3.58 Qwen2.5-VL-3B at the decision: latency and memory with the robot stack running

*`PLAN-ros-alignment.md` section 3.58; index: [README.md](README.md).*

**Why.** 3.48 measured five small VLMs on the Jetson as an offline identity
check for an arrival the cloud could not confirm (3.47's
`arrived_unconfirmed`). Qwen2.5-VL-3B at 4 bits (`Q4_K_M`, llama.cpp) met
every accuracy criterion -- precision 97.1% against the cloud's 67.9%, 0 of
34 teal-bin frames, recall 89.2% -- and failed two as specified:
**latency** (5.58 s p90 for the whole 64-token reply, though it had decided
by 2.84 s p90) and **memory** (a 3.48 GB drop in `MemAvailable` on an idle
board, against a 3.25 GB bar that was itself derived from the stack-running
figure). The user approved this follow-up on 2026-10-09: stop generation at
the decision, and measure memory with the full robot stack running,
criteria fixed first.

Measurement only. Wiring it in as the fallback is a separate decision for
the user.

**The model and runtime are 3.48's, unchanged:** `Qwen2.5-VL-3B-Instruct-
Q4_K_M.gguf` with `mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf`, llama.cpp
`e60eff9` (CUDA) as built in `~/bench-348/`, `-ngl 99`, context 4096,
`--cache-ram 0` (3.48 amendment 3), one slot, greedy (`temperature 0`,
`top_k 1`), `top_logprobs` 20, 3.48's prompt verbatim, the pinned 299 frames
(the four 2026-09-07 rig walks) with today's `labels.json` as the
reference, and the gate YES = score >= 0.5.

**The stopping rule, fixed now.** The reply is streamed and the client
stops reading -- closing the connection, which ends generation -- at the
first generated token after which 3.48's scorer (`p_localised`) has
everything it reads:

* a token that starts with `{` before any list opened (a bare object: the
  decision is that token);
* a token that starts with `[` and is not exactly `[` (a merged `[{` or
  `[]`: the decision is that token);
* after a bare `[`, the first token that is not whitespace-only (the
  decision; whitespace defers, as in 3.48 amendment 2);
* otherwise 64 tokens or the end of the reply, exactly as 3.48 (a reply
  that never opens a list scores 0 and is counted).

`p_localised` reads nothing past that token -- for the bare-object and
merged cases only that step, for the bare `[` case the steps up to the
first non-whitespace one -- so on the same greedy token stream the score
over the stopped reply equals the score over the full reply. Whether the
stream IS the same on this board (CUDA, one slot, streaming rather than
not) is an empirical question, so it is a criterion (S below), not an
assumption.

**What runs on the board, and how memory is measured.** 3.33's headroom
conditions (3.33 item 6 / 3.37: the run that measured the 4253 MB
`MemAvailable` the 3.25 GB bar was derived from), at 15 W, desktop off
(`multi-user.target`, restored after):

* the split simulator body and sensor programs, the robot server with the
  20 Hz wheel loop on the fake ESP32, and the brain (`service/tunnel/
  restart.sh`, `ROBOT_DRIVE=ros WORLD_MODE=ros ROBOT_MODE=hardware
  SIM_MOTOR_BOARD=fake SIM_MAP=scaled_house`);
* the ROS container -- `ros2_control`, `slam_toolbox`, nav2 and the bridge
  -- from this branch's `service/slam`, built on the board as
  `vision-picar-ros:plan-3.58` (never `:latest`);
* nav2 goals round the scaled house after the mapping lap, for the whole
  window;
* the perception tier as a mission carries it: ONE YOLOE + CLIP pipeline,
  loaded once, real frames at 4 Hz on the GPU (3.33's
  `perception_loop.py`);
* and `llama-server` with Qwen2.5-VL-3B resident for the whole window,
  answering the 299 frames back to back with the stopping rule.

The board's own checkout (`~/vision-picar`, branch `jetson-bringup`) is not
touched: this runs from a separate worktree on the board.

Memory is measured directly, not as a drop: `MemAvailable` sampled every
second over the window, its minimum compared with **3.33's 1 GB floor**.
That is the same rule the 3.25 GB bar came from (stack-running
`MemAvailable` 4253 MB less the 1 GB floor), taken without assuming that a
drop measured on an idle board adds linearly to a running stack's -- page
cache and a shared CUDA context need not.

Two things make this window harsher than an arrival, recorded so a pass
can be trusted and a fail read correctly: 299 identity calls back to back
contend with perception for the GPU far more than one call per arrival
would, and the model answers while nav2 drives (a real arrival is
stationary).

**Criteria (written before measuring; CLAUDE.md section 7).** All from the
one loaded window (run L) unless marked.

S. **The stopping rule changes no answer:** on all 299 frames the YES/NO
   decision equals 3.48's Jetson record for the same model
   (`evaluations/identity-348/jetson/qwen25vl-3b-q4km.json`); the largest
   score difference is reported. Any flipped decision fails S.
1. **Precision >= 95%** (3.48 criterion 1, unchanged).
2. **0 YES on the 34 teal-bin frames** (3.48 criterion 2).
3. **Recall >= 50%** of the 74 visible frames (3.48 criterion 3).
4. **Precision >= the cloud's recorded 67.9%** on the same frames (3.48
   criterion 4).
5. **Latency: p90 <= 3.6 s** from sending the request (image encoding
   included) to receiving the deciding token, client-side, over the 299
   calls (3.48 criterion 5's bar; the quantity is now the time to the
   decision, since that is all a deployment would wait for).
6. **Memory: `MemAvailable` minimum >= 1024 MB** over the window, with 0
   OOM-killer events in the kernel log and 0 failed identity calls.
7. **The safety loop is unharmed: 0 late wheel-loop ticks** over the
   window's moving ticks (3.33 criterion 6's bar).
8. **Progress, paired with 6 and 7:** every nav2 goal in the window
   succeeds, and perception under this load stays within its budget, p90
   <= 250 ms a frame.
9. **No thermal throttling** in `tegrastats` (3.33 criterion 6).

Also reported, never as a criterion: the same stopped bench on the idle
board (run I: the time to the decision with nothing else running, and S
checked a second time), the model's resident footprint estimated from the
before/after `MemAvailable`, and the maximum temperature.

The model is recommended as the offline fallback only if S and 1-9 all
hold.

## Measured 2026-10-09

Both runs on the Jetson Orin Nano Super at 15 W, llama.cpp `e60eff9`
(CUDA, `--cache-ram 0`), from a worktree of this branch on the board
(`~/vp-358`; the board's own checkout untouched), the ROS image built from
this branch as `vision-picar-ros:plan-3.58`. Records and logs in
`evaluations/identity-358/` (`idle.json`; `L/` for the loaded window);
accuracy rows in `evaluations/identity-358/accuracy-299.json`
(`python -m control.identity_eval`). Jetson rows; never merged with
laptop or A10G rows (P24).

**Run I, idle board** (desktop on, nothing else running): 299 frames, 0
failed calls, time to the decision p50 2.49 s, **p90 2.95 s**, max 2.96 s
(3.48's server-side estimate was 2.84 s p90); `MemAvailable` drop 3.37 GB.

**Run L, the loaded window** (`tools/jetson/headroom_identity.sh`, rev
`c21f41d`): stack up and mapped in 2 min 54 s; `MemAvailable` 5964 MB
before anything, **5542 MB with the stack mapped**; then a 982 s window
with perception at 4 Hz, nav2 goals and the model answering all 299
frames back to back.

| criterion | bar | run L | verdict |
|---|---|---|---|
| S. stopping changes no answer | 0 flipped decisions vs 3.48 | **0 / 299** flipped, largest score difference **0.0** (run I the same) | **met** |
| 1. precision | >= 95% | **97.1%** (66/68) | **met** |
| 2. teal bin | 0 YES of 34 | **0 / 34** | **met** |
| 3. recall | >= 50% | **89.2%** (66/74) | **met** |
| 4. precision vs the cloud | >= 67.9% | 97.1% | **met** |
| 5. time to the decision, p90 | <= 3.6 s | **3.64 s** (p50 3.13, max 3.85) | **failed**, by 37 ms |
| 6. `MemAvailable` minimum | >= 1024 MB, 0 OOM, 0 failed calls | **296 MB**; 0 OOM events; 0 failed calls | **failed** |
| 7. late wheel-loop ticks | 0 | **0** in 17,512 moving ticks | **met** |
| 8. nav2 goals; perception p90 | all succeed; <= 250 ms | **47 / 47**; **182 ms** over 3,977 frames | **met** |
| 9. thermal throttling | none | none; max 59.9 C | **met** |

**Criterion 6 is not a near miss.** `MemAvailable` fell from 5541 MB to
435 MB within the first 30 s of the window (perception's pipeline and the
model loading together) and stayed between about 300 and 400 MB for the
rest of it: 967 of the window's 1,012 one-second samples were under the
1 GB floor, median 362 MB. Nothing was killed and no call failed, so the
board did not run out -- but it ran the whole window with a third of the
headroom 3.33 requires, which is the margin the floor exists to keep. The
model's share cannot be separated from perception's in this window: the
drop from the moment the bench started (perception already loaded, 5261
MB) to the low was 4.96 GB, against 3.37 GB for the model alone on the
idle board, so either the two processes' CUDA allocations grow together
under contention or part of the fall is perception's own; this run cannot
tell which. Either way the combination does not fit with 1 GB to spare.

**Criterion 5 failed narrowly, under a load harsher than an arrival:**
idle, the time to the decision is 2.95 s p90; with the model sharing the
GPU with perception at 4 Hz for 299 back-to-back calls while nav2 drives,
it is 3.64 s. A real arrival asks once with the robot stopped -- recorded
before the run as a reason this window is harsher -- but the verdict
stands as measured.

**Accuracy is unchanged by stopping or by load:** both runs' 299 decisions
are 3.48's exactly (criterion S), so criteria 1-4 carry 3.48's numbers.

**Recommendation: do not wire it in as measured.** Accuracy is the best
any local model has shown and stopping at the decision is free, but the
model does not fit beside the stack with the 1 GB floor (296 MB minimum),
and under load it misses the 3.6 s bar by 37 ms. What could change the
verdict, each a new section with criteria written first:

* **Load the model only for the arrival check, with perception paused**:
  at arrival the robot is stationary and perception's job is done, so the
  two need not be resident together. Cost: the model's load time (6.0 s
  idle, 9.0 s loaded in these runs) on each offline arrival.
* **A smaller vision projector or a lower-bit model** (the projector here
  is Q8_0, 0.84 GB), judged against S and criteria 1-4 first, since
  quantisation can move answers.
* **Or close it** and keep 3.53's late cloud re-check as the offline
  answer, which costs no memory.

**Open for the user:** whether this branch goes to `dev` (a measurement
record plus the stop-at-decision bench mode, the loaded-window harness
and their tests; nothing in the mission path changes), and whether to
pursue a variant above or close the local fallback. `~/bench-348/`
(llama.cpp and the models, about 11 GB) and `~/vp-358` (this branch's
worktree on the board) are left on the Jetson for that decision.
