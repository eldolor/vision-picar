# 3.72 A randomizer button: the robot server picks one of the 100 ProcTHOR houses

*`PLAN-ros-alignment.md` section 3.72; index: [README.md](README.md).*

**Why.** The user (2026-10-11): a button on the twin that has the robot
server pick one of the 100 ProcTHOR houses at random and shows it on the
page -- **without restarting the robot server** each time. Until now the
house was fixed at start-up (`SIM_MAP`).

**The rule this bends, and how far.** CLAUDE.md section 7: "Restart the
robot server to reset the robot; there is no reset endpoint, on purpose."
A new house moves the body, so this route is a reset. It is kept narrow:

* **Sim only:** the plain in-process simulator (`MockRobot` + `MockWorld`).
  Hardware, teleop, replay, `drive: ros` and the split simulator
  (`SIM_MOTOR_BOARD=fake`) answer 409 and change nothing.
* **Never under a driver:** refused (409) while any driver holds the robot
  (M4's authority) or a verb is running; the twin also disables the button
  while the brain reports a mission running.
* **A fixed list:** the first 100 usable ProcTHOR houses, the set 3.66 and
  3.69 measure on. No caller-supplied name.
* **Behind the secret,** like every other robot route.

**Design.** `POST /sim/house/random` builds the new house and swaps it into
the running body and map in place (`MockRobot.load_house`,
`MockWorld.load_house`): the motors stopped, the odometry zeroed (a new
body placement), the discovered map back to unknown. `/health` then names
the new house. The twin's Sim tab gets a "Random house" button that calls
it and redraws the map at once.

**Criteria (written before building; CLAUDE.md section 7):**

1. **The swap is complete and in place:** after the call, `/health`
   `sim_map` names a house from the list; the body's pose is that house's
   start; `/world/map` is the new house's size with only what has been
   seen known; odometry reads zero; the robot server's process is the
   same one (no restart).
2. **Driving works after it:** a verb after the swap moves the robot in
   the new house, vetted by safety against the NEW walls -- tested by a
   forward move toward a wall that exists only in the new house being
   refused.
3. **Refusals change nothing:** while a driver holds the robot, under a
   non-sim backend, and without the secret: 409/401, and `/health`'s house
   is unchanged.
4. **Random over the list:** 200 calls cover >= 80 distinct houses of the
   100, and never repeat the house just shown.
5. **On the page:** the button, at a 390 px phone viewport (a UI test
   against the real server, red first), changes the drawn map; a
   phone-size screenshot is the evidence; disabled while a mission runs.
6. **The suite passes;** the twin deployed (`service/static/sync.sh`,
   invalidation `Completed`, `app.js` parity) only after merge.

## Review (2026-10-11)

`/code-review` and the Thermos bug pass (the route touches who-drives
arbitration). Both found the same two medium bugs, so confirmed; the bug
pass added five lows, each checked against the code and fixed:

* **A mission between moves was not protected** (both). Authority lapses
  1 s after a move, so a brain waiting on a cloud step held nothing, and a
  tab without the brain connected (or curl) could swap the house under it
  -- the inventory then mixing two houses. The server now also refuses
  (`409 mission`) for `MISSION_QUIET_S` (30 s) after the brain or nav2 last
  drove; a person's driving does not block it.
* **The swap was not serialised with movement** (both). Check and swap now
  happen under `motion_lock` (non-blocking: `409 driving` if a move holds
  it), the house built before taking it; `MockWorld` swaps its world and
  cells, and reads the map, under its own lock, so a map read never sees
  half a swap.
* Lows: a map fetch begun before a swap is dropped after it (an epoch), not
  drawn as the old house; the swap no longer stamps `last_command_at`, which
  made the watchdog record a stop nobody caused; the button row shows only
  when `/health` says `mode: sim` with a house; a refusal's toast reads its
  sentence, not JSON; `SIM_MOVERS` is applied to the new house (ProcTHOR
  houses define none, so a server started with movers has none after a
  swap).
