# 3.65 Reinforcement learning inside the brain: three narrow decisions, not the whole brain

*`PLAN-ros-alignment.md` section 3.65; index: [README.md](README.md).*

**Why.** The user asked (2026-10-09) where reinforcement learning fits and
whether the brain should become an RL component. The answer agreed the same
day: **not the whole brain.** Learning goes into three narrow decisions,
each with a reward the simulator or the recorded walks can score, each
behind a config flag that defaults off, each with today's rule as the
fallback. The user approved all three and left the order and timing to
Claude.

**What stays out of any learned policy, and why:**

* **Safety** (`robot/safety.py`, the watchdog, arrival confirmation). Rule 4
  of CLAUDE.md section 2: the robot server has the last word on every move,
  and a policy is never the thing that decides it is safe to move.
* **Path following.** nav2 plans and the safety layer vetoes; RL would
  relearn that worse.
* **A single reward on its own.** This project has seen one gamed already
  ("reversals alone reward a spin", CLAUDE.md section 7): every reward is
  paired with a progress metric and judged on held-out data.

## The three phases, in the order they run

| Phase | Decision | Today | Learned version | Waits on |
|---|---|---|---|---|
| **1** | When the tier calls the cloud | Fixed triggers (`brain/tiered.py`: mission start, candidate sighting, cold search, staleness) | A contextual bandit: call now, or not | Nothing -- starts first |
| **2** | Which frontier to explore next | A hand-written rule (3.45, 3.69) | A small scoring model that picks the next goal | Nothing since 2026-10-11 -- criteria below; trained against `FakeNav` (3.66/3.69's sweeps), so nav2's parking cannot be learned round, and judged live on nav2 too |
| **3** | Where to search first | Not built (`brain/planner.py`) | Room/object priors learned from past missions | 3.50's map save/reload built, and 3.46's real-frame inventory (phase C) |

**Why phase 1 first:** it depends on no open section, its reward is real
money and seconds, and the recorded walks hold its ground truth -- each
walk's `labels.json` says, frame by frame, whether the target was visible,
which is exactly whether a cloud call could have helped. Phases 2 and 3
get their criteria when they start, written before building like this one.

## Phase 1: when to call the cloud -- criteria, written before building

**The decision.** On each frame the tier either calls `/navigate` or does
not. Today four fixed triggers decide; the bandit decides from what the
robot knows locally, never from labels.

**Context (local only):** the best candidate's probability this frame and
its streak, frames since the last call, frames since mission start, turns
since the last call, whether the target has a COCO word (the vocabulary
verdict), and whether anything passed the gate in the last few frames.

**Value of a call, from the walks' ground truth.** A call on a frame is
*useful* when it changes what the robot should believe:

* the target is visible (`labels.json`), the local tier did not pass the
  gate, and the cloud says visible -- a sighting local perception missed; or
* the local tier passed the gate, the target is NOT visible, and the cloud
  says not visible -- a local false positive caught.

Every other call is *spent* for nothing. Reward = useful - lambda x cost,
with lambda swept and reported, never chosen after looking at the held-out
result.

**Data.**

* The 2,261 labelled frames of the 21 labelled walks (535 with the target
  visible); the tier's local outputs recomputed per frame with the shipped
  pipeline (`control/perception_eval.py`'s path, frame set pinned).
* Today's triggers as recorded: 2,825 frames were walked under `tiered`, so
  the baseline's call decisions are in each `walk.jsonl` (`_tier.trigger`);
  where a frame was not walked under `tiered`, the baseline is replayed
  through `TieredVision` on the same outputs.
* **The cloud's answer on every labelled frame** -- only 373 frames carry
  one today. Replayed through the deployed `/navigate` (`control/walk_replay.py`,
  the honest way to compare, as its docstring argues), Opus 4.5 as shipped.
  **Cost: estimated $25-45; a 20-frame pilot measures it first, and the
  full replay waits for the user's go-ahead on the measured figure.**

**Split.** By walk, never by frame (neighbouring frames are near-duplicates):
seed 3651, about a third of the walks held out, every target kept in both
halves where it allows. The policy is a logistic model -- small and
readable -- trained on the training walks only.

**Criteria, on the held-out walks:**

1. **Same help for less money:** useful calls captured >= today's
   triggers', with **>= 30% fewer calls**; or more useful calls at no more
   calls.
2. **No walk abandoned:** no held-out walk with a useful call under today's
   triggers ends with none under the bandit.
3. **Mission start kept:** the first frame of a mission still calls (the
   tier's 2.5 rule) -- a hard rule outside the bandit.
4. **Cost reported** in calls and dollars per walk, beside useful calls per
   walk (stability paired with progress).
5. **Through the real path:** behind `tier_call_policy: learned` (default
   `fixed`), the simulator's tiered sweep keeps 3.46 criterion 1's property
   for safety (no new contacts, identical safety vetoes) and its arrival
   rate does not fall; one live tiered mission through the brain's HTTP API
   runs with it on.
6. **Pinned in a test** that a regression fails.

**Out of scope for phase 1:** learning on the car while it runs (the
reward needs labels, which only recorded walks have); the arrival
confirmation call (identity, handoff 1a), which stays a fixed rule.

## Phase 2: which frontier next -- criteria, written before building (2026-10-11)

**Why now.** The user asked (2026-10-11) whether to learn the driving
itself; the answer agreed was no -- the 3.69 misses were all decisions, our
simulator is kinematic, and nav2 reaches every goal it is sent -- and to
learn explore's choices instead. That is this phase. What held it back is
gone: 3.69's sweeps judge decisions against `FakeNav` (ground-truth
reachability), separately from nav2, and 3.66 gives 570 usable houses.

**The decision.** When no goal is live, explore picks one goal among the
candidates it already computes (`find_frontiers()`'s frontiers and
`find_view_gaps()`'s patches). Today a hand-written score ranks them. The
learned version scores each candidate from features explore already has --
path length, frontier size, unknown area near it, camera-unseen area near
it, whether it was reached before or set aside, kind (frontier or view),
steps and goals so far -- and picks the best. **Everything else in explore
stays rule-based:** sightings, approaches, the face/back-off rules, escapes,
the retry book, when the search ends. A candidate the rules would never
send (unleavable, set aside, reached twice) is never offered to the model.

**The model.** Linear in those features -- a few weights, printed and
readable -- trained by reinforcement on simulated missions: the
cross-entropy method over the weights (sample weight vectors, run each on a
batch of training houses, keep the best fraction, refit), CPU only, no
cloud, no GPU. A small network only if the linear model fails criterion 1
and the failure is recorded first.

**Which kind of RL, and why.** Evolutionary (black-box policy search): each
weight vector is judged by the total reward of whole missions, with no
value function and no gradient. The policy is the ranking of candidate
goals; scoring whole missions sidesteps per-step credit assignment, which
fits ten weights and a reward mostly decided at the end. The fallback
network (the same features in, one score per candidate out, two hidden
layers of about 32 units) would be trained by a gradient method (PPO).

**Reward,** per mission: +1 if found, minus 0.02 per goal sent, minus 0.01
per metre driven (stability paired with progress, CLAUDE.md section 7.4);
the weights 0.02/0.01 fixed here, before any training.

**Houses -- three sets, never mixed:**

* **Training:** usable houses 300-569 (270 houses never used by 3.66 or
  3.69), seeds varied per sample.
* **Selection:** usable houses 100-199 -- to choose between training runs,
  never to train.
* **Test:** usable houses 0-99 and 200-299, the rule's numbers as 3.69
  left them (99 and 99 found; median goals 13 and 10), run once at the end.

**Criteria, on the test set (200 houses), against the rule:**

1. **Fewer goals, no fewer finds:** found >= the rule's minus 1 (>= 197 of
   200), with the median goals per found mission **>= 20% lower**, or the
   median metres driven **>= 20% lower**.
2. **No house lost unexplained:** every test house the rule finds and the
   model does not is classified in this entry.
3. **Clean:** 100% of missions end with an outcome under the tick cap.
4. **The hand-drawn houses:** with the flag on, the four hand-drawn houses'
   explore tests and pinned sweeps hold; with it off (the default), nothing
   changes at all.
5. **Live, on nav2:** behind `explore_goal_policy: learned` (default
   `rule`), three `explore` missions in `home_first_floor` on the live
   stack end `found`, with no more contact samples than the rule's runs and
   median time no worse than 20% over the rule's -- the check that a choice
   learned against `FakeNav` survives real nav2.
6. **Readable and pinned:** the weights committed and printed in this entry;
   the test-set numbers pinned in a test that a regression fails.

**Out of scope:** learning while missions run; anything below the choice
of goal (nav2 drives); the found/arrival rules.

**Amendment 1 (2026-10-12, before any training run).** How it is built:

* **Features** (`brain/goal_policy.py`): path, turn from the heading (added
  to the list above), is-view, frontier size, view area, unknown share and
  camera-unseen share within 1 m, retry failures near it, times reached,
  and is-view x goals sent. Each scaled to about 0..1.
* **Pooled candidates:** frontiers and view gaps compete together (the rule
  looks at views only once no frontier is left). With the rule's order as
  weights the learned path sends the rule's goals exactly
  (`tests/test_goal_policy.py`).
* **"Seeds varied per sample":** a ProcTHOR mission is deterministic, so
  variety comes from a fresh sample of 40 training houses per iteration.
* **Training:** cross-entropy method, seed 3652, 24 weight vectors per
  iteration, best 6 refit, 20 iterations, starting at the rule's order;
  the mean scored on the 100 selection houses every 4 iterations, the best
  kept (`evaluations/explore-365/train.py`).
* **Metres** are each succeeded nav goal's shortest true-floor path plus
  what the verbs drove (`evaluations/explore-365/harness.py`).
* **The rule's test numbers** are re-run with this harness (3.69's rows
  have no metres), once, at the end, beside the learned run.

**Finding while training (2026-10-12).** The rule, re-run on the selection
houses for comparison, found 99 of 100 (median 10 goals, 27.9 m; mean
reward 0.327), where 3.69 records 100: house 270 now ends `searched` after
55 goals (3.69: found, 34). The same on `dev` (2d54e78), so not this
section's change; 3.69's held-out file was committed with its third
review's fix and was likely measured before it. The rule's numbers used
here are today's, re-run, never 3.69's.
