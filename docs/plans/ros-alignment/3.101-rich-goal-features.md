# 3.101 Explore's goal choice on ~40 features: 3.96's F-large plus route, information gain, room graph, history, budget and relative features

*`PLAN-ros-alignment.md` section 3.101; index: [README.md](README.md).*

**Why.** The user, 2026-10-25: "What if we use more than 10 features? Come
up with a much higher number of features that are applicable to our use
case", then "take over this and execute the approaches and give me the
results". 3.100 found the evolutionary and gradient models land on the
same -11% on fresh houses with the ten features, and 3.96's F-large (the
ten plus seven room features, 5,464 training houses) cut median goals 43%
on its 588 test houses. This section asks whether more features of the
same honest kind -- computed only from what the brain has at the choice,
never from ground truth -- add to F-large.

**The user's choices (2026-10-25, before any run):** the win bar is
"beat F-large" (below); about 20 simulator-trainable features in one arm;
records only (nothing in `brain/` changes, whatever the result); fix the
session-start Playwright pin; update the "A Thousand Houses" artifact.

**The arm, F-rich.** F-large's 17 features plus the 25 below (42), and
nothing else changed: the same network shape (linear + MLP 42 -> 32 -> 32
-> 1), the same training houses (3.96's large set, 5,464), the same oracle
clone (30 epochs) and PPO budget (60 iterations x 48 houses x 8 missions,
seed 3961), the same selection houses and checks every 10 iterations, the
same reward. The oracle sets are recorded again, because they store each
choice's features. Code in `evaluations/goal-learn-3101/`; 3.96's
`train.py` gains one hook (`EXTRA_FEATURES`, default `None`, so its own
runs are unchanged).

**The 25 new features** (each scaled to about 0-1, clipped):

* **Route:** detour (path / straight line), path rank in the pool, path
  minus the pool's shortest, distance to the nearest other candidate,
  share of the pool within 2 m, clearance from the goal to the nearest
  occupied cell.
* **Information gain:** unknown cells visible from the goal by raycast
  within 3 m, known floor the camera has not seen visible within 3 m,
  unknown share within 2 m and within 4 m, gain per metre of path.
* **Room graph** (from `segment()` on the brain's map, as 3.96's room
  features): hops from the robot's room, the candidate's room a dead end
  (one neighbour), its number of neighbours, the camera's coverage of its
  floor.
* **This search:** the trail's closest approach to the candidate, the
  share of the trail within 1.5 m, goals sent since a new room was
  entered, seconds since the map last grew.
* **Budget:** share of the time limit used, pool size, known share of the
  map's box.
* **Relative:** the rule's own pick (a flag), the information-gain rank
  in the pool, the share of the pool better on both path and gain.

**Left out, and why (written before the run):** near-miss sightings
(sub-threshold detections). The simulator's detector is exact, so a
near-miss feature would need a made-up noisy detector built on the true
target position; the policy could learn to trust a signal the car's
perception does not give at that rate. It waits for the Rover's frames
(3.92's calibration). Families 4 (object co-occurrence), 6 (across
missions) and 8 (car risk) wait on the car's data for the same reason.

**Where it runs.** This cloud container (4 cores); no AWS (its credentials
are refused here) and no spend; the Jetson is not reachable, so its
timing is owed.

**Baselines, re-run today on the same code** (explore changed since
2026-10-23): F-large's `best.json` on the selection and test houses, and
the rule on the test houses.

**Criteria (written before any run; CLAUDE.md section 7):**

* **S (gate to the test houses).** F-rich's best selection check (mode R
  mean reward, the clone's own check counted, as 3.96) is above F-large's
  on the same selection houses today. If not, F-rich never runs on the
  test houses and the section stops, recorded.
* **On the 588 test houses (`train` 1000-1999), run once:**
  1. **Reward:** mode R mean reward >= F-large's + 0.02.
  2. **Finds:** found >= 0.99 x F-large's, in mode R and in mode U.
  3. **Trips:** median goals per found mission <= F-large's, in R and U.
  4. **Clean:** 100% of F-rich's missions end with an outcome, no
     exception and under the tick cap.

  F-rich wins only if 1-4 are all met. Reported, not judged: mode U's
  reward; metres; 3.96's criterion-2 bars against the rule; houses won and
  lost against F-large; the linear weights; which features matter
  (permutation of each feature on the held-out oracle choices); one goal
  choice's time on this container for both arms (the Jetson's 100 ms bar
  is owed); the 50%-labels-dropped arm if the night allows.

**Out of scope:** wiring into `brain/` (the user: records only), live
nav2 runs, the Jetson.

**Amendment 1 (2026-10-25, after the code review and before the run; the
first start, 6 minutes of oracle shards, was stopped and its data
deleted).** Four feature definitions changed, the count stays 25:

* `since_new_room` became **`since_new_ground`**: goals sent since the
  trail last covered 3 m² of new floor. Counting rooms stood in moved with
  `segment()`'s re-cut as the map grew (rooms merging or splitting), so it
  recorded segmentation churn, not progress.
* **`time_used`** is sim seconds since the mission started / 120 s. As
  "share of the 1,200 s limit" it never passed 0.02 in the sweeps, whose
  missions take tens of sim seconds.
* **`unknown_2m` / `unknown_4m`** count cells off the map as unknown, as
  3.96's map crop does; counting them as known undervalued frontiers at the
  map's edge.
* The room-graph features look a point up with 3.96's own `_seg_at` (the
  cell, else its 8 neighbours), so both feature sets put a candidate in the
  same room.

Not changed: the two room cuts per choice (3.96's and this one's), about a
millisecond on the simulator's 0.30 m maps; the timing report measures it.
