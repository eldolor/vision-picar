# 3.93 One session on the Jetson at a time: a lock held on the board

*`PLAN-ros-alignment.md` section 3.93; index: [README.md](README.md).*

**Why.** The user (2026-10-22): "there may be other Claude Code sessions
that are using the Jetson. Figure out a way to use it exclusively for your
use if there is a need." Sessions share one board. A bench run, a service
restart and a memory measurement each disturb the others: 3.81's memory
numbers and 3.78's latency bars are only valid on a board doing nothing
else. Until now each session checked by hand (`systemctl is-active`,
`pgrep`), and the laptop's heavy-run lock (`tests/demo_explore.py`
`heavy_lock`) does not cover the board.

**Found on the way.** On 2026-10-22 another session was already holding an
ad hoc lock on the board: `~/.picar-board.lock` held with `flock`, plus a
one-line `~/.picar-board.owner`
(`session_01AcPP84 (Mac): updating picar-stack to dev, since <iso>`). No code
for it is in git. This section keeps that file, that lock call (`flock(2)`)
and that line's format, so a hold taken by hand and one taken by the tool
exclude each other.

**The design.**
* **The lock lives on the board**, because the board is what is shared,
  and laptop sessions, a second Mac and cloud sessions all reach it over
  `ssh picar-jetson`. A small Python holder (`python3 -c`) runs on the
  board and holds `flock(LOCK_EX)` on `~/.picar-board.lock`.
* **A hold ends by itself when its session goes away.** The holder reads
  its ssh stdin, and the local side writes a heartbeat byte every 20 s. The
  holder lets go when any of these happens:
  * its stdin closes (the local process ended, or was killed, and ssh
    went with it);
  * no heartbeat arrives for 90 s (the network dropped silently);
  * its declared maximum passes (`--max`, default 4 h).

  A crashed session cannot hold the board for longer than that.
* **`tools/jetson/board_lock.py`:**
  * `run [--why] [--wait S] [--max S] -- <cmd>`: holds the lock for one
    local command and exports `PICAR_BOARD_TOKEN` to it.
  * `hold` / `release`: for a session's multi-step work. A detached
    holder is kept per worktree.
  * `status`: free, or the owner's line.
  * `env`: prints the token of this worktree's hold.

  Busy: `run` and `hold` exit 75 and print the owner's line, or wait up
  to `--wait`.
* **Board-side scripts refuse when another session holds the board.**
  `tools/jetson/board_lock_check.sh` is sourced by `headroom_identity.sh`,
  `headroom_mission.sh` and `bench_local_vlm.sh`. It exits 75 when the lock
  is held and `PICAR_BOARD_TOKEN` is not the holder's, and goes on when the
  lock is free or the token matches.
* **The rule** (`docs/guides/PARALLEL-SESSIONS.md`, `tools/jetson/README.md`,
  CLAUDE.md 3c): take the board lock before anything that changes the
  board's state or measures it, including a service stop or start, a bench,
  or an install. Read-only checks (`status`, `free`, `systemctl
  is-active`) need none.

**Criteria (written before building; CLAUDE.md section 7).** Criteria 1-5
run in the suite on the laptop, with the holder in a local shell in place
of ssh (`PICAR_BOARD_SSH`) and the lock in a temporary directory
(`PICAR_BOARD_LOCK_DIR`). Criterion 6 runs on the board.

1. **Exclusion.** While one `run` holds the lock, a second `run`, a `hold`
   and a by-hand `flock -n` on the same file all fail. The two tool calls
   exit 75 and print the owner's line.
2. **Release on death.** After the holding process is killed with SIGKILL,
   the lock is free within 5 s (stdin closes).
3. **Release on silence.** With the heartbeat stopped (the test's hook)
   and stdin left open, the lock is free within the silence limit plus 5 s.
   The suite runs this with the limit set to 3 s.
4. **Release at the maximum.** A hold with `--max 2` is free within 7 s.
5. **The check.**
   * `board_lock_check.sh` exits 0 when the lock is free, 0 with the
     holder's token, and 75 with no token or a wrong one.
   * A hold taken by hand (`flock` plus an owner line, as the other session
     did) counts as held.
6. **On the board.** The test itself holds the lock while it runs (it
   changes nothing on the board).
   * `run` takes and releases the real lock.
   * `status` from a second process names the holder while it is held.
   * The check refuses a wrong token on the board.
   * Killing the local `run` frees the board's lock within 5 s.
