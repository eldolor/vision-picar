# 3.71 The robot server, brain and tunnel as Jetson services

*`PLAN-ros-alignment.md` section 3.71; index: [README.md](README.md).*

**Why.** On 2026-10-11 the deployed twin showed "Brain unreachable": the
robot server, brain and ngrok had been started by hand on the laptop, and
nothing brought them back when they stopped. The user then asked for them
to run on the Jetson, reachable over the internet, and to start at boot.
That was done the same day by hand (two systemd units, written on the
Jetson). This section puts those units, and how to install and update
them, in the repo -- the first half of B5 (`HARDWARE-READINESS.md`; its
second half, `mode: hardware` with the Rover attached, waits for the
Rover).

**Scope.** The units run `service/tunnel/run.sh` as it is (sim mode, the
twin's Sim tab) from a service worktree, `~/vision-picar-service`, so the
bench checkout `~/vision-picar` is never touched; and `ngrok start picar`.
No code changes.

**Criteria (written before building; CLAUDE.md section 7):**

1. **The repo is what runs:** `tools/jetson/install_services.sh` installs
   the units from `tools/jetson/systemd/`; afterwards the installed files
   are byte-identical to the repo's (`diff` empty).
2. **A crash comes back:** killing the robot server's process, the
   service is `active` again and `/health` answers through the public
   tunnel URL **within 30 s**.
3. **A reboot comes back, with no laptop:** after `sudo reboot` of the
   Jetson, both units are `active` and `/brain/health` answers through the
   public URL **within 180 s** of the reboot command; then one `frontier`
   mission started through the public URL (robot + brain both reached by
   the tunnel) ends with an outcome.
4. **The update procedure works:** the documented steps move the service
   worktree to a new `dev` commit, and `/health` through the tunnel reports
   that commit's `git_revision`.

## Results (2026-10-11)

| # | Criterion | Bar | Measured | |
|---|---|---|---|---|
| 1 | installed units are the repo's | `diff` empty | both identical after `install_services.sh` | met |
| 2 | a crash comes back | <= 30 s via the tunnel | **~7 s** (robot server killed; `NRestarts=1`) | met |
| 3 | a reboot comes back, no laptop | <= 180 s; a mission ends | brain `/health` via the tunnel **53 s** after `reboot`; a `frontier` mission started through the public URL ended **`found`** at step 61 | met |
| 4 | the update procedure | `git_revision` = the new commit | at merge: the Jetson moves to the merged `dev` | |

**Criterion 2 failed first, on `dev`'s `run.sh`.** It ended with a bare
`wait`, so a crashed robot server left the brain and proxy running: the
service stayed `active`, systemd never restarted it, and the robot was still
down 40 s later. `run.sh` now polls its children and exits when any one
ends (its EXIT trap stops the rest); polled because the Mac's bash 3.2 has
no `wait -n`. Interactively on the Mac, the same change means one crashed
server stops the set instead of leaving it half up.

**Found on the way: the Jetson's secret was its own.** The twin holds the
Mac's `LOCAL_SECRET`; the Jetson's file (2026-10-04) had a different one,
and the twin showed "Secret rejected". The Mac's files were copied over
(the Jetson's old one kept as `~/.vision-picar-local-secrets.jetson-2026-10-04`);
the README's setup now copies them.

**Code review** (3 findings, all fixed and re-measured on the Jetson): a
requested stop now exits 0 at once (it waited for a child to die, up to the
20 s SIGKILL, and left the unit "failed"; now a restart takes 1.9 s,
`Result=success`); the install script starts the stack once and polls
health; README section 4's bench stops the services first, since
`picar-stack` restarts itself and would race the bench for its ports.
Crash recovery re-checked after the fix (`NRestarts=1`, back on its own).

**Not in scope:** the house (`SIM_MAP`, unset: `starter_house`), and B5's
second half -- `mode: hardware` with the Rover.
