# 3.126 The bridge answers 304 for an unchanged map

*`PLAN-ros-alignment.md` section 3.126; index: [README.md](README.md).*

**Why.** Since 3.123/3.124 the brain gets a 304 from `/world/map` for an
unchanged map (63% of reads live), but the hop behind it still moves the
whole grid: `RosWorld.get_map()` GETs `/slam/map` on every read, the bridge
JSON-encodes every cell and the robot server decodes them, on its
threadpool, under the GIL the wheel loop's event loop needs (3.87). Only
then does `RosWorld` see from `(session, version, anchor)` that its cache
is current. Found by 3.124's review.

**Change.** The bridge tags a map reply `ETag: "<session>:<version>"`
(versions move only when the grid does, 3.124); a `GET /slam/map` whose
`If-None-Match` names the tag of the map it would send answers a bodiless
304. `RosWorld` keeps the last reply and its tag, sends the tag, and on a
304 naming it uses the kept reply (the cache key, and so the resample, are
unchanged). A 304 naming another tag drops the kept reply and asks
once more in full (amendment 1); a 304 to a request with no tag, and any
other non-2xx, is an error as today. The bridge's `/health`
counts `map_replies: {full, not_modified}`.

**Criteria (written before building or measuring; CLAUDE.md section 7):**

1. Unit tests, laptop, no ROS: the bridge's handler (stubbed bridge)
   answers 304 only for the current tag while `slam.state` is `ready`; a
   changed version or session, a cleared map or a not-ready state answers
   in full (or unusable, as today), never 304; no tag on an unusable
   reply. `RosWorld` (httpx `MockTransport`) sends the kept tag, returns
   the same map on a 304 as on the full reply, re-reads in full on a new
   version; a 304 naming another tag is followed by one full read (amendment
   1), and a 304 to an untagged request is a bridge error (`unusable_map()`
   with `classify`).
2. Cost, desktop, a real bridge HTTP handler serving a 400 x 400 grid
   (0.05 m, 20 m square) and a real `RosWorld`: the median wall time of an
   unchanged `get_map()` is at most 10% of `dev`'s on the same grid
   (`dev` today: a full GET, decode and cache hit).
3. Live, `home_first_floor`, explore, branch image
   `vision-picar-ros:plan-3.126`, `PICAR_ROS_NETWORK=host`: at least 55% of
   the bridge's map replies are 304s (`/health` `map_replies`; 3.124's
   brain-side share was 63%, and the brain's reads drive the robot's);
   the mission ends `found` with 0 contacts.
4. `ready` passes.

**Amendment 1 (2026-10-31, while building, before any test or
measurement):** criterion 1 first said a 304 naming another tag is a bridge
error. `classify` reads a 304 as non-retryable, so explore would end its
mission `failed` on one stray reply; the robot server now drops its kept
reply and asks once more in full.

**Amendment 2 (2026-10-31, after review, before the live result was
read):** a 304 to the untagged retry is a retryable transport fault
