# 3.82 A refused goal must not lift a Stop's hold

*`PLAN-ros-alignment.md` section 3.82; index: [README.md](README.md).*

**Why.** Two bugs 3.76 batch H found and left for the user
([3.76-legacy-review.md](3.76-legacy-review.md), batch H, "Open for the
user"):

1. **Safety path.** `robot/server.py`'s `world_goal_set` bumps
   `goal_stop["gen"]` and clears `goal_stop["hold"]` BEFORE
   `world.set_goal()` answers. A goal that is then refused -- the bridge
   unreachable (`ros_unavailable`), its 409 (`no SLAM session yet`), nav2
   down (503), `accepted: false` -- still supersedes the Stop's goal-ending
   loop (`_end_goal_after_stop`) and lifts its hold on driver `ros`, for a
   goal that never existed. If the Stop's cancel had not yet landed, nav2
   drives the goal the Stop was ending. The safety spec already says only
   an **accepted** goal bumps the generation; the code does not.
2. **A configuration fault waited out as an outage.** A bridge 401 on
   `POST /goal` (mismatched secrets) reaches explore as `200 {accepted:
   false, reason: ros_unavailable}`, and `brain/explore.py` `_send()` waits
   on every refusal, so the mission sits still for `mission_time_limit_s`
   (1200 s) instead of failing. `_bridge_blip`'s rule (transient waits, a
   401 ends it) never sees it: the robot server labels every bridge error
   the same, in prose (3.76 C13 records the structured-field root fix as
   open).

**Design.**

* Bug 1: the goal route reads the generation under `goal_gen_lock`, calls
  `set_goal()` (still under `goal_stop_lock`, never under `goal_gen_lock`:
  3.76 A8), and only when the answer is `accepted: true` AND the generation
  is unchanged does it bump it and clear the hold. Unchanged matters: a Stop
  that landed while `set_goal()` was in flight owns a newer generation, and
  its loop (blocked on `goal_stop_lock` until the call returns) must end the
  goal just taken. Bumping after it would cancel the Stop instead. A refused
  goal changes nothing: the Stop's loop carries on.
* Bug 2: the refusal carries structured fields, not prose: `retryable`
  (bool) and `bridge_status` (the bridge's HTTP status, or null for a
  transport error). `retryable` is false for a 4xx other than 408, 409 and
  429 -- the same split `brain/navigate.py`'s `CloudUnavailable` uses -- and
  true for transport errors and 5xx. Explore ends the mission on
  `retryable: false` (a raise, so the runner finishes `failed` naming the
  status); a refusal without the field, or `retryable: true`, still waits.
  Additive: the reason stays `ros_unavailable`, so the twin and older
  brains read it as before.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Red first.** Every test written for a bug (criteria 2 and 5) fails
   on `dev` (`a7ffc83`) for the reason it names and passes with the fix.
   The guards for rules `dev` already keeps (criteria 3 and 4) pass on
   both, and criterion 4's accepted case must fail against the naive fix
   (bump the generation after an accepted answer, unconditionally).
2. **A refused goal keeps the Stop's hold** (in process, the fake bridge
   and fake nav2 of `tests/test_stop_cancels_goal.py`, nav2 posting `ros`
   wheel commands at 20 Hz): for each refusal -- transport error, bridge
   503, bridge 409, `accepted: false` (no SLAM session) -- posted after a
   Stop whose first cancel failed, the fastest `ros` wheel speed applied
   over the next 1.5 s is **0.0 rad/s**, and the Stop's loop goes on to end
   the old goal (bridge goal `None` within 3 s).
3. **Handoff 3b holds:** an accepted goal after a Stop drives (wheel speed
   > 0 within 0.3 s) and the Stop's loop never cancels it (bridge cancel
   count unchanged over 1 s).
4. **The race:** a Stop landing while `set_goal()` is in flight. Accepted:
   the new goal is cancelled by the Stop's loop and the fastest `ros` wheel
   speed after the Stop is 0.0. Refused: the old goal is ended, speed 0.0.
   In both, the Stop answers in **< 0.5 s** while `set_goal()` hangs (A8).
5. **The auth fault ends explore:** a bridge 401 (and 403) on `POST /goal`
   through the real robot server and `RemoteNavigator` ends an explore
   mission `failed` within **3 ticks**, its note naming the 401; on `dev`
   the mission is still running after the same ticks. A transport error, a
   bridge 503 and a 409 still WAIT (no raise, mission running).
6. **Live, through the real stack** (robot server, ROS container
   `vision-picar-ros:latest`, `scaled_house`, this section's ports and
   domain), with a pass-through proxy between the robot server and the
   bridge that can fail one `DELETE /goal` and refuse `POST /goal` with 503:
   (a) goal A driving, Stop, the first cancel fails, a refused goal B at
   once: the robot's TRUE displacement (`/world/truth`) over the following
   8 s is **<= 3 cm**, and goal A ends neither `active` nor `succeeded`;
   (b) Stop, then an accepted goal B: nav2 reaches it (`succeeded`) within
   60 s. The same harness on `dev` is run once for (a) as the baseline and
   recorded, whatever it shows.
7. **Ground truth for safety:** the change does not touch motion vetting,
   so `tests/footprint_sweep.py` is not re-run; the live (a) displacement
   is the truth measurement.

## Review round 1 (2026-10-15): `/code-review` (high) and the Thermos bug pass on `a7ffc83..c00fa4a` (A, B)

**Confirmed by both, fixed red first: B's fix did not reach the real
fault.** The bridge checks the secret on every route but `/health`, so with
mismatched secrets the map and pose reads are refused before any goal:
`RosWorld.get_map()` read the 401 as "no map", explore waited on "no map
yet" for the whole time limit, `set_goal()` answered `no SLAM session yet`
(no `retryable`), and at start `RemoteNavigator.available()` read the goal
route's 503 as "no nav2". B's test passed only because its fake refused
`POST /goal` alone. Now one rule, `world/bridge_faults.py` `classify()`,
is used by `RosWorld` (an unusable map carries `bridge_status` and
`retryable`; a non-retryable fault before any session raises), the robot
server (the goal POST's fields; GET/DELETE `/world/goal`'s 503 carries
`x-bridge-retryable` and `x-bridge-status` headers), `RemoteNavigator`
(`available()` raises `PermissionError` naming the status, which the brain
turns into a start error) and explore (`_choose_next` ends the mission on a
non-retryable map; `_bridge_blip` reads the header). `world.bridge_faults`
joins the brain's import allowlist (httpx only, no backend).
