# 3.99 Log a person's interventions; interventions per hour

*`PLAN-ros-alignment.md` section 3.99; index: [README.md](README.md).*

**Why.** The user's parked idea from 2026-10-24, started on their word the
same day: log each time a person steps in on a mission and count
interventions per hour, as the start of learning from nudges. Whether to
learn from them is decided after the Rover produces data; this section only
keeps the record and the count.

**What an intervention is today.** Every one ends the mission. A person's
Stop (the brain panel's `POST /mission/stop`, or the robot server's `/stop`
from the D-pad, 3.84's latch) ends it `cancelled` / `stop`; a person at the
D-pad, or the phone's tap-to-goal, preempts the brain and ends it
`cancelled` / `dpad` (3.70 E5). So a mission holds at most one, and
interventions per hour is "missions a person ended" over "hours of
autonomy". A 3.88 goal pick is NOT one: it answers a question the robot
asked, and it is counted beside the intervention (`person_picks`), not in
it. An autonomous preemption (another brain, the ROS stack) and B3.3's
hung-tick abort are faults, `failed`, never a person's.

**Design.** `brain/intervention_log.py`. One JSON line per mission end,
interventions or not -- the missions without one are the rate's
denominator -- appended to one file, `<intervention_dir>/interventions.jsonl`
(`brain.intervention_dir`, default `recordings/interventions`, env
`INTERVENTION_DIR`), flushed and fsynced with 3.88's durable appender. A
line carries: the mission id, house (the simulator's map; None on the car),
policy, job, target, the start and end (UTC), `autonomous_s` (elapsed minus
3.88's pauses), the outcome, `person_picks`, and `intervention`: None, or
the kind (`stop` | `dpad`), how it arrived (`via`: `brain_stop`,
`robot_stop`, `preempted`), the driver when the robot server named one, the
detail, the mission second it landed, the step, the last action, explore's
last event, and the pose in the house frame read after the stop
(`pose_after_stop`; under a D-pad the person may already have moved it).
Positions only, never an image or a map, and the file stays on the machine:
nothing uploads it. The line is written on its own thread after the
robot's stop (the pose is an HTTP read, and a Stop runs `_finish` on the
brain's event loop); a write that fails is logged once and never fails a
mission. `python -m control.intervention_report [dir]` reads the file and prints
missions, autonomous hours, interventions (stop / dpad) and interventions
per hour, overall and per policy; a line cut by a power loss is skipped.

**Criteria (written before building; CLAUDE.md section 7):**

1. Every mission that started writes exactly one line at its end, with the
   fields above; red on `dev` first (no file is written there).
2. Only a person's end is an intervention: `stop` via the brain's Stop and
   via 3.84's latch (`StoppedByPerson`), `dpad` via a person's preemption.
   `found`, `exhausted`, `out_of_budget`, `failed` (an autonomous
   preemption, B3.3's abort, a step that raised) record `intervention:
   null`. A second end (a Stop after the mission ended) writes nothing.
3. A log that cannot be written (the directory unwritable, the pose read
   raising) never changes the outcome, never skips the robot's stop, and
   still writes the line when only the pose failed (`pose_after_stop:
   null`).
4. The report: on a pinned fixture it prints the right counts, hours and
   rate, per policy too; a partial last line is skipped; no file reads as
   "no missions recorded", not an error.
5. Live, through the brain's HTTP API on the local plain-sim stack: one
   mission ended by a D-pad tap (`/action` with `x-driver: twin-dpad`), one
   by the brain's Stop, one that ends on its own (a short time limit,
   `out_of_budget`). The file then holds three lines: `dpad`, `stop`,
   `null`, and the report reads 2 interventions over the three missions'
   autonomous time.
6. No mission outcome changes: the mission-runner, brain-server, explore-ask
   and offline suites pass unchanged.

## Review round 1 (2026-10-24, Sonnet, both passes)

Nothing above low-medium. Fixed, each red first
(`tests/test_intervention_log.py`, the seven "review round 1" tests):

* **Both:** the loop's cancellation handler calls `stop()`, so a cancel no
  person asked for (the process shutting down) read as a person's `stop`.
  The brain server now sets `runner.loop_cancelled` unless the Stop route
  set `operator_stopped`; such an end is `end_via: loop_cancelled`, no
  intervention. An attribute, not a `stop()` argument, so a harness
  runner's `stop(reason)` (AGENT-HARNESS.md) is unchanged.
* **Both:** the first build read `house` on every start (a `/health` round
  trip, up to 10 s). The start reads it for ask mode only, as on `dev`; the
  line reads it at the end, on its own thread (`runner.house_fn`).
* **Both:** the writer was a daemon thread, so a restart straight after a
  Stop lost the line. Not a daemon now: Python waits for it at exit (up to
  the pose read's timeout).
* **Bug pass:** each mission's `InterventionLog` had its own lock on the
  one shared file; the lock is now the file's.
* **Code review:** the report ignored `INTERVENTION_DIR` (now its default);
  an unusable pose and a failed read were the same `null` (now
  `pose_note`).

## Review round 2 (2026-10-24, Sonnet, both passes, on round 1's fixes)

Nothing above low-medium. Fixed (the two new tests red on round 1's code):

* **Both:** round 1's non-daemon writer made up to two blocking reads (the
  house's `/health`, the pose), so a brain exiting against a hung robot
  server or bridge waited out both client timeouts. The house is read at
  the start again, and the pose on a daemon thread of its own, waited for
  at most `POSE_READ_S` (2 s; `pose_note: read timed out after 2 s`).
* **Both:** reading the house at the end could name the next house after a
  Random house swap. Reading it at the start (round 1's first finding)
  costs a `/health` GET per start; the start already calls the robot
  server (`/autonomy/resume`), so a hung one fails the start either way.
  Round 1's "start reads no house" is reversed on purpose.
* **Code review:** round 1's registry of per-file locks worked around a log
  built per mission; the brain server now builds one in `create_app`.
* **Code review:** a test patched `threading.Thread` process-wide; the
  writer is kept on the runner (`_intervention_writer`) and read instead.
* **Bug pass:** the report's default skipped `config/robot.yaml`. The CLI
  is now `python -m control.intervention_report`, defaulting to
  `load_brain_config()`'s `intervention_dir`; `brain/` still imports
  nothing from `control/`.

Kept as is: the brain server marks a non-person cancel (`loop_cancelled`)
rather than marking the person's Stop (`operator_stopped` is that mark,
set by the Stop route before it cancels); in-process harness `stop()` calls
write no line, since only the brain server sets a log. A shutdown landing in
the same instant as a 3.84 latch refusal can still read `loop_cancelled`
(recorded below).

## Review round 3 (2026-10-24, Sonnet, both passes, on round 2's fixes)

Nothing above medium. Fixed: the config comments and this file still named
the removed `python -m brain.intervention_log` (it imported and printed
nothing); the pose read now uses the runner's own `call_with_timeout()`
rather than a copy, and a timed-out read is logged; the hung-read test
releases its reader in a `finally`. Kept: the `/health` read per start
(round 2's call), `InterventionLog` as a named subclass with no behaviour of
its own (the name is the file's role).

**Known limits** (recorded, not fixed):

* A person's robot-server Stop while the brain sends no verb -- the
  arrival's cloud confirmation of a local-led arrival -- can still end
  `found` (CLAUDE.md 3b's open 3.84 item: the brain cannot read the
  latch), and then the line carries no intervention.
* A preemption whose detail names no holder reads as a person (`dpad`,
  `by: null`), 3.70 E5's rule since before this section.
* `pose_after_stop` is read after the stop; under a D-pad the person may
  already have moved the robot.
* The start and end are wall-clock, `autonomous_s` the runner's clock: in
  a sweep on simulated time they disagree by design.
* `python -m control.intervention_report` with no directory resolves the
  config's relative `recordings/interventions` against its own working
  directory: run it from the repo root (or the board's service worktree),
  or pass the directory.
* One lock covers the brain server's one log; two apps in one process (only
  tests) would hold two on one file. Each append is one small write.
* A shutdown cancel and a person's latched Stop in the same instant: if
  the cancel reaches `_finish` first, the line reads `loop_cancelled`, no
  intervention.
* A shutdown's line counts in the denominator (`end_via: loop_cancelled`);
  the report does not split by `end_via`.
* SIGKILL or a power cut before the line's fsync loses it; the line is the
  only record (the mission's metrics row, when shipped, also carries
  `cancelled_by`).
