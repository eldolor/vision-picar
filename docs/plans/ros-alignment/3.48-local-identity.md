# 3.48 A local identity check: can a small VLM on the Jetson confirm arrival?

*`PLAN-ros-alignment.md` section 3.48; index: [README.md](README.md).*

**Why.** Since handoff 1a a tiered mission ends `found` only on a cloud yes
at arrival, and since 3.47 a mission whose cloud never answers ends
`arrived_unconfirmed`. Idea 3 of the 2026-10-07 XPENG/Banma comparison
("on-device first, cloud-assisted"), approved by the user 2026-10-09: could
a model on the Jetson answer "is the target in this frame?" when the cloud is
unreachable, so an offline arrival can be confirmed locally? **This section
measures only.** Nothing is wired into the mission path; the answer decides
whether a later section builds it.

The costly error is a wrong YES -- it would turn a local false positive into
`found` on the wrong object. That is the failure this project has already
seen from a VLM: on the 209-frame search walk the cloud model (Opus 4.5)
claimed the blue bottle on 44 frames, 34 of them a teal storage bin (P3,
2026-09-07; `perception_eval.py`'s docstring).

**Candidates, and why these.** P5/P7 (`EDGE-PERCEPTION-BENCH.md`) already
scored small VLMs on this corpus on an A10G, scored by GROUNDING
(`P(it localises)`), not yes/no, because a VLM's yes/no is answerable from
prior (P(yes) 0.884 on a frame it would not box). Their per-frame records
are in `evaluations/gpu/`. A web check (2026-10-09) found the current small
VLMs benchmarked on an Orin Nano 8 GB are Qwen2-VL-2B / Qwen3-VL-2B-class
(e.g. Cosmos-Reason2-2B) through llama.cpp / TensorRT Edge-LLM; none is
already in the project, and any new VLM weights are over this phase's 1 GB
download limit.

1. **Qwen2.5-VL-3B-Instruct** -- the best small VLM at 0 false positives in
   P7 (42% on 610 frames); trained grounding; Apache-2.0; cached on the Mac.
2. **InternVL3-2B** -- the smaller VLM P7 measured (3% at 0 FP, 75% at 3).
3. **Grounding DINO-tiny** (not a VLM; the control) -- owned P7's
   zero-false-positive point (50%), ~170M parameters, under the download
   limit, and "a model that is never wrong is a better corroborator than one
   that is more often right" (P7).

**Frame set, pinned:** the four rig walks of 2026-09-07 --
`blue-bottle-20260907-142454` (33), `blue-bottle-20260907-185007` (209),
`blue-shoes-20260907-152528` (19), `red-backpack-20260907-144856` (38):
**299 frames**. Reference: each walk's CURRENT `labels.json` (never
`walk.jsonl`); where a stored record's `visible` disagrees with today's
label, today's label wins and the count is reported. The teal-bin subset:
the frames of `blue-bottle-20260907-185007` where Opus's recorded
`navigate.target_visible` is true and the label is false. Opus's recorded
answers come from each frame's `walk.jsonl` (`model_id`
`us.anthropic.claude-opus-4-5-20251101-v1:0`).

Accuracy is rescored from the A10G records (GPU, fp32; never merged with a
CPU or Jetson row, P24). Latency and memory are measured on the Jetson at
15 W on `tools/jetson/bench_frames.json`'s 60 timed frames (+3 warm-up).

**Operating points, fixed now:** the VLMs' grounding score is decisive
(0 or 1), so YES = score >= 0.5. Grounding DINO: YES = box confidence >=
0.35, the model's published default `box_threshold`. A threshold fitted to
these frames would be a description, not a test; `@ 0 FP` is reported
beside it, marked as fitted.

**Criteria (written before measuring; CLAUDE.md section 7).** A candidate
is recommended only if it meets all of 1-6.

1. **Precision >= 95%** at its fixed operating point over the 299 frames.
2. **The teal bin:** 0 YES on the teal-bin subset.
3. **Recall >= 50%** of the visible frames (a fallback that confirms half
   of offline arrivals is worth building; below that it rarely fires).
4. **No worse than the cloud on precision:** precision >= Opus 4.5's
   recorded precision on the same 299 frames.
5. **Latency:** p90 <= 3.6 s a call on the Jetson at 15 W (the cloud step
   it would stand in for, ~3.6 s; it is one call per arrival).
6. **Memory:** resident memory <= 3.25 GB -- the 4253 MB MemAvailable
   measured with the whole stack running (3.37 / 3.33 criterion 6) less
   3.33's 1 GB floor. Weights that cannot fit at the precision available to
   this phase fail by arithmetic and are not loaded on the board.

**Measured 2026-10-09** (`python -m control.identity_eval`, rows in
`evaluations/identity-348/accuracy-299.json`; accuracy from P7's A10G fp32
records, 2026-09-11/12, relabelled against today's `labels.json`: 0 flips,
0 frames uncovered; 299 frames, 74 visible):

| model | gate | precision | recall | YES on the 34 teal-bin frames | @ 0 FP (fitted) |
|---|---|---|---|---|---|
| cloud: Opus 4.5 (recorded) | -- | 67.9% (72/106) | 97.3% (72/74) | 34/34 (the subset's definition) | 0.0% |
| **Qwen2.5-VL-3B** | 0.5 | **97.4% (38/39)** | **51.4% (38/74)** | **0/34** | 35.1% |
| InternVL3-2B | 0.5 | 97.4% (74/76) | 100.0% (74/74) | **1/34** | 5.4% (not separable) |
| Grounding DINO-tiny | 0.35 | 30.5% (74/243) | 100.0% (74/74) | 30/34 | 71.6% |

| criterion | Qwen2.5-VL-3B | InternVL3-2B | Grounding DINO-tiny |
|---|---|---|---|
| 1. precision >= 95% | **met** 97.4% | **met** 97.4% | failed 30.5% |
| 2. 0 YES on the teal bin | **met** 0/34 | failed 1/34 | failed 30/34 |
| 3. recall >= 50% | **met** 51.4% (by one frame) | **met** 100% | **met** 100% |
| 4. precision >= the cloud's 67.9% | **met** | **met** | failed |
| 5. p90 <= 3.6 s on the Jetson at 15 W | **not measured** (see 6) | not measured | not measured (already failed 1, 2, 4) |
| 6. resident <= 3.25 GB | **failed by arithmetic**: bf16 weights 7.51 GB (3,982,649,232 + 3,526,688,744 bytes), over the bar and nearly all of the board's 7.6 GB | failed by arithmetic (~2.1B parameters, ~4.2 GB at bf16) | not loaded |

For reference only, never against the robot's budget: A10G fp32 per frame
on these 299 frames -- Qwen2.5-VL-3B median 319 ms / p90 1680 ms,
InternVL3-2B 630 / 1368 ms, Grounding DINO-tiny 195 / 199 ms.

**No candidate meets all six, so no fallback is recommended as measured.**
Qwen2.5-VL-3B is the only one that passes on accuracy -- the first local
model measured here that beats the cloud on precision without saying yes to
the bin -- and it fails only on memory at the precision this phase could
load. The Jetson (idle, reachable, 2026-10-09) was not used: the bf16
weights cannot fit beside the stack, and a 4-bit build needs a download over
this phase's 1 GB limit.

**What would decide it (the user's call):** a 4-bit Qwen2.5-VL-3B (an AWQ or
GGUF build; size, runtime and accuracy unmeasured) on the Jetson, scored on
the same 299 frames against the same six criteria, because quantisation can
move answers (3.41: fp16 TensorRT moved CLIP by 0.052). Criterion 3 passes
by one frame, so a 4-bit build that loses two true positives fails it.

**Caveats, recorded rather than tuned away:**

* The 299 frames are whole walks, not arrival frames. At arrival the target
  is centred within 40 cm, so recall there is probably higher than 51.4%
  and the teal bin less likely to be in view; neither is measured.
* Opus's 34/34 on the teal-bin subset is true by construction; its row is
  there for its precision and recall.
* The cloud's recorded answers came from the navigation prompt, not the
  arrival-confirmation call, so its row is the cloud as the corpus recorded
  it, not `confirm_arrival()`.
