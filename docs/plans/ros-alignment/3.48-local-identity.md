# 3.48 A local identity check: can a small VLM on the Jetson confirm arrival?

*`PLAN-ros-alignment.md` section 3.48; index: [README.md](README.md).*

**Why.** Since handoff 1a a tiered mission ends `found` only on a cloud yes
at arrival, and since 3.47 a mission whose cloud never answers ends
`arrived_unconfirmed`. Idea 3 of the 2026-10-07 XPENG/Banma comparison
("on-device first, cloud-assisted"), approved by the user 2026-10-09: could
a model on the Jetson answer "is the target in this frame?" when the cloud is
unreachable, so an offline arrival can be confirmed locally? **This section
measures only.** Nothing is wired into the mission path; the answer decides
whether a later section builds it.

The costly error is a wrong YES -- it would turn a local false positive into
`found` on the wrong object. That is the failure this project has already
seen from a VLM: on the 209-frame search walk the cloud model (Opus 4.5)
claimed the blue bottle on 44 frames, 34 of them a teal storage bin (P3,
2026-09-07; `perception_eval.py`'s docstring).

**Candidates, and why these.** P5/P7 (`EDGE-PERCEPTION-BENCH.md`) already
scored small VLMs on this corpus on an A10G, scored by GROUNDING
(`P(it localises)`), not yes/no, because a VLM's yes/no is answerable from
prior (P(yes) 0.884 on a frame it would not box). Their per-frame records
are in `evaluations/gpu/`. A web check (2026-10-09) found the current small
VLMs benchmarked on an Orin Nano 8 GB are Qwen2-VL-2B / Qwen3-VL-2B-class
(e.g. Cosmos-Reason2-2B) through llama.cpp / TensorRT Edge-LLM; none is
already in the project, and any new VLM weights are over this phase's 1 GB
download limit.

1. **Qwen2.5-VL-3B-Instruct** -- the best small VLM at 0 false positives in
   P7 (42% on 610 frames); trained grounding; Apache-2.0; cached on the Mac.
2. **InternVL3-2B** -- the smaller VLM P7 measured (3% at 0 FP, 75% at 3).
3. **Grounding DINO-tiny** (not a VLM; the control) -- owned P7's
   zero-false-positive point (50%), ~170M parameters, under the download
   limit, and "a model that is never wrong is a better corroborator than one
   that is more often right" (P7).

**Frame set, pinned:** the four rig walks of 2026-09-07 --
`blue-bottle-20260907-142454` (33), `blue-bottle-20260907-185007` (209),
`blue-shoes-20260907-152528` (19), `red-backpack-20260907-144856` (38):
**299 frames**. Reference: each walk's CURRENT `labels.json` (never
`walk.jsonl`); where a stored record's `visible` disagrees with today's
label, today's label wins and the count is reported. The teal-bin subset:
the frames of `blue-bottle-20260907-185007` where Opus's recorded
`navigate.target_visible` is true and the label is false. Opus's recorded
answers come from each frame's `walk.jsonl` (`model_id`
`us.anthropic.claude-opus-4-5-20251101-v1:0`).

Accuracy is rescored from the A10G records (GPU, fp32; never merged with a
CPU or Jetson row, P24). Latency and memory are measured on the Jetson at
15 W on `tools/jetson/bench_frames.json`'s 60 timed frames (+3 warm-up).

**Operating points, fixed now:** the VLMs' grounding score is decisive
(0 or 1), so YES = score >= 0.5. Grounding DINO: YES = box confidence >=
0.35, the model's published default `box_threshold`. A threshold fitted to
these frames would be a description, not a test; `@ 0 FP` is reported
beside it, marked as fitted.

**Criteria (written before measuring; CLAUDE.md section 7).** A candidate
is recommended only if it meets all of 1-6.

1. **Precision >= 95%** at its fixed operating point over the 299 frames.
2. **The teal bin:** 0 YES on the teal-bin subset.
3. **Recall >= 50%** of the visible frames (a fallback that confirms half
   of offline arrivals is worth building; below that it rarely fires).
4. **No worse than the cloud on precision:** precision >= Opus 4.5's
   recorded precision on the same 299 frames.
5. **Latency:** p90 <= 3.6 s a call on the Jetson at 15 W (the cloud step
   it would stand in for, ~3.6 s; it is one call per arrival).
6. **Memory:** resident memory <= 3.25 GB -- the 4253 MB MemAvailable
   measured with the whole stack running (3.37 / 3.33 criterion 6) less
   3.33's 1 GB floor. Weights that cannot fit at the precision available to
   this phase fail by arithmetic and are not loaded on the board.

For reference only, never against the robot's budget: A10G fp32 per frame
on these 299 frames -- Qwen2.5-VL-3B median 319 ms / p90 1680 ms,
InternVL3-2B 630 / 1368 ms, Grounding DINO-tiny 195 / 199 ms.

**No candidate meets all six, so no fallback is recommended as measured.**
Qwen2.5-VL-3B is the only one that passes on accuracy -- the first local
model measured here that beats the cloud on precision without saying yes to
the bin -- and it fails only on memory at the precision this phase could
load. The Jetson (idle, reachable, 2026-10-09) was not used: the bf16
weights cannot fit beside the stack, and a 4-bit build needs a download over
this phase's 1 GB limit.

**What would decide it (the user's call):** a 4-bit Qwen2.5-VL-3B (an AWQ or
GGUF build; size, runtime and accuracy unmeasured) on the Jetson, scored on
the same 299 frames against the same six criteria, because quantisation can
move answers (3.41: fp16 TensorRT moved CLIP by 0.052). Criterion 3 passes
by one frame, so a 4-bit build that loses two true positives fails it.

**Caveats, recorded rather than tuned away:**

* The 299 frames are whole walks, not arrival frames. At arrival the target
  is centred within 40 cm, so recall there is probably higher than 51.4%
  and the teal bin less likely to be in view; neither is measured.
* Opus's 34/34 on the teal-bin subset is true by construction; its row is
  there for its precision and recall.
* The cloud's recorded answers came from the navigation prompt, not the
  arrival-confirmation call, so its row is the cloud as the corpus recorded
  it, not `confirm_arrival()`.

also evaluate other models like the Nvidia Nemotron and a few more along
with Qwen2.5". Downloads up to ~5 GB a model are approved for this.

**The runtime changes, the criteria do not.** Every candidate below runs
as it would on the car: **llama.cpp (`llama-server`, CUDA, built from
source in the home directory on the Jetson, no system packages changed)
at 15 W**, as a GGUF. So accuracy, latency and memory are all measured on
the Jetson, for every candidate, in the quantisation it would ship in.
These rows are Jetson rows and are never merged with the A10G rows above
(P24). Re-measuring Qwen2.5-VL-3B this way also shows what quantising it
moves, against its A10G row.

**Considered and failing criterion 6 by arithmetic (not downloaded, not
loaded -- the same rule as the bf16 rows above):**

* **NVIDIA Nemotron VL.** The smallest is Llama-3.1-Nemotron-Nano-VL-8B-V1;
  then Nemotron-Nano-12B-v2-VL and Nemotron 3 Nano Omni (30B-A3B, listed
  for Jetson Thor and AGX Orin 64 GB only). The 8B's only 4-bit build with
  its vision tower is 7.37 GB (MLX, vision unquantised) -- over the 3.25 GB
  bar and nearly the board's 7.6 GB. The one 8B GGUF published
  (`forkjoin-ai/...nemotron-nano-vl-8b-v1-gguf`, 4.92 GB) is the text-only
  Nemotron Nano 8B with no vision projector, so it cannot answer this
  question at all.
* **Gemma-3-4B-it:** Q4_K_M 2.49 GB + mmproj f16 0.85 GB = 3.34 GB of
  weights, over the 3.25 GB bar before a KV cache.

**Protocol, fixed now.** The prompt is `VlmDetector._locate()`'s,
verbatim. The score is the same quantity as the VLM rows above, P(it
localises): at the token after the first `[` the model generates, the
probability of `{` (a box follows) over `{` + `]` (empty), read from the
chat-completions API's `top_logprobs` (20); a token outside the top 20
counts as 0. Greedy, `max_tokens` 64. A reply with no `[` within 64 tokens
scores 0 (counted and reported). The frame JPEG is sent as-is; llama.cpp
does its own resizing (the A10G rows used a 921,600-pixel cap -- a
difference recorded, not corrected). YES = score >= 0.5 for every
candidate, as for the VLM rows.

**Criteria 1-6 apply unchanged** (the pinned 299 frames, today's
`labels.json` -- identical on the Jetson, md5-checked -- the same bars).
How 5 and 6 are taken on this runtime, fixed now: **5** is the p90 of the
299 end-to-end HTTP calls (image encode included), a superset of
`bench_frames.json`'s 60; **6** is the drop in `MemAvailable` from before
the server starts to its lowest point during the 299-frame run, sampled
every second, against 3.25 GB.

## Amendment 2, 2026-10-09 (after a one-walk smoke test, before the measured runs)

A smoke test (Qwen2.5-VL-3B, `blue-shoes`, 19 frames; not a measurement and
not reported as one) showed the scorer reading the wrong step: the model
boxed the shoes correctly (`[257, 160, 379, 250]`) but scored 0.53, because
it wrote `[`, then a whitespace token (`\t`), then `{"`, and the scorer
took the whitespace step as the decision. **Correction:** whitespace-only
tokens defer the decision the way a bare `[` does -- at each such step the
mass on `{` and `]` is taken there, and the whitespace mass carries forward
to the next generated step (`p_localised`, pinned by a test). The prompt,
the gate (0.5), the frames and the criteria are unchanged.

**Also reported, never as criterion 5:** the time to the decision token,
from llama-server's own timings (`prompt_ms` plus per-token generation time
up to and including the token that decided). Criterion 5 stays the
end-to-end call with `max_tokens` 64, as fixed in amendment 1; the smoke
test put that at ~5.7 s for Qwen2.5-VL-3B (2.7 s prompt and image, then
13 tokens/s), so this second number is what a deployment that stopped at
the decision would cost, recorded so the next section need not re-measure.

Recorded, not changed: llama.cpp warns that Qwen-VL "requires at minimum
1024 image tokens ... on grounding tasks"; a 640x480 frame gives ~400,
which is also what the A10G rows saw at native resolution (their
921,600-pixel cap is above it), so both rows ask the same question.
Context is 4096 for every candidate (the KV cache at that length is ~0.15
GB for a 3B model; not a lever on criterion 6).

**From `/code-review` of this amendment, also before any measured run:** a
reply that opens a bare object before any list (`{"bbox_2d": [...]}`) is a
box answered outside the asked-for list; the first `[` in it is the
coordinate list, which the scorer would have read as "absent". Such a reply
is now scored at its opening step -- a box opening (`{`, `[{`) against an
empty list (`[]`) -- and counted per model (`object_replies`). A failed
call is recorded as one unavailable frame (a miss when the target is
visible) rather than losing the run, and counted (`errors`).

## Amendment 3, 2026-10-09 (after the first measured runs failed as runs, before the re-run)

The first runs of all five candidates (llama.cpp `e60eff9`) are **void,
not results**: on four of them the kernel's OOM killer killed
`llama-server` part-way (`MemAvailable` fell to 4-15 MB; 125-231 of 299
calls failed). The cause is the harness, not the models: this llama.cpp's
`llama-server` keeps a host-RAM prompt cache, **8192 MiB by default**
(`--cache-ram`), and on the Jetson host RAM is the GPU's memory. Every
frame's image prompt was cached and none is ever reused (no two frames
match), so memory grew frame by frame until the kill. A deployed arrival
check asks once per arrival and would never cache unrelated frames.
**Correction:** `--cache-ram 0` for every candidate, recorded in each run's
config. All five are re-run, LFM2-VL included -- its first run completed,
but its memory figure carried the same growth. Nothing else changes: the
frames, prompt, scorer (`b3a589b`), gate and criteria are as before. The
void runs stay on the board (`~/bench-348/out-void/`) and are not scored.
