# 3.80 Tiered identity: perception, then local Qwen, then the cloud

*`PLAN-ros-alignment.md` section 3.80; index: [README.md](README.md).*

**Why.** The user, 2026-10-13: "The ultimate goal is to replace the cloud
VLM with Qwen running locally on the rover. I want it to be tiered,
starting with perception first, and if perception is unable to answer the
question or identify the object, then it gets sent to the local Qwen
model, and if that's unable to answer or identify, then, beyond a certain
number of failures, it gets sent over to the cloud VLM [...] which then
resolves it."

**What 3.78 established for the middle tier** (Jetson, JetPack 6.2.1, 15 W):

* Qwen2.5-VL-3B is the only local model that meets 3.48's accuracy bars.
  Qwen3-VL-4B and Qwen3.5-4B say YES on almost every look-alike frame.
* Under TensorRT Edge-LLM v0.9.1 it decides in **1.13 s p90 idle** and
  **1.41 s p90 beside the whole robot stack** (3.78.F).
* On the identity question it is **more precise than the cloud**: 97.2%
  against Opus 4.5's 67.9% on the same 299 frames. So the cloud must not
  simply overrule a confident local answer. It resolves what the local
  tiers *cannot answer*, not what they answered and the cloud would
  answer differently.
* **Memory: settled 2026-10-14.** The user set the floor at **0.5 GB**,
  with the VLM killed first. The shrunk engine **VE** (reduced vocabulary
  17,920 + FP8 embedding) leaves **606 MB** free beside the whole stack
  (median 635), decides in **1.32 s p90** under load, and keeps 3.48's
  accuracy (97.2% precision, 94.6% recall). VE is this section's local
  model. Its margin above the floor is about 100 MB; 3.81 wins memory
  back.

## How the tiers work today (read 2026-10-13)

* **Every frame:** `brain/tiered.py` `TieredVision.__call__` (689-750)
  runs YOLOE + CLIP (`brain/perceive.py` `perceive`, 871-947; gate P >=
  0.8). The result is detected, absent or unavailable.
* **The cloud is called on triggers** (`_trigger_for`, 959-1015):
  * `mission_start`;
  * `candidate_sighting` (`tier_consecutive_frames` = 2);
  * `cold_search` (`tier_cold_search_after` = 6);
  * `staleness` (`tier_stale_after` = 8).

  It is asynchronous, with one call in flight (`tier_async_cloud`). A
  frame whose status is unavailable never triggers.
* **At arrival:** `brain/arrival.py` holds the lidar rule (2 frames,
  <= 0.40 m, centred). `brain/agent.py` `_confirm_identity` (315-349) then
  makes one cloud identity call (`TieredVision.confirm_arrival`, 786-826,
  guarded by `arrival_confirm_timeout_s` 8 s in `_guarded_confirm`,
  `control/mission_runner.py` 1122-1180).
  * The cloud's yes gives `found`.
  * Its no gives REFUSED until the arrival ends.
  * `CloudUnavailable` gives `arrived_unconfirmed` (3.47), and 3.53's
    late re-ask follows.
* **Failures:** `max_vision_failures` = 3 (B3.2) counts consecutive failed
  ticks, and is reset by any success.

## The design (for the user to confirm)

Three tiers. Each one answers or **escalates**; nothing below the cloud
waits on the cloud.

1. **Perception (YOLOE + CLIP, every frame), as today.** It *escalates* a
   frame to the local VLM when:
   * a candidate is in the **uncertain band**, CLIP P in [`tier_local_band_low`,
     0.8);
   * the target is **out of vocabulary** for YOLOE (the OOV path that
     already lengthens `cold_search`);
   * any of today's cloud triggers fires (`mission_start`,
     `candidate_sighting`, `cold_search`, `staleness`): each is sent to
     the local VLM first.
2. **Local Qwen** (Qwen2.5-VL-3B, 3.78's VE engine under TensorRT, its own
   process on the Jetson, resident). It answers the escalated question:
   * **Identity at arrival:** the 3.48 question. It replaces the cloud's
     first call. Score >= 0.5 is YES (`found`). A score <=
     `tier_local_no_below` is a confident NO (REFUSED, as the cloud's no
     is today).
   * **Sightings:** "is the target in this frame, and where" (the same
     prompt, which returns a box).

   It counts as **unable** when its score is in the uncertain band between
   `tier_local_no_below` and 0.5, when the reply does not parse, when it
   times out (`tier_local_timeout_s`), or when the process is gone.
3. **The cloud** (today Opus 4.5 on Bedrock, `/navigate`). It is called
   only after **`tier_local_max_unable` consecutive unable answers** from
   the local VLM for the same question, or when the local VLM is absent.
   When it is reached, its answer still carries the direction it gives
   today (the action the tiered policy holds).

**The order is strict (the user, 2026-10-14):** "Perception sends the
request in this order: 1. YOLOE + CLIP, 2. Local Qwen, 3. Cloud VLM."
* No trigger goes to the cloud directly. Today's four cloud triggers
  (`mission_start`, `candidate_sighting`, `cold_search`, `staleness`) and
  the arrival confirmation all go to local Qwen first.
* The cloud is reached only through tier 2: after
  `tier_local_max_unable` unable answers, or when the local VLM is
  absent (killed, not started, or timed out).
* **Consequence:** the cloud's navigation direction arrives only on an
  escalation, so between escalations the robot steers by perception's
  bearing and explore, as it already does while a call is in flight.
  Criterion 2's progress half (the `found` rate not lower) is what
  guards this.

**The cloud model is a setting, not part of this design.** The user named
"GPT Astra or Opus 5.5".
* This account reaches Anthropic models through Bedrock. Fable 5.1 answers
  only from us-east-1 (CLAUDE.md section 6).
* An OpenAI model is a separate integration, not available today.
* Any new model id is confirmed with one real call carrying a real frame
  (CLAUDE.md section 6). That is a Bedrock call, so it needs the user's
  yes and a cost estimate first.

**Process and memory.**
* The local VLM runs as its own service (the 3.78 `edgellm_identity`
  driver behind a small HTTP front), never inside the robot server or the
  brain.
* `oom_score_adj` makes it the first thing the kernel kills (+1000) and
  protects the robot server (-1000). A killed VLM is "absent": tier 3
  takes over and the robot keeps driving.
* The floor is 0.5 GB (the user, 2026-10-14).

## Criteria (written before building; approved by the user 2026-10-14)

Measured through the real mission path (CLAUDE.md section 7), on the
Jetson:

1. **Identity at arrival:** on the pinned 299 frames, the tiered answer
   (local, escalating to the cloud by the rules above) has precision >=
   95% and recall >= 85%. The cloud's escalations are counted, and paid
   for only with the user's yes.
2. **Cloud calls per mission** fall by >= 80% against today's tiered
   policy, on the same simulated missions (`home_first_floor` and 20
   ProcTHOR houses, fixed seeds), **with the `found` rate not lower**
   (the progress half, section 7.4).
3. **Arrival latency:** time from the lidar arrival to the identity
   verdict, p90 <= 2.0 s when the local tier answers (today the 8 s cloud
   deadline).
4. **Offline:** with the network refused, a mission whose target is
   present ends `found` through the local tier, not `arrived_unconfirmed`
   (3.47's end state stays for a local VLM that is absent or unable).
5. **Failure isolation:** with the VLM process killed mid-mission (a
   drill), the wheel loop has 0 late ticks, the mission continues, and
   the next escalation goes to the cloud. The robot server and the brain
   survive.
6. **Memory:** the loaded window (3.78.F) with the VLM resident holds
   `MemAvailable` above 0.5 GB, and the OOM-kill drill (5)
   names the VLM, never the robot server.

**Thresholds (approved by the user 2026-10-14):**
* `tier_local_band_low`: 0.5;
* `tier_local_no_below`: 0.1;
* `tier_local_max_unable`: 2;
* `tier_local_timeout_s`: 3.0, against VE's 1.32 s p90 under load.
