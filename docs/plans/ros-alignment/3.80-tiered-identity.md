# 3.80 Tiered identity: perception, then local Qwen, then the cloud

*`PLAN-ros-alignment.md` section 3.80; index: [README.md](README.md).*

**Why.** The user, 2026-10-13: "The ultimate goal is to replace the cloud
VLM with Qwen running locally on the rover. I want it to be tiered,
starting with perception first, and if perception is unable to answer the
question or identify the object, then it gets sent to the local Qwen
model, and if that's unable to answer or identify, then, beyond a certain
number of failures, it gets sent over to the cloud VLM [...] which then
resolves it."

**What 3.78 established for the middle tier** (Jetson, JetPack 6.2.1, 15 W):

* Qwen2.5-VL-3B is the only local model that meets 3.48's accuracy bars.
  Qwen3-VL-4B and Qwen3.5-4B say YES on almost every look-alike frame.
* Under TensorRT Edge-LLM v0.9.1 it decides in **1.13 s p90 idle** and
  **1.41 s p90 beside the whole robot stack** (3.78.F).
* On the identity question it is **more precise than the cloud**: 97.2%
  against Opus 4.5's 67.9% on the same 299 frames. So the cloud must not
  simply overrule a confident local answer. It resolves what the local
  tiers *cannot answer*, not what they answered and the cloud would
  answer differently.
* **Memory: settled 2026-10-14.** The user set the floor at **0.5 GB**,
  with the VLM killed first. The shrunk engine **VE** (reduced vocabulary
  17,920 + FP8 embedding) leaves **606 MB** free beside the whole stack
  (median 635), decides in **1.32 s p90** under load, and keeps 3.48's
  accuracy (97.2% precision, 94.6% recall). VE is this section's local
  model. Its margin above the floor is about 100 MB; 3.81 wins memory
  back.

## How the tiers work today (read 2026-10-13)

* **Every frame:** `brain/tiered.py` `TieredVision.__call__` (689-750)
  runs YOLOE + CLIP (`brain/perceive.py` `perceive`, 871-947; gate P >=
  0.8). The result is detected, absent or unavailable.
* **The cloud is called on triggers** (`_trigger_for`, 959-1015):
  * `mission_start`;
  * `candidate_sighting` (`tier_consecutive_frames` = 2);
  * `cold_search` (`tier_cold_search_after` = 6);
  * `staleness` (`tier_stale_after` = 8).

  It is asynchronous, with one call in flight (`tier_async_cloud`). A
  frame whose status is unavailable never triggers.
* **At arrival:** `brain/arrival.py` holds the lidar rule (2 frames,
  <= 0.40 m, centred). `brain/agent.py` `_confirm_identity` (315-349) then
  makes one cloud identity call (`TieredVision.confirm_arrival`, 786-826,
  guarded by `arrival_confirm_timeout_s` 8 s in `_guarded_confirm`,
  `control/mission_runner.py` 1122-1180).
  * The cloud's yes gives `found`.
  * Its no gives REFUSED until the arrival ends.
  * `CloudUnavailable` gives `arrived_unconfirmed` (3.47), and 3.53's
    late re-ask follows.
* **Failures:** `max_vision_failures` = 3 (B3.2) counts consecutive failed
  ticks, and is reset by any success.

## The design (for the user to confirm)

Three tiers. Each one answers or **escalates**; nothing below the cloud
waits on the cloud.

1. **Perception (YOLOE + CLIP, every frame), as today.** It *escalates* a
   frame to the local VLM when:
   * a candidate is in the **uncertain band**, CLIP P in [`tier_local_band_low`,
     0.8);
   * the target is **out of vocabulary** for YOLOE (the OOV path that
     already lengthens `cold_search`);
   * any of today's cloud triggers fires (`mission_start`,
     `candidate_sighting`, `cold_search`, `staleness`): each is sent to
     the local VLM first.
2. **Local Qwen** (Qwen2.5-VL-3B, 3.78's VE engine under TensorRT, its own
   process on the Jetson, resident). It answers the escalated question:
   * **Identity at arrival:** the 3.48 question. It replaces the cloud's
     first call. Score >= 0.5 is YES (`found`). A score <=
     `tier_local_no_below` is a confident NO (REFUSED, as the cloud's no
     is today).
   * **Sightings:** "is the target in this frame, and where" (the same
     prompt, which returns a box).

   It counts as **unable** when its score is in the uncertain band between
   `tier_local_no_below` and 0.5, when the reply does not parse, when it
   times out (`tier_local_timeout_s`), or when the process is gone.
3. **The cloud** (today Opus 4.5 on Bedrock, `/navigate`). It is called
   only after **`tier_local_max_unable` consecutive unable answers** from
   the local VLM for the same question, or when the local VLM is absent.
   When it is reached, its answer still carries the direction it gives
   today (the action the tiered policy holds).

**The order is strict (the user, 2026-10-14):** "Perception sends the
request in this order: 1. YOLOE + CLIP, 2. Local Qwen, 3. Cloud VLM."
* No trigger goes to the cloud directly. Today's four cloud triggers
  (`mission_start`, `candidate_sighting`, `cold_search`, `staleness`) and
  the arrival confirmation all go to local Qwen first.
* The cloud is reached only through tier 2: after
  `tier_local_max_unable` unable answers, or when the local VLM is
  absent (killed, not started, or timed out).
* **Consequence:** the cloud's navigation direction arrives only on an
  escalation, so between escalations the robot steers by perception's
  bearing and explore, as it already does while a call is in flight.
  Criterion 2's progress half (the `found` rate not lower) is what
  guards this.

**The cloud model is a setting, not part of this design.** The user named
"GPT Astra or Opus 5.5".
* This account reaches Anthropic models through Bedrock. Fable 5.1 answers
  only from us-east-1 (CLAUDE.md section 6).
* An OpenAI model is a separate integration, not available today.
* Any new model id is confirmed with one real call carrying a real frame
  (CLAUDE.md section 6). That is a Bedrock call, so it needs the user's
  yes and a cost estimate first.

**Process and memory.**
* The local VLM runs as its own service (the 3.78 `edgellm_identity`
  driver behind a small HTTP front), never inside the robot server or the
  brain.
* `oom_score_adj` makes it the first thing the kernel kills (+1000) and
  protects the robot server (-1000). A killed VLM is "absent": tier 3
  takes over and the robot keeps driving.
* The floor is 0.5 GB (the user, 2026-10-14).

## Criteria (written before building; approved by the user 2026-10-14)

Measured through the real mission path (CLAUDE.md section 7), on the
Jetson:

1. **Identity at arrival:** on the pinned 299 frames, the tiered answer
   (local, escalating to the cloud by the rules above) has precision >=
   95% and recall >= 85%. The cloud's escalations are counted, and paid
   for only with the user's yes.
2. **Cloud calls per mission** fall by >= 80% against today's tiered
   policy, on the same simulated missions (`home_first_floor` and 20
   ProcTHOR houses, fixed seeds), **with the `found` rate not lower**
   (the progress half, section 7.4).
3. **Arrival latency:** time from the lidar arrival to the identity
   verdict, p90 <= 2.0 s when the local tier answers (today the 8 s cloud
   deadline).
4. **Offline:** with the network refused, a mission whose target is
   present ends `found` through the local tier, not `arrived_unconfirmed`
   (3.47's end state stays for a local VLM that is absent or unable).
5. **Failure isolation:** with the VLM process killed mid-mission (a
   drill), the wheel loop has 0 late ticks, the mission continues, and
   the next escalation goes to the cloud. The robot server and the brain
   survive.
6. **Memory:** the loaded window (3.78.F) with the VLM resident holds
   `MemAvailable` above 0.5 GB, and the OOM-kill drill (5)
   names the VLM, never the robot server.

**Thresholds (approved by the user 2026-10-14):**
* `tier_local_band_low`: 0.5;
* `tier_local_no_below`: 0.1;
* `tier_local_max_unable`: 2;
* `tier_local_timeout_s`: 3.0, against VE's 1.32 s p90 under load.

## 3.80.B: the local VLM service (written 2026-10-14, before building)

**Shape.** `service/local_vlm/` runs 3.78's `edgellm_identity` driver with
VE's engines resident, behind a small FastAPI app on `127.0.0.1:8005`
(`LOCAL_VLM_PORT`). It asks exactly what 3.78 measured: the same prompt
(`bench_identity_llama.PROMPT`), the same request file
(`bench_identity_trt.request_doc`), the same stop at the deciding token
(`decision_reached`) and the same score (`p_localised`), imported, not
copied. The brain applies 3.80's thresholds (3.80.C); the service returns
the raw score.

* `POST /identity` `{image_b64, target, deadline_s}` (secret-gated as the
  other servers are). Status `answered` with `score`, or one of the
  *unable* statuses: `timeout` (the deadline passed: the driver is sent
  `C`, and stays usable), `unparsed` (the reply never opened a list),
  `busy` (the one runtime was held past the deadline), `error` (the
  driver refused the request). **503** means the VLM is *absent*.
* `GET /health` (open): ready, alive, the engine dir, requests served.
* One request at a time: the next request file is written to the driver
  only after the previous one's end line. A reply returns at the deciding
  token or the deadline; the cancelled tail is drained behind it (review,
  2026-10-14: the driver sees a cancel only between tokens, so without
  this a deadline inside the ~1 s prefill could not be kept).
* If the driver dies (an OOM kill), the service exits non-zero and
  systemd restarts it after 30 s, at most 3 times in 15 min; then the
  unit stays failed and the VLM is absent until a person starts it.
* `tools/jetson/systemd/picar-local-vlm.service`: `OOMScoreAdjust=1000`.
  **Deviation from the design above:** an unprivileged process cannot
  lower its own `oom_score_adj`, so the robot server alone cannot be set
  to -1000. Instead `picar-stack` gets `OOMScoreAdjust=-900` for the whole
  stack (robot server, brain, simulated body, proxy): never killed before
  the VLM or anything else, but still killable if it is itself the leak.
* **Who kills (checked on the board 2026-10-14):** the kernel's OOM
  killer, which honours `oom_score_adj`. `systemd-oomd` (which ignores it
  and kills by cgroup pressure) is enabled but never starts: the L4T
  kernel has no `/proc/pressure/memory`. `dockerd` runs at -500 and the
  ROS container at 0, both below the VLM.
* The unit is installed but **not enabled at boot** until 3.80.C wires the
  brain to it: other sessions' benches stop `picar-stack` and
  `picar-ngrok`, and a resident 4 GB VLM they do not know about would
  change their numbers. `tools/jetson/README.md` says to stop it too.

**Acceptance (on the board, 15 W, desktop and the twin's units off):**

* **B1, same answers:** the 299 frames through `POST /identity` score
  within 0.01 of 3.78's VE idle records (`evaluations/identity-378/V/`) on
  every frame, with 0 decisions flipped at 0.5.
* **B2, little overhead:** p90 of the HTTP round trip <= VE's idle p90 +
  0.10 s.
* **B3, same memory:** the `MemAvailable` drop with the service resident is
  within 100 MB of VE's (4.05 GB).
* **B4, OOM order:** `oom_score_adj` is 1000 for the service and its
  driver, -900 for every `picar-stack` process.
* **B5, death:** after `kill -9` of the driver, `/health` stops answering
  within 2 s, systemd restarts the service and it answers again; a fourth
  death within 15 min leaves the unit failed.
* **B6, deadline:** a request with `deadline_s` 0.3 returns `timeout`
  within 0.8 s, and the next request answers with the score B1 expects.
* Laptop: the suite covers the service against a fake driver that speaks
  the same protocol (answered, cancel at the decision, timeout, busy,
  unparsed, error, death, secret).

## 3.80.C: arrival identity through the local tier (written 2026-10-14, before building)

**Shape.** `TieredVision.confirm_arrival` asks the local VLM service
first, through a small client (`brain/local_vlm.py`), and the cloud only
as the design above says. One tier per tick: a tick asks the local VLM
*or* the cloud, so the arrival tick's deadline is never the sum of both.

* **Local yes** (score >= 0.5): confirmed, `found`, no cloud call.
* **Local no** (score <= `tier_local_no_below`): refused for the rest of
  the arrival, as the cloud's no is today. No cloud call.
* **Unable** (score in between, `unparsed`, `timeout`, `busy`, `error`, or
  the client's own timeout): a new arrival state, **`checking`**. Not
  refused: the next arrival frame asks again. After
  `tier_local_max_unable` unable answers in one arrival, the next arrival
  frame asks the cloud, as today.
* **Absent** (connection refused, 503): the cloud is asked on the same
  frame (an absent answer is instant, so one deadline still covers it).
* The cloud's answer, its errors and 3.47's `arrived_unconfirmed` path are
  unchanged. The 3.53 late re-ask stays cloud-only: it exists because the
  cloud was unreachable after the local tier could not decide.
* The local tier's count of unable answers starts again with each arrival
  (the agent tells the policy when an arrival stops holding).
* The client's HTTP timeout is `tier_local_timeout_s` plus the tail B6
  measured (2 s), under the runner's confirmation guard.
* **Off by default:** `tier_local_vlm_url` empty (env `LOCAL_VLM_URL`).
  Until 3.80.E measures it on the board, a mission behaves as before.
* The status says which tier answered (`identity.tier`: `local` or
  `cloud`), and the tier stats count local calls, their answers and the
  escalations, so 3.80.E can count cloud calls saved.

**Acceptance (laptop, before 3.80.E's board measurements):**

* **C1** local yes: `found`, 0 cloud calls at arrival.
* **C2** local no: refused, 0 cloud calls, not asked again in that
  arrival.
* **C3** unable: `checking`, asked again next frame; after 2 unable
  answers the cloud is asked on the next frame, and its answer decides.
  Each unable kind (band, unparsed, timeout, busy, error, client
  timeout) is tested.
* **C4** absent (refused connection, 503): the cloud is asked on the
  same frame.
* **C5** offline: local yes with the cloud unreachable ends `found`;
  local absent or unable with the cloud unreachable ends
  `arrived_unconfirmed` (3.47 unchanged).
* **C6** a new arrival starts the unable count again.
* **C7** with `tier_local_vlm_url` empty, every existing test passes
  unchanged, and no local call is made.
* **C8** live: one tiered mission in the simulator through the brain's
  HTTP API, with the real `service/local_vlm` app on a fake driver that
  says yes, ends `found` with the identity from the local tier and no
  cloud call at arrival.

Tests: `tests/test_tiered_local.py` (40), two UI tests (the arrival row names
the tier; `checking` on the panel), phone screenshot
`evaluations/tiered-380/C/380C-arrival-local.png`.

**Reviews.** `/code-review` (three rounds) and the bug pass (two rounds)
found 12 real defects in the first cut and its fixes, all fixed with a test
that fails without the fix. The ones that mattered:
* a local check that used up a short deadline (a drill's 2 s) was charged
  to the cloud as an outage, ending `arrived_unconfirmed` with the cloud
  never asked: the local call now gets part of the step and counts unable;
* a Stop during the local check went on to a paid cloud call;
* a flickering arrival reset the local tries every frame, so an
  undecidable target never reached the cloud;
* a local check still out was joined by a second request, and a late
  answer could be counted twice or credited to the wrong call (calls now
  carry ids, reserved before their thread starts).

**The driver, from 3.78's bug pass** (`edgellm_identity.cpp`): a runtime
failure before the first token left the stream open and `consume()` waited
for ever (Edge-LLM's `handleRequest` returns early before attaching its
finaliser); an exception in the worker thread ended the process; the
runtime's INFO log shared stdout with the protocol. Rebuilt on the board and
3.80.B's acceptance re-run at `913a3bf` (`evaluations/tiered-380/C/driver/`):
B1 299 of 299 within 0.01 of both 3.78's VE records and 3.80.B's, 0 flips;
B2 p90 1.170 s (bar 1.175); B3 4,071 MB; B5 health gone in 1.0-1.6 s,
restarted 3 times, failed after the 4th; B6 timeout at 0.31 s. The one frame
3.80.B recorded `unparsed` (score 0, as in 3.78) now answers, score 0.

**Known limits.**
* After a cloud refusal, a flicker of one or two frames clears the agent's
  refusal while the local tier's tries stay spent, so the next arrival frame
  asks the cloud again (paid). Pre-3.80 paid on every flicker too.
* A local call that never returns (a server trickling bytes under httpx's
  per-phase timeout) keeps the local tier busy: each later arrival spends two
  frames, then asks the cloud.
* A brain whose `LOCAL_VLM_URL` is not on this machine sends no secret unless
  `LOCAL_VLM_SECRET` is set (the shared secret also gates the robot).

## 3.80.D: per-frame escalation through the local tier (written 2026-10-14, before building)

**Shape.** Every question a frame raises goes to the local VLM first, on the
one worker `tier_async_cloud` already uses (one question in flight, either
tier). Nothing in `brain/perceive.py` changes: perception already returns
every candidate's CLIP P on an absent frame, and the vocabulary verdict is
already read at mission start. With `tier_local_vlm_url` empty nothing below
exists and a mission behaves as before.

* **The questions** (each a trigger, counted by name):
  * today's four, `mission_start`, `candidate_sighting`, `cold_search`,
    `staleness`, with their pacing unchanged;
  * **`uncertain_band`**: perception absent, its best candidate's P in
    [`tier_local_band_low` 0.5, 0.8), for `tier_consecutive_frames` frames
    in a row. Asked once per run of band frames; a run broken by any other
    frame arms it again;
  * **`out_of_vocabulary`**: the target has no COCO word
    (`Vocabulary.in_vocabulary` false) and perception has been absent for
    `tier_consecutive_frames` frames. Local questions cost no money, so an
    out-of-vocabulary search asks the local VLM about as often as it can
    answer; `cold_search` stays for the in-vocabulary case.
* **The question** is 3.48's prompt, with the service asked to keep decoding
  after a yes until the box closes (`POST /identity` `box: true`). A no
  (`[]`) ends at the deciding token as before. A deadline that falls after
  the decision returns the score with no box.
* **Answers:**
  * **yes** (score >= 0.5) with a box: the box centre gives a bearing (the
    camera's field of view, plus the frame's pan), corrected by the turn the
    odometry measured since the frame was taken. The robot turns by it once
    and then holds FORWARD until a newer answer. A yes with no box changes
    no direction. Perception's own measured bearing still steers first.
  * **no** (score <= 0.1): answered; no cloud call; a FORWARD held from an
    earlier local yes is dropped.
  * **unable** (the band between, `unparsed`, `timeout`, `busy`, `error`,
    the client's timeout): the question stays open. The pacing counts are
    not reset and the candidate edge is armed again, so the same question is
    asked on the next frame that still raises it. After
    `tier_local_max_unable` (2) unable answers in a row, across questions,
    the next question goes to the cloud; a decided local answer or a cloud
    call starts the count again.
  * **absent** (refused connection, 503, a fault in the client): the cloud
    is asked about the same frame on the same dispatch.
* **Money:** `cloud_calls` counts only calls that reached the cloud, by
  trigger as before; `tier_max_calls` caps those only. The stats add the
  local questions by trigger, their answers, and the escalations by reason
  (`unable`, `absent`). B3.2 counts only cloud failures; a local failure is
  never a mission failure.
* A Stop (the epoch) during a local question sends no cloud call after it,
  and its late answer is dropped.

**Acceptance (laptop; D10 on the board in 3.80.E):**

* **D1** band: a P in [0.5, 0.8) on 2 frames asks the local VLM, never the
  cloud first; P 0.49 or 0.8 does not; asked once per run; a broken run
  arms it again.
* **D2** out of vocabulary: with the local tier on, 2 absent frames ask the
  local VLM; an in-vocabulary target keeps `cold_search`'s bar.
* **D3** each of today's four triggers goes to the local VLM first: 0 cloud
  calls when it answers yes or no.
* **D4** unable: asked again on the next frame that raises it; after 2 in a
  row the cloud is asked, and its answer is applied as today; a decided
  answer between resets the count. Each unable kind is tested.
* **D5** absent: the cloud on the same dispatch, counted once with its
  trigger; the call cap still holds.
* **D6** a yes with a box turns the robot toward the box's bearing (corrected
  for a turn made while the question was out), then FORWARD; a yes with no
  box and a no change no direction; a no drops a held local FORWARD.
* **D7** one question in flight across both tiers; a Stop during a local
  question sends no cloud call; a late answer after a Stop is not applied;
  a cloud failure after an escalation reaches B3.2 as today.
* **D8** off by default: `tier_local_vlm_url` empty, every existing test
  passes unchanged and no local call is made.
* **D9** the service with `box: true`, against the fake driver: a yes

* **D10** (board, measured in 3.80.E): on the pinned 299 frames, `box: true`

## 3.80.F: the local tiers steer (written 2026-10-16, before building)

**The problem (criterion 2's failure).** YOLOE + CLIP and Qwen point at a
target in view; neither says where to look for one out of view. The cloud's
FORWARD/LEFT/RIGHT was the search. With the local tier answering, nothing
chose where to go, and 19 of 21 missions turned in place to the limit.

**The user's choice (2026-10-16, superseding the explore-driven draft
committed the same day):** "Option 1 + see if you could add steering logic
to the YOLOE + CLIP tier as well." Option 1: the local Qwen gives the search
direction, asked the cloud's question and held as the cloud's answer is
held; explore is not used.

**F-a, Qwen's direction.**
* The local VLM service gains `POST /direction` `{image_b64, target,
  deadline_s}`: the same driver, a second prompt asking for ONE word,
  `left`, `right` or `forward`, the robot's next move toward the target
  (the cloud's question 5, without the JSON). It stops at the first
  generated token. The answer is the option with the most probability
  among the first token's top 20 alternatives, any token that is a
  prefix of one option counting toward it (`f`, `for`, `forward`...).
  `p` is that option's share of the three; `mass` is the three's total.
  Status `answered` with `direction`, `p`, `mass`; *unable* when `mass` <
  0.5 (`unparsed`) or on `timeout`/`busy`/`error`; 503 absent, as
  `/identity`.
* `brain/tiered.py`: a search trigger (`mission_start`, `cold_search`,
  `staleness`) put to the local tier asks the sighting question as
  3.80.D does; when that does not say yes, the worker asks the direction
  question about the same frame. A direction answer is held as a cloud
  goal is (`_held_direction`, under `tier_hold_goal`), until a newer
  answer. A direction question that is unable counts as unable for the
  escalation rule (`tier_local_max_unable` in a row, then the cloud). The
  candidate, band and out-of-vocabulary triggers are unchanged.
* `brain.tier_local_direction` (env `TIER_LOCAL_DIRECTION`), default
  `true`; it does nothing while the local tier is off (no URL). `false`
  is 3.80.D's behaviour (the 2026-10-15 local arm).

**F-b, YOLOE + CLIP's steering.** Today the perception tier steers only
on a detection (P >= 0.8). A frame whose best crop is in the uncertain
band (P in [`tier_local_band_low`, 0.8)) already asks the local VLM; while
that question is out, nothing turns the robot toward the crop. With
`brain.tier_steer_on_candidate` (env `TIER_STEER_ON_CANDIDATE`), the tier
turns toward a band candidate's bearing (LEFT/RIGHT by it, as `_steer_to`,
FORWARD when centred) when nothing measured better steers, and stops doing
so for `tier_stale_after` frames after a local "no". It never feeds the
arrival rule (arrival needs a detection). Default `false` until F5 says
otherwise.
* **It cannot be measured in the simulator:** there perception is the
  simulator's own report (`FrameReportedPipeline`, 1.12), which has no
  sub-gate candidates. It is judged on the real labelled frames (F5).

## 3.80.R amendment 1 (2026-10-18, before any measured run)

Written after smoke tests (one or two frames outside the timed runs), before
any of the 299 or 142 frames was asked of any model.

  Microsoft's remote code). Recorded, not a change of model.
* **A model's runtime may need its own transformers version**, from its
  model card (Eagle2: 4.51; Molmo2: 4.57.1). On the board each gets its own
  venv over the board's torch 2.8 wheel; versions recorded per row.
* **Attention kernel:** where a model's code asks for FlashAttention-2 and

* **PaliGemma 2 is blocked:** its repository is gated (HTTP 403 for this
