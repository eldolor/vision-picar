# 3.94 The tiered ladder as a behavior tree: today's logic redrawn, no behaviour change

*`PLAN-ros-alignment.md` section 3.94; index: [README.md](README.md).*

**Why.** Point 5 of the user's 2026-10-22 discussion: "why not convert this
into policies where each policy has its own tunable settings and flow
behaviors?" The user agreed the order the same day: first redraw today's
logic as a tree with **no change in behaviour**, then tune it in the
scenario simulator, then add learned nodes. Inputs:
* the settings-vs-code inventory (23 `tier_*` keys, plus constants in
  `brain/tiered.py`, `brain/arrival.py` and `brain/perceive.py`);
* the scenario catalogue;
* 3.92's finding that the tiers' disagreement, not VE's own uncertainty,
  is the signal to escalate on.

The finding is not acted on here: this section changes no behaviour.

**What the tree replaces.** `TieredVision` (`brain/tiered.py`, 2,686 lines)
makes four kinds of decision. Today they are written as nested code:

| Decision | Today | As a tree |
|---|---|---|
| **What to do this frame** | `_local_scene`: steer on this frame's box > the local VLM's located yes > dead reckoning > an uncertain candidate > a held goal > scan; then the spin guard; then the turn's size | A **fallback** of rung nodes, the spin guard a **decorator** over it |
| **When to ask** | `_trigger_for`: start, start retry, tracking, candidate edge, band, out-of-vocabulary, cold search (frames or metres), staleness, in that order | A **fallback** of trigger nodes, first to fire wins |
| **Who to ask** | `__call__`, `_local_first` and `_ask_tiers`: local first; the cloud after `tier_local_max_unable` unable answers or with the local tier absent; the call cap, one call in flight, the mission epoch | A **fallback** of tier branches, each behind guard conditions |
| **What an answer changes** | `_apply_local`: yes / no / unable update held goals, rejections and pacing | Unchanged in this section: answer handling stays code, called by the nodes |

**What stays outside the tree, as hard rules** (the shield; nothing a tree
or a later learned node does can get past them):
* `robot/safety.py`'s veto.
* A person's Stop (3.84).
* The arrival rule, and "`found` needs the cloud" (3.80.O).
* B3's failsafes.
* The epoch and `close()` races, the async worker and the stats:
  `TieredVision` keeps all of that plumbing. The tree only decides.

**Decided here, not asked: a small tree module of our own
(`brain/tree.py`), not `py_trees`.** The tree ticks once per frame,
synchronously, inside a policy whose threads already exist. That needs
only a few node kinds: sequence, fallback, condition, action and
decorator, with the success / failure / running statuses. Writing them
(~150 lines) avoids a new dependency on the Jetson and keeps the order
exact. The semantics are `py_trees`', so moving to it later is mechanical.

**Criteria (written before building; CLAUDE.md section 7).**

1. **The existing tests pass unchanged:** `tests/test_tiered*.py`,
   `test_tier_cloud_answers.py`, `test_local_arrival_slow.py`, the
   ProcTHOR and goal-policy sweeps and the full suite, with no existing
   test edited.
   * **Amendment 1 (2026-10-22, before step A's run).** One existing test
     reads the policy's source text, not its behaviour:
     `test_tiered.py::test_a_live_sighting_still_outranks_a_dead_reckoned_one`
     asserts lines of `_local_scene`. It is rewritten to assert the same
     precedence on the tree's rung order. It is the only existing test
     edit allowed; any other counts as a failure of criterion 1.
2. **Exactly the old decisions, frame for frame.** The old functions are
   frozen as a reference (`tests/tiered_reference.py`, as
   `frontier_reference.py` was for 3.77). Two checks:
   * **2a, random states.** 10,000 seeded states are fed to both the
     reference and the tree, for each of the step's decisions. **0
     differences** in the action, the turn's size, the trigger, the
     reasoning text and the state left behind.
   * **2b, missions.** 3.80.O's in-process sweep
     (`evaluations/tiered-380/O/sweep_inprocess.py`), run on 21 houses at
     pace 1 and pace 6, plus the `--decoy` and `--cloud no` arms. The
     reference and the tree must give identical per-frame actions,
     triggers and cloud and local call counts in every run, so outcomes
     match too.
3. **Every node's settings are config, with today's values.**
   * The constants the moved nodes read become node settings in
     `config/robot.yaml` `brain:` `tier_tree:`, defaulting to the values
     in the code today. These are `STEER_BAND_DEG`, `SCAN_TURN_DEG`, the
     turn bounds, `LOCAL_YES_AT` and `LOCAL_RESET_FRAMES`.
   * The node order is config too.
   * `load_brain_config` rejects an unknown node or setting. A tree with
     no default branch (scan for "what to do", none for "when to ask") is
     refused at load.
   * The 23 `tier_*` keys keep working as they do; the tree reads them.
4. **It costs nothing per frame.** On the laptop, the decision time per
   frame (old functions vs tree, 10,000 frames) has a p90 of at most
   **1 ms** for the tree. Perception's budget is 250 ms (3.33).
5. **It can be read.** `describe()` prints the tree with each node's
   settings. The engineering spec shows the default tree, and the
   architecture spec says what the tree owns and what stays a hard rule.
6. **Live.** One tiered mission through the live local stack (the brain's
   HTTP API, `home_first_floor`) ends `found` with 0 contacts.

**Out of scope.** Any change of behaviour, including 3.92's disagreement
trigger and 3.91.C's rules. Those become new nodes in their own sections,
with their own bars. Learned nodes. Answer handling (`_apply_local`) and
the arrival's own ladder.
