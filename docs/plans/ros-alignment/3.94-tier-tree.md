# 3.94 The tiered ladder as a behavior tree: today's logic redrawn, no behaviour change

*`PLAN-ros-alignment.md` section 3.94; index: [README.md](README.md).*

**Why.** Point 5 of the user's 2026-10-22 discussion: "why not convert this
into policies where each policy has its own tunable settings and flow
behaviors?" The user agreed the order the same day: first redraw today's
logic as a tree with **no change in behaviour**, then tune it in the
scenario simulator, then add learned nodes. Inputs:
* the settings-vs-code inventory (23 `tier_*` keys, plus constants in
  `brain/tiered.py`, `brain/arrival.py` and `brain/perceive.py`);
* the scenario catalogue;
* 3.92's finding that the tiers' disagreement, not VE's own uncertainty,
  is the signal to escalate on.

The finding is not acted on here: this section changes no behaviour.

**What the tree replaces.** `TieredVision` (`brain/tiered.py`, 2,686 lines)
makes four kinds of decision. Today they are written as nested code:

| Decision | Today | As a tree |
|---|---|---|
| **What to do this frame** | `_local_scene`: steer on this frame's box > the local VLM's located yes > dead reckoning > an uncertain candidate > a held goal > scan; then the spin guard; then the turn's size | A **fallback** of rung nodes, the spin guard a **decorator** over it |
| **When to ask** | `_trigger_for`: start, start retry, tracking, candidate edge, band, out-of-vocabulary, cold search (frames or metres), staleness, in that order | A **fallback** of trigger nodes, first to fire wins |
| **Who to ask** | `__call__`, `_local_first` and `_ask_tiers`: local first; the cloud after `tier_local_max_unable` unable answers or with the local tier absent; the call cap, one call in flight, the mission epoch | A **fallback** of tier branches, each behind guard conditions |
| **What an answer changes** | `_apply_local`: yes / no / unable update held goals, rejections and pacing | Unchanged in this section: answer handling stays code, called by the nodes |

**What stays outside the tree, as hard rules** (the shield; nothing a tree
or a later learned node does can get past them):
* `robot/safety.py`'s veto.
* A person's Stop (3.84).
* The arrival rule, and "`found` needs the cloud" (3.80.O).
* B3's failsafes.
* The epoch and `close()` races, the async worker and the stats:
  `TieredVision` keeps all of that plumbing. The tree only decides.

**Decided here, not asked: a small tree module of our own
(`brain/tree.py`), not `py_trees`.** The tree ticks once per frame,
synchronously, inside a policy whose threads already exist. That needs
only a few node kinds: sequence, fallback, condition, action and
decorator, with the success / failure / running statuses. Writing them
(~150 lines) avoids a new dependency on the Jetson and keeps the order
exact. The semantics are `py_trees`', so moving to it later is mechanical.

**Criteria (written before building; CLAUDE.md section 7).**

1. **The existing tests pass unchanged:** `tests/test_tiered*.py`,
   `test_tier_cloud_answers.py`, `test_local_arrival_slow.py`, the
   ProcTHOR and goal-policy sweeps and the full suite, with no existing
   test edited.
   * **Amendment 1 (2026-10-22, before step A's run).** One existing test
     reads the policy's source text, not its behaviour:
     `test_tiered.py::test_a_live_sighting_still_outranks_a_dead_reckoned_one`
     asserts lines of `_local_scene`. It is rewritten to assert the same
     precedence on the tree's rung order. It is the only existing test
     edit allowed; any other counts as a failure of criterion 1.
2. **Exactly the old decisions, frame for frame.** The old functions are
   frozen as a reference (`tests/tiered_reference.py`, as
   `frontier_reference.py` was for 3.77). Two checks:
   * **2a, random states.** 10,000 seeded states are fed to both the
     reference and the tree, for each of the step's decisions. **0
     differences** in the action, the turn's size, the trigger, the
     reasoning text and the state left behind.
   * **2b, missions.** 3.80.O's in-process sweep
     (`evaluations/tiered-380/O/sweep_inprocess.py`), run on 21 houses at
     pace 1 and pace 6, plus the `--decoy` and `--cloud no` arms. The
     reference and the tree must give identical per-frame actions,
     triggers and cloud and local call counts in every run, so outcomes
     match too.
   * **Amendment 2 (2026-10-22, before 2b's counted run).**
     * **The reference is `dev` just before 3.94** (`0c4677f8`, the whole
       checkout through the sweep's `--root`), not `ReferenceTieredVision`.
       It is the stronger check: the code as it ran.
     * **The async arms run on a deterministic worker.** A first run found
       the async arms differ from run to run on the *same* code (the
       baseline against itself: 50 frames apart on `procthor:val:12`, from
       the worker thread's timing). Per-frame identity cannot be measured
       there. The harness's worker therefore lands each call two frames
       after it went out, or at once when waited on. The calls are still
       in flight on the frames between (93 such frames on that house).
     * **`PYTHONHASHSEED=0`.** The decoy's seed is `hash(house)`, which
       Python salts per process.
     * **Arms:** pace 6, pace 1, decoy 0.05, cloud "no", and sync, each on
       the 21 criterion houses.
3. **Every node's settings are config, with today's values.**
   * The constants the moved nodes read become node settings in
     `config/robot.yaml` `brain:` `tier_tree:`, defaulting to the values
     in the code today. These are `STEER_BAND_DEG`, `SCAN_TURN_DEG`, the
     turn bounds, `LOCAL_YES_AT` and `LOCAL_RESET_FRAMES`.
   * The node order is config too.
   * `load_brain_config` rejects an unknown node or setting. A tree with
     no default branch (scan for "what to do", none for "when to ask") is
     refused at load.
   * The 23 `tier_*` keys keep working as they do; the tree reads them.
4. **It costs nothing per frame.** On the laptop, the decision time per
   frame (old functions vs tree, 10,000 frames) has a p90 of at most
   **1 ms** for the tree. Perception's budget is 250 ms (3.33).
5. **It can be read.** `describe()` prints the tree with each node's
   settings. The engineering spec shows the default tree, and the
   architecture spec says what the tree owns and what stays a hard rule.
6. **Live.** One tiered mission through the live local stack (the brain's
   HTTP API, `home_first_floor`) ends `found` with 0 contacts.

**Step D's design (written 2026-10-22, before building it; the user's yes
the same day).** One `brain:` key, `tier_tree`, validated by
`load_brain_config` (it runs in the walks Lambda too, which carries only
`control/`, so the schema lives in `control/brain_config.py`). Every
default is today's value.

* **What may be reordered or tuned:**
  * `what_rungs`: the steering rungs' order, and which run. Each is one of
    `steer`, `located`, `reckoned`, `candidate`, `held`, `scan`.
    * `scan` must be present and last: it is the default that always
      chooses.
    * A rung may be left out.
    * No name may appear twice.
  * `absent_events`: the order of `band`, `oov`, `cold_frames` and
    `cold_metres` on an absent frame. Each may be left out, none may
    repeat.
  * `steer_band_deg` (3.0, in (0, 45]); `scan_turn_deg` (45, in [5, 90]).
  * `min_turn_deg` (5) and `max_turn_deg` (90): 1 <= min <= max <= 180.
  * (Narrowed by the reviews before the push: see 3.94.D's results.)
  * `local_yes_at` (0.5), above `tier_local_no_below` and at most 1.
    It applies to the frame questions only.
* **What is fixed (hard rules, not settings).**
  * The order of "who to ask": the call cap, one call at a time and
    "mission ended" before any question.
  * The head of "when to ask": the opening question, an `unavailable`
    frame, the retry, tracking and the candidate edge, then the absent
    edge.
  * The arrival's own `LOCAL_YES_AT`: the found guard is 3.80.O's.

  A config that names any of these is refused as unknown.
* **Shared constants keep one meaning outside tiered.** `explore.py` and
  `arrival.py` read `STEER_BAND_DEG` and `turn_for` from the module, and
  keep the module's values. A changed `steer_band_deg` moves tiered's band
  only (stated in the spec).

**Out of scope.** Any change of behaviour, including 3.92's disagreement
trigger and 3.91.C's rules. Those become new nodes in their own sections,
with their own bars. Learned nodes. Answer handling (`_apply_local`) and
the arrival's own ladder.

## Results

**3.94.A, 2026-10-22 (on `dev` at `f8ae1b2e`).**
* **Criterion 1 (for A): met.** The tiered suites pass, 294 tests, and
  the full suite passes at `ready`. The only existing test edited is
  amendment 1's.
* **Criterion 2a (for A): met.** 10,000 seeded states with 1-3 frames
  each give **0 differences** in the scene, the reasoning, the turn's size
  and the state left behind.
  * Every rung was exercised, the spin guard included.
  * Three planted bugs were each caught: the spin guard's exemption
    narrowed, a turn's size dropped, and the located yes not spent.
* **Criterion 4 (for A): met.** The tree's p90 is under 1 ms a frame (the
  test's bar).
* **Reviews.**
  * The Thermos pass found no behaviour difference.
  * `/code-review` asked for the rung names as constants, a precedence
    test that also checks each node's function, settings read live by
    `describe()`, a ladder that chooses nothing raising instead of
    skipping the turn's size, and the spec in the same commit. All done.
  * Kept: the tree holds bound methods (a reference cycle, freed by the
    cyclic collector), because frames after `close()` still use the tree.

**3.94.B, 2026-10-22 (on `dev` at `1710d029`).** "When to ask" (`_trigger_for`) is a tree
(`_build_when_tree`). The old body is frozen beside 3.94.A's in
`tests/tiered_reference.py`.
* **Criterion 1 (for B): met.** The tiered suites pass, 294 tests. No
  existing test was edited.
* **Criterion 2a (for B): met.**
  * 10,000 seeded runs of 1-8 frames each, with random configuration and
    state (the vote, sighting spans and stamps, the band, local tracking,
    the call cap, vocabulary, the pacing counts), give **0 differences**
    in the trigger and in the state left behind.
  * Every trigger fired, and so did "none".
  * Five planted bugs were each caught: the absent count dropped, the
    out-of-vocabulary node disabled, the absent edge dropped, the band
    asked twice, and the frames node made to check metres. Swapping the
    two cold-search nodes would not be caught, and is no bug: they fire
    the same trigger and change nothing.
  * After review, the test also applies the dispatch path's changes
    between frames: an answer landing, an unanswered question, a band no,
    distance travelled.
  * **Criterion 4 (for B): met.** p90 under 1 ms a frame.
  * **Reviews.** Neither reviewer found a behaviour difference. The fixes

**3.94.C, 2026-10-22 (on `dev` at `3157229b`).** "Who to ask" (the tail of `__call__`) is a tree
(`_build_who_tree`). The old `__call__` is frozen beside A's and B's.
* **Criterion 1 (for C): met.** 333 tiered, local-arrival and offline
  tests pass. No existing test was edited.
* **Criterion 2a (for C): met.**
  * 2,500 seeded runs of 1-10 frames each go through the whole
    `__call__`. They cover sync and async; a local tier present or absent,
    answering, timing out or down; a cloud that answers or fails, fatal or
    not; the call cap; a call still in flight; a close; and a Stop landing
    while the frame is in perception.
  * They give **0 differences** in the scene, the policy's state, its
    stats, the model calls and the dispatches. The clock was pinned, so
    timings cannot differ.
  * Every route was taken: no trigger, the cap, in flight, ended, the
    local tier, dispatched, cloud answered, cloud failed, and raised.
  * Six planted bugs were each caught: the local route removed, the
    no-trigger count dropped, the band's re-arm dropped, a refused
    dispatch still counted, the epoch check removed, and in-flight checked
    without async. The epoch bug was caught only after the test learnt to
    land a Stop mid-perception, which it had missed at first.
* **Reviews.** Neither reviewer found a behaviour difference. The fixes:
  * a tree that ends without an answer raises;
  * the re-arm calls `_rearm`;
  * the test's dispatches leave a call in flight, which lands later as a
    scene or a failure;
  * the arrival check holds the local VLM in some runs;
  * a located yes is held in some runs;
  * more state is compared;
  * the clock is pinned for these two modules only.

  After these, planted bugs 1-6 still fail, and so does a seventh (a sync
  cloud answer that leaves the located yes in place). In-flight checked
  without async now passes: in sync mode nothing is ever in flight, so
  the change makes no difference.
* **Open, found by the reviews; not this section's to change** (each is
  today's behaviour):
  * a dispatch that `close()` refuses rolls the call counts back, but
    leaves the pacing counts reset;
  * the "a cloud answer landed" block is written twice
    (`_who_ask_cloud`, `_ask_local_first`).

**3.94.D, 2026-10-22.** `brain.tier_tree` (`{}` in `config/robot.yaml`:
the defaults live in the code) is validated in `load_brain_config` and
passed to the policy by the brain server. The metrics row carries it as
one compact string, so a recorded walk says which tree ran.
* **The reviews changed the design's limits** (both reviewers, before the
  push):
  * **The steering band can only narrow.** The arrival counts a target
    centred within `ARRIVAL_CENTRE_DEG` (3.0). A wider band would stop
    turning toward a target the arrival never counts, and the robot would
    never arrive. The cap is pinned to the arrival's constant.
  * **Turn numbers are whole degrees,** at most 90, and the scan step sits
    inside the bounds.
  * **`steer`, `located` and `scan` must stay.** A located yes is spent
    and held every frame whether its rung runs or not, so without the rung
    the hold would drive on it unsteered.
  * **Under `tier_search: explore` the band and bounds keep their
    defaults,** since explore steers with the module's (one band a
    mission).
  * **The policy checks its own names.**
* **Criterion 3: met.**
  * The shipped yaml loads to `TIER_TREE_DEFAULTS`, which equals the
    policy's `TREE_DEFAULTS`.
  * Sixteen bad trees are refused at load: a rung list not ending in
    `scan`, a name twice, an unknown rung or event, a key naming
    who-to-ask's order, a band of 0, a band past the arrival's, the scan
    outside the bounds (twice), a fractional turn, a required rung left
    out, a scan of 120, min above max, `local_yes_at` at or below
    `tier_local_no_below`, a bool for a number, and a non-mapping.
  * Explore's rule holds both ways.
  * A partial tree keeps the other defaults.
  * Each setting takes effect:
    * leaving `held` out makes a held goal scan;
    * a 1-degree band turns at 2 degrees (FORWARD at today's 3);
    * the bounds cap a 70-degree turn at 40 and raise an 11-degree turn
      to 12;
    * the scan step is 30;
    * an empty `absent_events` falls through to staleness;
    * `local_yes_at` 0.7 makes 0.6 unable for a frame question, while the
      arrival keeps 0.5.
* **Criterion 1:** the tiered, brain-server, arrival, config and metrics
  tests pass with the defaults (the 2a equivalence tests still pass: 0
  differences).
* **Criterion 5: met.** `describe_tree()`, `describe_when_tree()` and
  `describe_who_tree()` print the trees with their settings, read live.
  The engineering spec gives the default tree and the config row. The
  architecture spec says what the tree owns and what stays a hard rule.
