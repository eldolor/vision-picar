# 3.128 A shared/exclusive desktop lock: timing-sensitive runs alone, other heavy jobs together

*`PLAN-ros-alignment.md` section 3.128; index: [README.md](README.md).*

**Why.** On 2026-10-31 one session's `plan_section.py ready` suite (6
xdist workers) ran during another session's live explore run (3.126,
`home_first_floor`, started 08:21:45). The desktop's log (`~/temp-log`,
10 s readings, 12 cores) shows load 3.7-5.8 from 08:23 to 08:26, above
3.79's ~4 bar for about 3 minutes, and the clock at 2.8-3.2 GHz instead of
~4.0, so the run's timings are suspect and it is being rerun. Rule 7's
lock (`.git/heavy-run.lock`) was taken only by `tests/demo_explore.stack()`;
the suite, the push gate and training took nothing, so nothing stopped
them. A single lock for every heavy job would fix it but idle the desktop:
suites, builds and training do not spoil each other's results, only a timed
run's.

**The user's ask (2026-10-31):** jobs whose results depend on timing take
the lock alone, every session respects it, and lighter heavy jobs share the
desktop.

**Design.** A readers-writer lock on the existing file, so worktrees not
yet rebased (whose `demo_explore` takes a plain exclusive `flock` on it)
still exclude and are excluded:

* **Exclusive** (`flock` LOCK_EX): live runs (`demo_explore.stack()`,
  through `heavy_lock()`), `ready --full`, any run with a wall-clock bar.
  Waits for every holder; then the desktop is its own.
* **Shared** (LOCK_SH): the fast tier (`ready`, the push gate), training,
  evaluations, docker builds. Any number together; none while an exclusive
  holder runs.
* **Fairness:** a second file, `.git/heavy-run.gate`. Every acquirer takes
  it exclusively, then the main lock, then lets the gate go. An exclusive
  acquirer holds the gate while it waits, so new shared jobs queue behind
  it instead of starving it (Linux `flock` lets readers jump a waiting
  writer).
* **Nesting:** the holder's mode goes to its children in
  `PICAR_DESKTOP_LOCK`. Under an exclusive holder any request passes
  through (`ready --full`'s live tests call `stack()`); under a shared
  holder a shared request passes and an exclusive one fails at once naming
  why, never a deadlock.
* **Who holds it:** each holder writes one line to
  `.git/heavy-run.d/<pid>`; an exclusive holder also writes the main file,
  as before, for old readers. `status` lists live holders and drops dead
  pids' lines.
* `tools/desktop_lock.py status | shared --why W -- CMD | exclusive --why W -- CMD`
  (`--no-wait`: exit 75 when busy). `PICAR_HEAVY_LOCK=0` still skips it.
* Known limit: the lock is held by the wrapper, not inherited by the
  command (inherited, daemons it starts would keep it, as the nightly's
  did); a `kill -9` of the wrapper frees the lock while the command runs.
  The nightly (`tools/nightly_suite.sh`) keeps its own lock, unchanged.

**Criteria (written before building; CLAUDE.md section 7):**

1. Two shared holders run at the same time; an exclusive request waits for
   both; a shared request waits for an exclusive holder (subprocess test,
   real `flock`).
2. No starvation: with an exclusive request waiting behind a shared holder,
   a later shared request starts only after the exclusive one has run.
3. Old style: a plain LOCK_EX on `heavy-run.lock` (an unrebased
   `demo_explore`) makes shared and exclusive requests wait, and a shared
   holder makes it wait.
4. Nesting: under exclusive, child requests of either mode pass through;
   under shared, a child's shared passes and its exclusive raises at once.
5. `ready` and the push gate run the fast tier under shared and
   `ready --full` under exclusive, with `PICAR_DESKTOP_LOCK` in pytest's
   environment.
6. `demo_explore.heavy_lock()` goes through the tool and keeps its
   `waiting for the heavy-run lock` line (evaluations grep it) and
   `PICAR_HEAVY_LOCK=0`.
7. `status` names each live holder with its mode and drops dead pids.
8. `ready` passes (holding shared itself).

**Live, the first time it mattered (2026-10-31).** This branch's own
`ready` was started while 3.126's live rerun held the lock exclusively
(`status`: EXCLUSIVE, pid 313168, since 08:40:18). The rerun wrote its
result at 08:47:58; the suite's load appears from 08:48:33 (`~/temp-log`:
1.5 at 08:48:03, 2.9 at 08:48:33, 4.3 at 08:49:33). The suite waited
for the run instead of running beside it.

**Review fixes (bug pass and `/code-review`, before merge).** Both found
that a bare `PICAR_DESKTOP_LOCK` outlived its hold (a daemon or tmux
started under one would pass every later job through): the value is now
`<mode>:<pid>`, trusted only while that pid is alive and, on Linux, holds a
flock on the file (`test_a_token_whose_holder_is_gone_or_holds_nothing_is_not_trusted`).
An inherited descriptor no longer counts a live stranger's row (an
unlocked `exec 9>` would have read another session's hold as its own);
acquiring cannot leak the lock or a descriptor; `hold_for_life()` clears
its note at exit; `--no-wait` retries 1.5 s before calling a busy gate
busy; `run_tests` turns `Nested` into a plain refusal; no token is passed
under `PICAR_HEAVY_LOCK=0`.

**Known limits.**
* The nightly (`tools/nightly_suite.sh`) runs the full suite under its own
  lock only; a session's shared work can overlap it at night. Its driver's
  signal handling (26 review rounds) is its own section.
* A queued exclusive job holds the gate, so a push (shared) waits behind
  it and so behind whatever it waits for (a long training run). That is
  the fairness rule; the waiter is told a job is queued ahead.
* Old-style holders (unrebased worktrees; evaluations' `heavy_lock_free()`
  probes) skip the gate and can wait behind a stream of shared jobs; the
  probes read any suite as a live run.
* Ancestor detection needs /proc/locks and a filesystem whose `st_dev`
  matches it (ext4 here); elsewhere (macOS) only the token passes a
  child through.
* A `kill -9` of the wrapper frees the lock while its command runs on.
