# 3.83 nav2's costmap on the twin's map, live

*`PLAN-ros-alignment.md` section 3.83; index: [README.md](README.md).*

**Why.** The user asked (2026-10-15) whether the UI shows the SLAM map as
`slam_toolbox` builds it (it does: the Sim tab's map panel, `GET
/world/map`, re-read every 1 s) and whether nav2's costmap can be shown the
same way. It could not: nothing outside the ROS container read a costmap,
so the only view of one was Foxglove (`PICAR_FOXGLOVE=1`, off by default
since 3.81, and never on the deployed twin). The costmap is what explains
nav2's behaviour this plan keeps measuring -- 3.67's 0.35 m inflation, goal
6's slot beside the car, the garage wedge -- so seeing it from the phone,
over the SLAM map, while the robot drives, is the point.

**Design.**

* **Which costmap.** The GLOBAL costmap (`/global_costmap/costmap`,
  `nav_msgs/OccupancyGrid`, frame `map`, 1 Hz, full every publish:
  `always_send_full_costmap`). It is the one the planner plans on, it holds
  the static layer (the SLAM map), the obstacle layer (the live scan) and
  the inflation, and it is in SLAM's own frame, so `RosWorld`'s anchor
  places it exactly as it places the map. The local costmap (frame `odom`,
  a 2 x 2 m rolling window) is left out: placing it needs the map -> odom
  transform at its stamp, and it adds nothing the global one does not show
  at this scale.
* **The bridge** subscribes to it (transient local, reliable, depth 1, as
  `costmap_2d` publishes) and serves the latest on ONE new route, `GET
  /nav/costmap`, in ROS's own frame and convention, tagged with the
  session and a version -- `/slam/map`'s shape exactly, built by one shared
  helper (`convert.grid_record`). Values are as nav2 publishes them:
  -1 unknown, 0 free, 1-98 inflation, 99 inscribed, 100 lethal. The bridge's
  route budget goes 13 -> 14, in the commit that says why.
* **`RosWorld.get_costmap()`** (not part of `WorldInterface`, like goals):
  the same anchor and the same resampling as `get_map()`, keeping the raw
  cost per cell instead of the three map states. The resampling is done in
  numpy and is pinned to pick exactly the cell `_resample()` picks, so the
  two layers cannot drift apart. Cached by (session, version, anchor).
  No costmap yet, another session, or a bridge that cannot answer:
  `usable: false` (with 3.82's `retryable` when the bridge failed).
* **The robot server** serves it as `GET /world/costmap` (secret-guarded,
  a pass-through like `/world/map`). A world without a costmap answers 501,
  as `/world/goal` does.
* **The twin.** A "Costmap" switch under the map, shown only on a SLAM map
  whose server has the route; OFF by default and remembered per phone. On,
  the page fetches `/world/costmap` on the map's own 1 s clock and draws it
  over the cells and under the route, goal and pose: free and unknown
  transparent, inflation shaded by cost, inscribed and lethal strongest, in
  its own colour token (`--map-cost`). The readout names it. Off, nothing
  is fetched, so the default costs the tunnel nothing.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Alignment.** For every cell of the house-frame output, the costmap
   resampler picks the SAME source cell as the map's `_resample()` on the
   same grid geometry and anchor: 0 differences over a cardinal start
   (0/90/180/270 deg), a non-cardinal one (37 deg) and an origin that is
   not a whole number of cells, on grids of 10 x 10 and 120 x 80.
2. **Values cross unchanged.** A known costmap through the bridge's record,
   `RosWorld` and the robot server: every in-bounds cell's value in
   {-1, 0..100} arrives as nav2 sent it; a lethal cell 0.3 m straight ahead
   of the robot in ROS lands 0.3 m along the robot's TRUE heading in the
   house frame (within one cell).
3. **Honest absence.** No costmap yet, a costmap from another session, a
   bridge that is down, a bridge 401 and a bridge without the route (an old
   image, 404) each give `usable: false`, never an empty or zero grid; a
   world with no costmap answers 501; the route refuses a missing secret
   when one is set.
4. **Cost.** On this machine, `get_costmap()` on a 300 x 240 grid (a
   furnished home at 5 cm) takes p90 < 50 ms uncached and < 1 ms cached
   (the robot server's wheel loop shares the process).
5. **The twin, in a real browser at 390 px** (red first: each test fails
   before the twin change): (a) on a SLAM map with the route, the switch
   shows; ON draws costmap-coloured pixels where the stub's lethal and
   inflated cells are and none where its free cells are, and OFF removes
   them; (b) with the switch off, `/world/costmap` is never requested;
   (c) on a sim map, or a server answering 501, the switch is hidden and
   nothing is drawn; (d) a costmap version change redraws within 2.5 s;
   (e) no page errors. A phone-size screenshot is the evidence.
6. **Wall rules hold:** `tests/test_wall_linters.py` and
   `tests/test_ros_containment.py` pass with the new route (budget 14, a
   consumer outside the container, in the bridge's docstring).
7. **Live, through the real stack** (robot server, this section's ROS image
   and domain, `scaled_house`, a nav2 goal across a room): with the switch
   on, the twin's costmap version advances at least once every 2.5 s while
   nav2 drives, and the inflation it draws borders the walls the SLAM map
   draws (lethal cells within 1 cell of an occupied map cell, 95%+).

**Amendment 1 (2026-10-15, written before the twin's tests ran).** Building
5(d) found that the twin re-read the map ONLY with a camera frame -- a D-pad
press on this page or a brain mission's poll. A robot driven by a tapped
nav2 goal, a script or another phone built its map unseen, so neither layer
could be "live" as the user asked. Added: (f) on the Sim tab a SLAM map is
re-read on its own 1 s clock with no press and no brain (a new version on
the canvas within 2.5 s), and keeps being re-read through an unusable reply
(a bridge blip) until the map is back.

**Also changed, found on the way.** `/world/map` was encoded by FastAPI's
own encoder, walking ~10^5 cells in Python on the robot server's process
(the wheel loop's): 191 ms p90 on a 300 x 240 house. With `json.dumps` and
compact separators: 43 ms, same 378 KB. The map's placement is vectorised
with the costmap's (same answers, criterion 1). The bridge now copies both
grids outside its lock.

**Known limits.** nav2 publishes the whole global costmap every second, so
with the switch on a phone pulls ~400 KB/s through the tunnel and the robot
server places it every second; the switch is off by default. The local
costmap is not shown. An image built before 3.83 answers 404 (the switch
hides) and one without `age_s` is never marked stale.
