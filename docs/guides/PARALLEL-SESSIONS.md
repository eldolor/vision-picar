# Parallel sessions on the plan

Several Claude Code sessions work on `PLAN-ros-alignment.md` at once (the
user, 2026-10-07). These rules keep them from colliding. Each one answers a
collision this project has already had.

## The workflow

```bash
# 1. Reserve a section: the next free number, its own branch and worktree.
python tools/plan_section.py new <slug> "<title>"
#    -> branch plan/3.N-<slug>, worktree .claude/worktrees/plan-3.N,
#       docs/plans/ros-alignment/3.N-<slug>.md, committed.
cd .claude/worktrees/plan-3.N

#    Or continue one: `board` shows every open step and who holds it; `next`
#    names the first step you may take. Then claim it (rule 8):
python tools/plan_section.py board
python tools/plan_section.py claim 3.N.X     # refused if it would collide

# 2. Your own ports, ROS domain, container, image tag and log directory.
eval "$(python tools/plan_section.py env)"
docker build -t "$ROS_IMAGE" service/slam    # only if you change service/slam

# 3. Before touching a shared file, see who else is touching it.
python tools/plan_section.py overlap

# 4. Review every code commit (CLAUDE.md section 6), then record it; the
#    push warns about code commits with no record (it never blocks).
python tools/plan_section.py reviewed [--thermos]   # --thermos when it ran too

# 5. When done: rebase, then the gate.
git fetch origin && git rebase origin/dev
python tools/plan_section.py ready           # fast tier; records a pass (optional:
                                             # the push runs the same check itself)
# 6. Push when your judgement says the work is ready (the user, 2026-10-15):
git push origin HEAD:dev
```

Continuing an existing section: work in its worktree
(`git worktree list`). Do not create a second branch for it.

## The rules

1. **One file per section.** Every `3.N` section is
   `docs/plans/ros-alignment/3.N-<slug>.md`. A session edits its own
   section's file; `PLAN-ros-alignment.md` keeps only the shared context
   (sections 0-2 and 4-6). The index (`ros-alignment/README.md`) is
   generated by `tools/plan_section.py index` and merges by union. On a
   conflict there, regenerate it. *Why:* every session appended its section
   at the same line of one 5,000-line file, so every pair of sessions
   conflicted.
2. **The number is reserved by the branch.** `new` takes the highest number
   on `origin/dev` and in every `plan/*` branch name, plus one, and creates
   the branch at once. Worktrees share one `.git`, so every session on this
   machine sees every branch, and git refuses a duplicate branch name.
   *Why:* two sessions both wrote a 3.42 on 2026-10-06/07.
3. **Shared status is edited at merge, not on a branch.** A branch writes
   its own section file, its code, its specs and its own handoff
   (`docs/handoffs/HANDOFF-<date>-3.N-<slug>.md`). CLAUDE.md section 3b,
   `docs/ARCHITECTURE.md`'s status and section 6's open questions are
   updated by whoever merges, after rebasing. *Why:* one branch's status
   text was stale the moment another merged.
4. **Your own runtime resources.** `tools/plan_section.py env` derives from
   the section number:
   * ports 9000 + 10 x N (robot, brain, body, sensors, bridge; 3.106 ->
     10060), never shared;
   * `ROS_DOMAIN_ID` N (3.44 -> 44; 73 and 74, older stacks' fixed domains,
     map to 100 and 101). Domains must stay within 1-101, so past 3.99 N
     wraps (3.106 shares 3.6's 6), and `env` prints a WARNING comment when
     another section with a worktree here shares yours (3.107);
   * container `picar-ros-3N`;
   * image `vision-picar-ros:plan-3.N`;
   * logs in `/tmp/vision-picar-3.N`.

   `tests/demo_explore.stack()` and everything built on it read these.
   Never rebuild `vision-picar-ros:latest` from a branch; it is built from
   `dev`. *Why:* two ROS containers on one domain crossed topics (8 of 13
   tests failed), and a branch rebuilt the shared image under another
   session.
5. **Check overlap before editing a shared file.** `overlap` lists every
   file you change that another `plan/*` branch also changes. A text merge
   can succeed and still be wrong: `robot/safety.py` changed on two
   branches at once on 2026-10-06/07. Coordinate through the user, or
   sequence the work.
6. **The merge gate: fast on push, full at night.** A push to `dev` runs
   `tools/hooks/pre-push` (installed by `git config core.hooksPath
   tools/hooks`), which calls `plan_section.py gate`. A push that changes
   only Markdown (any `.md`) and the images under `docs/` runs the spec
   lint and `test_plan_section.py` (which reads the real section files and
   index) and nothing else; the data under `docs/` is not docs, since tests
   read it. Any other push runs the **fast tier**: the whole suite
   except the real-browser tests (`test_ui*.py`, `test_frame_source.py`),
   the live-stack ones (`*_live.py`) and the measurement sweeps
   (`SLOW_FILES` in `tools/plan_section.py`, which held ~45 of the full
   run's 51 minutes), unless `ready` already recorded a pass for that
   commit. Both run on the working tree, so the gate and `ready` refuse
   one that is not the commit: a different HEAD, uncommitted changes, or
   an untracked file that is not ignored (it could be a module the commit
   imports). A pass is recorded for the CHANGE (its diff without blob ids
   or line numbers, whitespace kept -- not `git patch-id`, which ignores
   indentation), so a clean rebase onto another session's push does not
   rerun the tier. A push that deletes `dev` is refused (only the user
   overrides that too, with `PICAR_SKIP_GATE=1`). Review records use the
   same id; ones written before 2026-10-14 used `git patch-id`, so re-run
   `reviewed` on a branch that had them. A new
   sweep that runs hundreds of missions belongs on that list. The **full suite** runs once a night on the latest
   `origin/dev` (`tools/nightly_suite.sh`, installed with `--install`;
   result in `~/Library/Logs/vision-picar/nightly-latest.txt`, whose first
   line reads RUNNING while a run is going and is not left so once it
   ends, unless no write can land at all (a full disk), the wrapper itself
   is killed, or there is no venv python to hold the lock; its worktree
   is reset and cleaned to that commit each night, a refresh that fails is
   that night's FAIL, a run past `NIGHTLY_TIMEOUT_S`, default 7000 s, is
   stopped and reported FAIL, a run someone stops (TERM, HUP, Ctrl-C)
   reads STOPPED and is not emailed -- a signal that reaches only the
   script, an OOM kill, is a FAIL, and one that also kills the job's
   wrapper (Ctrl-\\ in a terminal, a kill -9 of the job) leaves RUNNING -- and one run holds a lock: a second is refused and adds a
   SKIPPED line under the night's verdict, which stays the first line; if
   no run got the lock tonight, SKIPPED is the first line) and with
   `ready --full` before merging a section that changes the twin or the
   ROS stack. It reports; it never blocks a push. Only the user overrides
   the gate (`PICAR_SKIP_GATE=1`).
   *Why:* the gate first ran the full suite, about 40 minutes, on every
   push, and a pass named one commit, so each rebase onto another
   session's push started it over; two timing-sensitive tests then failed
   one run in two. The user called that too heavy (2026-10-09).
7. **One heavy run at a time.** `tests/demo_explore.stack()` takes a lock
   (`.git/heavy-run.lock`) held until the run's process exits; a second
   heavy run waits and prints who holds it. *Why:* late ticks, scan skew
   and nav2 smoothness are timing measurements, and two stacks on one
   laptop skew each other. Long runs can go to the Jetson instead
   (`tools/jetson/README.md`). `PICAR_HEAVY_LOCK=0` skips the lock, for
   in-process work only.
   **The Jetson has its own lock, held on the board** (3.93). Take it before
   anything that changes the board's state or measures it: a bench, a
   service stop or start, an install, a memory or latency number.
   ```bash
   python tools/jetson/board_lock.py status                  # FREE, or who holds it and why
   python tools/jetson/board_lock.py run --why "<what>" -- <command>
   python tools/jetson/board_lock.py hold --why "<what>"     # multi-step work, then
   eval "$(python tools/jetson/board_lock.py env)"           # PICAR_BOARD_TOKEN
   python tools/jetson/board_lock.py release
   ```
   * Busy: the tool exits 75 and prints the holder's line (`--wait S` waits
     instead). Exit 1 means the board could not be reached. A hold ends by
     itself when its session dies, when the network goes silent for 90 s,
     or at its `--max` (default 4 h).
   * Board-side benches (`headroom_identity.sh`, `headroom_mission.sh`,
     `bench_local_vlm.sh`) refuse to run under another session's hold. Pass
     your token to them:
     `ssh picar-jetson "PICAR_BOARD_TOKEN=$PICAR_BOARD_TOKEN bash ..."`.
     A bench then keeps the lock for itself as long as it runs, even after
     your session's hold ends.
   * A hold taken by hand counts too: `flock ~/.picar-board.lock` with a line
     in `~/.picar-board.owner`, `"<session> (<host>): <why>, since <iso>"`.
   * Read-only checks (`systemctl is-active`, `free`, `status`) need no lock.
8. **Claim a step before working on it** (3.75). A section's discrete
   steps are rows of a `## Steps` table in its own file:

   ```
   | Step | Title | Needs | Waits | Touches | State |
   |---|---|---|---|---|---|
   | 3.70.S | Survey mode | 3.50.D | -- | `brain/survey.py`, `control/` | open |
   ```

   `Needs` names steps that must be `done` first; `Waits` is `user`,
   `rover` or `--`; `Touches` lists the paths the step will change (a
   trailing `/` is a directory, `*` globs and crosses `/`); `State` is
   `open`, `done` or `dropped`, and only its first word counts (`done
   (sweep met)` is done); any other word shows as `unknown` and is never
   claimable. Commit the table: the board reads committed text, from the
   section's newest `plan/*` branch that changed the file and holds
   `origin/dev`'s copy of it; else from `origin/dev`. A branch whose file
   `origin/dev` changed after it forked (a branch merged under other
   commits, or abandoned, stays unmerged for good) is not read until it
   merges `origin/dev`: until then `claim` does not see its new rows. In a
   Touches cell, tick every path, one per comma: other text makes the step
   `unknown` until it is fixed. `Waits` reads `user`, `rover` or `--` by
   the same first-word rule as `State`.
   * `claim <step>` writes a claim into the shared `.git`
     (`plan-claims/`), which every worktree on this machine sees. It is
     owned by your Claude Code process and **frees itself when that process
     exits**. `release` gives it back sooner. `/clear` keeps the process, so
     the new conversation inherits the claim; the session-start board says
     so first.
   * A claim is refused when its `Needs` are not done, when it waits on the
     user or the Rover, when another live session holds a step of the same
     section (one session per section: its worktree, ports and ROS domain),
     or when its `Touches` overlap a live claim or a branch worked on in
     the last 2 hours. A branch with no claim yet counts as active from its
     last commit or its newest uncommitted edit. Against such a branch,
     and only such a branch, `claim --accept-overlap` takes the step after
     you have checked the shared file by hand. The claim records it.
   * Guards: before editing a path inside another session's claim, Claude
     Code asks the user (a `PreToolUse` hook on Edit/Write). In auto or
     bypass mode no one would see that question, so the edit is denied with
     the reason. Only if the user agrees, `python3 tools/plan_claims.py
     allow <step>` lets this session edit inside that claim; the claim
     records it. **This is on trust:** nothing can check that the user was
     asked, so a session that runs `allow` without asking breaks this rule. A commit
     touching one prints a warning from `tools/hooks/pre-commit`, which
     catches edits made through Bash; it never blocks. Every local session
     starts with the board in its context (`.claude/hooks/plan-board.sh`).
   * Limit: a claim's owner is the nearest process named `claude`. One
     such process hosting several conversations (`/clear`, or perhaps the
     desktop app) makes them one owner; a CLI installed through npm shows
     as `node` and cannot claim (`PICAR_CLAIM_PID` names an owner by hand).
   * Limit: claims are per machine. A Jetson or cloud session still meets
     the others only at push.

   *Why:* asked "what can you pick up next?" on 2026-10-12, a session had to
   guess who was working from commit times. The tool's first run found two
   sessions editing within the last minutes, neither visible from `dev`, and
   one of them changing a file this section also changed.
9. **Helpers.** `git rerere` is enabled, so a resolved conflict replays
   itself. Handoffs are named after their section.
10. **Each session pushes to `dev` on its own judgement** (the user,
   2026-10-15: "Each agent can use their judgement to commit to dev").
   No go-ahead is asked. Push work that is finished as a step: reviewed
   (CLAUDE.md section 6), its criteria recorded (met or failed), and
   through the gate. Still the user's call, and asked: anything that
   spends money (Bedrock, paid GPU hosts), a deploy (Lambda, CloudFront,
   the twin), a force push or a deleted `dev`, and `PICAR_SKIP_GATE=1`.
   Merge `origin/dev` in (or rebase) first.
11. **Delete a branch once its work is in `dev`** (the user, 2026-10-15).
   After your push lands, delete your section's branch on `origin`
   (`git push origin --delete plan/3.N-<slug>`), its local branch and its
   worktree (`git worktree remove .claude/worktrees/plan-3.N`). Any
   session may also delete another session's stale branch when **all**
   hold:
   * its content is in `dev`: `git merge-tree --write-tree origin/dev
     origin/<b>` prints `origin/dev`'s own tree
     (`git rev-parse origin/dev^{tree}`), or a section on `dev` says it
     superseded the branch (a renumbered section). The count of commits
     "ahead" is not enough: rebased or squashed work still shows as ahead;
   * it holds no live claim and has had no commit for 2 hours (rule 8's
     "active");
   * it is not `main` (the default branch) or `dev`.

   A branch with work that is NOT in `dev` (abandoned or still open) is
   deleted only when the user says so. Fetch the full history first
   (`git fetch --unshallow origin` in a cloud clone): a shallow clone has
   no merge base, so every branch looks unmerged. Deleting a `plan/*`
   branch never frees its number, because `new` also counts the section
   files on `origin/dev`. *Why:* nine branches besides `dev` had piled up
   on `origin` by 2026-10-15, six of them already in `dev`, and `overlap`
   and `board` read every `plan/*` branch.

## Setting up a machine (once)

```bash
git config core.hooksPath tools/hooks
git config rerere.enabled true
git config rerere.autoupdate true
```
