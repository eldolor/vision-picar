# Parallel sessions on the plan

Several Claude Code sessions work on `PLAN-ros-alignment.md` at once (the
user, 2026-10-07). These rules keep them from colliding. Each one answers a
collision this project has already had.

## The workflow

```bash
# 1. Reserve a section: the next free number, its own branch and worktree.
python tools/plan_section.py new <slug> "<title>"
#    -> branch plan/3.N-<slug>, worktree .claude/worktrees/plan-3.N,
#       docs/plans/ros-alignment/3.N-<slug>.md, committed.
cd .claude/worktrees/plan-3.N

# 2. Your own ports, ROS domain, container, image tag and log directory.
eval "$(python tools/plan_section.py env)"
docker build -t "$ROS_IMAGE" service/slam    # only if you change service/slam

# 3. Before touching a shared file, see who else is touching it.
python tools/plan_section.py overlap

# 4. When done: rebase, then the gate.
git fetch origin && git rebase origin/dev
python tools/plan_section.py ready           # full suite; records a pass
# 5. Ask the user. Only then: git push origin HEAD:dev
```

Continuing an existing section: work in its worktree
(`git worktree list`). Do not create a second branch for it.

## The rules

1. **One file per section.** Every `3.N` section is
   `docs/plans/ros-alignment/3.N-<slug>.md`. A session edits its own
   section's file; `PLAN-ros-alignment.md` keeps only the shared context
   (sections 0-2 and 4-6). The index (`ros-alignment/README.md`) is
   generated by `tools/plan_section.py index` and merges by union. On a
   conflict there, regenerate it. *Why:* every session appended its section
   at the same line of one 5,000-line file, so every pair of sessions
   conflicted.
2. **The number is reserved by the branch.** `new` takes the highest number
   on `origin/dev` and in every `plan/*` branch name, plus one, and creates
   the branch at once. Worktrees share one `.git`, so every session on this
   machine sees every branch, and git refuses a duplicate branch name.
   *Why:* two sessions both wrote a 3.42 on 2026-10-06/07.
3. **Shared status is edited at merge, not on a branch.** A branch writes
   its own section file, its code, its specs and its own handoff
   (`docs/handoffs/HANDOFF-<date>-3.N-<slug>.md`). CLAUDE.md section 3b,
   `docs/ARCHITECTURE.md`'s status and section 6's open questions are
   updated by whoever merges, after rebasing. *Why:* one branch's status
   text was stale the moment another merged.
4. **Your own runtime resources.** `tools/plan_section.py env` derives from
   the section number:
   * ports 9000 + 10 x N (robot, brain, body, sensors, bridge);
   * `ROS_DOMAIN_ID` N (3.44 -> 44; 73 and 74, older stacks' fixed domains,
     map to 100 and 101);
   * container `picar-ros-3N`;
   * image `vision-picar-ros:plan-3.N`;
   * logs in `/tmp/vision-picar-3.N`.

   `tests/demo_explore.stack()` and everything built on it read these.
   Never rebuild `vision-picar-ros:latest` from a branch; it is built from
   `dev`. *Why:* two ROS containers on one domain crossed topics (8 of 13
   tests failed), and a branch rebuilt the shared image under another
   session.
5. **Check overlap before editing a shared file.** `overlap` lists every
   file you change that another `plan/*` branch also changes. A text merge
   can succeed and still be wrong: `robot/safety.py` changed on two
   branches at once on 2026-10-06/07. Coordinate through the user, or
   sequence the work.
6. **The merge gate.** `ready` checks the branch is rebased on
   `origin/dev`, the index is fresh, section numbers are unique and the
   tree is committed. It then runs the full suite and records a pass for
   that commit. The pre-push hook (`tools/hooks/pre-push`, installed by
   `git config core.hooksPath tools/hooks`) refuses a push to `dev` without
   one. Pushing still needs the user's go-ahead. Only the user overrides
   the gate (`PICAR_SKIP_GATE=1`).
7. **One heavy run at a time.** `tests/demo_explore.stack()` takes a lock
   (`.git/heavy-run.lock`) held until the run's process exits; a second
   heavy run waits and prints who holds it. *Why:* late ticks, scan skew
   and nav2 smoothness are timing measurements, and two stacks on one
   laptop skew each other. Long runs can go to the Jetson instead
   (`tools/jetson/README.md`). `PICAR_HEAVY_LOCK=0` skips the lock, for
   in-process work only.
8. **Helpers.** `git rerere` is enabled, so a resolved conflict replays
   itself. Handoffs are named after their section.

## Setting up a machine (once)

```bash
git config core.hooksPath tools/hooks
git config rerere.enabled true
git config rerere.autoupdate true
```
