The moving parts, once

So the rest of this page doesn't repeat itself.

Why three surfaces, not one It's tempting to read the digital twin as existing purely to emulate the robot, which makes Sim, Guide me, and Robot view look redundant with each other — they aren't, and none of them is actually emulating the robot in the literal sense (that's still blocked on buying hardware, Phase 11). Each answers “does this work” for a different layer of the system.
  • Sim tab proves the control logic — mission memory, the safety veto, the failure budgets, MissionRunner's failsafes — against a free, deterministic grid world, because this project is simulation-first by design: nothing here gets validated against real hardware first. It's also the only place control/drills.py's fault injection is safe to run at all — nobody deliberately kills the vision link or hangs the brain loop on a real robot to prove the failsafe fires.
  • Guide me has nothing to do with the robot. It's a phone-as-sensor, human-as-actuator feature that exists because the sim structurally can't answer one question: can the vision model read a real room? MockRobot's camera renders a flat-shaded raycaster, not real pixels (PLAN-sim-hardening.md's point that every “the simulation works” result so far is a statement about synthetic geometry, not rooms). Guide me answers that with real photographs, and is a genuinely useful standalone feature in its own right — point your phone, find your keys.
  • Robot view is the same real-pixel test as Guide me, but asks “what would the robot do” instead of “where should the person go” — the cheapest go/no-go gate for the navigation policy before spending money on a PiCar-X.

So: Sim validates the software that will eventually run the robot; Guide me and Robot view validate the vision model that software depends on, on real pixels the sim can never produce. All three matter, and they're testing different things, not the same thing three ways.

Four backend processes this UI can talk to, all HTTP, all optionally behind an x-app-secret header:

Robot server:8000Safety layer + watchdog + one RobotInterface backend (sim / teleop / eventually hardware)robot/server.py

The twin (web-twin/index.html) is a browser client of the first three. It never talks to a simulator or a robot backend directly — everything goes over HTTP to the robot server and/or the brain server, the same way a Pi's own client eventually will. The robot server is also what serves the twin page itself (GET /) in the deployed app, so “load the app” and “have a robot connection” can be the same request.

Only one may drive at a time. This is the Sim tab’s Local/Remote brain split, and — new — it is also Robot view’s “Drive via brain” switch.

01

Guide tab

Two modes, picked with the Guide me / Robot view toggle. Both are “point the phone at a room and repeat one vision call on a timer” with a different prompt, schema, and renderer.

Shared mechanics, both modes

  • Requires a secure context (https:// or localhost) — getUserMedia is blocked otherwise, and the start error explains this rather than failing silently.
  • Full-screen <video> camera takeover, CSS-simulated (position:fixed), not the real Fullscreen API — iOS Safari’s support for arbitrary elements is unreliable.
  • Every capture downscales to a 960px long edge before upload — smaller payload, faster Bedrock inference, no visible quality loss for a coarse position/action question.
  • Loop cadence is 500 ms for both routes (moved onto Amazon Nova Lite on 2026‑08‑28). A consecutive error backs the delay off exponentially, capped at 30s, resetting the moment a call succeeds.
  • A capture is skipped entirely if the phone’s orientation sensor says nothing has moved since the last tick — a free way to avoid a paid call with nothing new to answer.
  • A hard cap of 120 calls per session (~1 minute) auto‑pauses with a “Resume searching” button.
  • Backgrounding the tab pauses the timer; the camera stream itself releases only on Stop or navigating away.
  • A wake lock keeps the screen on while active; rotating the phone re‑syncs overlay positions immediately rather than waiting for the next tick.

1.1 · Guide me

Steer a person to an object.

Question answered“Where is {target_object}, relative to where I’m standing, and how do I get closer?” The person is the actuator; nothing in the app moves anything.

Backend · POST /guidance on the vision-analyze service → describe_image_bytes_guidance(), model amazon.nova-lite-v1:0 by default. Never touches the robot server — works with only the Cloud endpoint settings filled in.

/guidance response 
{
  "target_visible": true | false,
  "position": "far_left" | "left" | "center" | "right" | "far_right" | "not_visible",
  "proximity": "near" | "medium" | "far" | "unknown",
  "guidance": "short human-readable instruction",
  "bounding_box": {x_min, y_min, x_max, y_max} | null
}

bounding_box is normalized 0.0–1.0 against the full captured frame, requested only when the model is confident — a malformed one is rejected server-side and falls back to null.

What's on screen

  • Searching: a directional chevron pans toward position’s zone; a screen-edge glow brightens on the side to turn toward; the chevron pulses faster as proximity tightens. While the object hasn’t been spotted at all, a fixed search-sweep pattern takes over instead (right for ~5 ticks, then down for ~5, repeating) — the model has zero positional information in this state, so it's a UI convention, not a model-informed suggestion.
  • Found: a bounding-box outline (DOM/SVG, so it glides via CSS transition rather than snapping), smoothed 55%-toward-the-new-estimate each tick to damp per-tick localization jitter, and mapped from normalized coordinates to on-screen pixels accounting for the video's object-fit:cover crop.
  • Found gate: proximity === "near" (any position), or proximity === "medium" && position === "center" — added after real-device testing showed a dead-centered object sometimes scored “medium” and never advanced.
  • Feedback: directional Web Audio tones (panned left/right, works on iOS, muteable) and vibration patterns (Android Chrome only — Apple has never implemented the Vibration API in Safari; audio is the real cross-platform channel).
  • Auto-pause: once “found” holds for one tick, polling stops entirely — no reason to keep paying for calls once the answer stopped changing. “Resume searching” restarts the loop without restarting the session.

Cost: a real Bedrock vision call roughly every 1.7s effective cycle. Never auto-starts. Never touches RobotInterface, the robot server, or control/ — the same phone-as-sensor, human-as-actuator design as the rest of the twin's non-robot features.

1.2 · Robot view

Question answered“If this frame came from the robot's camera right now, what move would it make?” Nothing executes. Read-only proof the vision policy works on real room pixels, not the grid-world sim's flat-shaded raycaster render.

Robot view has three distinct behaviors, as switches next to the target field — only visible in this mode, mutually exclusive with each other — plus two pickers (1.2.d) that apply whichever of the three you choose:

Guide tab -> Robot view
  |
  +-- (default) one-off /navigate preview -- nothing persists
  +-- "Record this walk"  -- saves each frame+reply to the brain, for replay
  +-- "Drive via brain"   -- runs a REAL MissionRunner mission, live
1.2.a

Default · one-off /navigate preview

Backend · POST /navigate, same request/response plumbing as Guide me, different prompt and schema. Claude Opus 4.5 by default — and both the model and the wording are pickers, not constants: see below.

/navigate response 
{
  "target_visible": true | false,
  "target_direction": "left" | "center" | "right" | "not_visible",
  "target_reached": true | false,
  "obstacle_ahead": true | false,   // absent under "bearing-only"
  "room_guess": "kitchen" | "hallway" | … | "unclear",
  "action": "FORWARD" | "LEFT" | "RIGHT" | "REVERSE" | "STOP",
  "reasoning": "one short sentence"
}

The frame splits into three vertical thirds (left/center/right). action only ever means movement; arrival is target_reached, a separate field — so a STOP from an obstacle can never be confused with a STOP from success. (The fallback schema also defaults action to STOP, which is exactly why the split matters: a parse failure must never look like arrival.)

  • A persistent three-zone HUD frame stays up for the whole session — it's the mode's visual identity, not a per-tick result, so it's the one thing not cleared every tick.
  • The zone matching target_direction highlights; nothing highlights on not_visible — a lit zone must always mean the model actually reported that zone.
  • Arrival is its own badge (REACHED), never the raw STOP action.
  • No audio/haptic cues here — they'd encode proximity, a field /navigate doesn't return.
  • Pauses only after two consecutive target_reached ticks, not one — this mode is a continuous decision readout, not a one-shot confirmation.
  • Hold the phone low, ~10cm — roughly PiCar-X camera height. This is Stage 0 of the build plan: the cheapest, fastest go/no-go signal for whether the vision model can navigate real rooms at all.
  • A session's calls die with it. Calls overlap (up to two in flight), so each one carries both a sequence number and the run it belongs to. Without the second, a call still outstanding when you pressed Stop would land in the next session, flash its answer over the new camera view, and then suppress that run's first few real decisions by claiming their sequence numbers. Reported from a phone as a brief flicker; the suppression was the larger, invisible half.
1.2.d

Two pickers · which model, and which wording

Both are served from the vision service's own allow-lists (GET /navigate/models, which publishes models and prompts together), so this page never hard-codes ids that drift. Each is echoed back on every reply, so a recorded walk can say what produced it — the one real failure this project has had was a week of walks attributed to a model that was never running.

The wording is at least as strong a lever as the model. The same recorded walk, replayed through every combination at 100% coverage, moved one model's FORWARD rate from 0.000 to 1.000 without changing the model. Five wordings now ship. The current default asks whether there is an obstacle ahead; bearing-only deletes that question outright and omits obstacle_ahead from the reply, on the argument that a single photograph does not contain distance and a sensor should own it. It is the only wording that leaves no model degenerate — and it is not the default, because that judgement needs a real distance sensor to settle.

The pickers live here, next to Robot view, because this is the flow that produces something comparable. They apply to “Drive via brain” and to the Sim tab's remote brain on the vision policy too, which is why choosing that policy reveals them.

1.2.b

“Record this walk”

Saves every captured frame plus its /navigate reply to the brain service — not the vision service, and not a browser download (60 download prompts on a phone isn't a workflow). Requires the brain connected in Settings; brain.allow_recording gates it server-side too.

  1. Start generates a walk name from the target + timestamp.
  2. Each tick's frame + reply → POST {brainUrl}/recording/frame, fire-and-forget — a failed save must never interrupt the walk or delay the next call. A running saved/failed counter shows under the switch.
  3. The brain writes frames to the shared EFS volume — the same storage the separate admin service lists/views/deletes from later.
  4. Stop shows the walk name and save count in a toast, with the exact replay command: python -m tests.demo_replay_mission recordings/<walk> "<target>".

A recorded walk becomes sim/replay_robot.py's input — an open-loop “body made of photographs” that lets the vision agent run, repeatedly and for free, against the exact same frames while a prompt is iterated on. Not the same as “Drive via brain” — recording still makes a one-off /navigate call per frame and just also saves it; driving via brain replaces that call entirely with a live mission tick, which is why the two are mutually exclusive.

1.2.c

“Drive via brain” — closes the loop for real

The one that actually exercises control/brain_server.py's real MissionRunner — mission memory, the failure budget, the timeouts, the whole B0–B3 stack — from a live phone camera instead of a recorded walk or a drill. Before this existed, nothing in the codebase read a live camera through MissionRunner; a phone walk proved the vision model could read a room but proved nothing about the brain. A phone is now one working instance of “live camera,” and a PiCar will be another.

The person holding the phone is the motor. TeleopRobot's drive methods don't move anything — they log what the model decided, the same honest no-op ReplayRobot's pan methods already are. The next frame is whatever you actually photograph after reading the instruction and walking, which is what makes this closed-loop where a recorded-walk replay is open-loop.

On Start, when the switch is on

  1. A pre-flight check: GET {serverUrl}/health must report mode: "teleop" — if the robot server is still plain mode: sim, this fails loudly here instead of 404-ing silently on the first frame push.
  2. POST {brainUrl}/mission/start with {policy: "vision", target_object}, plus model_id and prompt_variant when picked — both validated against the vision service's published allow-lists in one round trip at start, so a typo is a refusal rather than three burnt vision failures. The brain's runner factory resolves the vision policy into a real vision_fn bound to the configured vision service — the function that actually calls /navigate on the brain's behalf, per tick.
  3. The choice is latched at Start, not re-read from the toggle every tick — so Stop knows whether this session actually started a mission even if the toggle or brain connection changes mid-walk.

Each tick

  1. POST {serverUrl}/teleop/frame with the captured JPEG — TeleopRobot.push_frame(), secret-gated like every other robot route. Bumps a sequence number, notifies anyone waiting on a fresher frame.
  2. Independently, MissionRunner's own tick loop (an asyncio background task inside the brain server) calls RemoteRobot.get_camera_frame() → GET {serverUrl}/frame → TeleopRobot.get_camera_frame(), which returns whatever was most recently pushed — a staleness check, not a block (see below) — feeds it to /navigate, and applies the model's decision exactly as it would for a recorded walk or the sim.
  3. The page polls GET {brainUrl}/mission/status and reshapes it into the same {action, reasoning, target_reached, …} shape a raw /navigate reply has, so every existing renderer and the found-streak-to-pause logic keep working unmodified regardless of which sub-mode produced the result.
  4. The telemetry readout gains two rows raw /navigate never had — OUT (the mission's outcome) and VF (vision failures, so a live B3.2 budget counting up is visible) — and marks visibility/obstacle fields N/A rather than a false clear, since a mission status is a decision, not the per-frame reading that produced it.
  5. A mission ending any way other than found — stopped, failed, max steps, a live stall, a live vision-failure budget hit — surfaces through the exact same error path a lost /navigate connection would, and stops the tick loop the same way arrival does.

Stop → POST {brainUrl}/mission/stop (fire-and-forget), which stops both the mission loop and the robot — enforced at the robot gate, not just in the loop, so a tick already in flight can't get a move out after stop.

What makes this a real failsafe demo, not a preview

  • Stand still (or point the phone at the ceiling): within stall_timeout_s (default 15s) the mission ends failed with a stall message — a genuine failsafe firing, no drill involved.
  • Point the phone somewhere unparseable: exercises B3.2's vision-failure budget (default 3 chances) the same way a drill would, but for real.
  • Background the tab: the mission is a service call, not page state, so it's still running when you come back.

TeleopRobot, precisely

A fourth RobotInterface backend, alongside sim/hardware/replay (sim/teleop_robot.py):

  • push_frame(image_base64, media_type) — not part of RobotInterface; called only by the /teleop/frame route. Stores the frame, bumps a sequence number, records when it arrived.
  • get_camera_frame() — a staleness check, not a wait. Originally a blocking wait for a frame newer than the last one that caller had seen — and that shipped a real bug: the “last returned” cursor was shared across every caller of GET /frame, so Settings' own passive reachability check could consume the current frame and leave the next caller (an active mission tick) blocking the full 15s and then failing — even with a healthy phone actively streaming. Confirmed live: two consecutive plain curl reads took 15.2s on the second call. Fixed the same day: it now tracks when a frame was last pushed, returns it immediately if within stall_timeout_s, or raises TeleopStall immediately otherwise — never blocks.
  • Drive/turn/look methods — log-only acks, no position tracked.
  • get_distance() — always 999.0, the same “honestly no ultrasonic here” constant ReplayRobot uses, so the safety layer never blocks a move against this backend.
  • TeleopStall needs no special handling in MissionRunner — it surfaces straight into tick()'s existing catch-all, which already stops the robot and ends the mission failed with the exception's own message. One known rough edge: the /frame route doesn't catch it specially yet, so a live stall currently surfaces as a generic HTTP 500 rather than a named 503 — functionally correct, just a less legible log line.

Config: config/robot.yaml's mode: teleop (a sibling of sim, not a stand-in for hardware) plus a teleop: block (stall_timeout_s, default 15.0).

What this doesn't solve: room-level step memory — a photograph still carries no room label, so a teleop mission can revisit an already-searched room; only the step cap stops it, same limitation as every vision-policy mission today.

02

Camera tab · Analyze a photo

The original, one-shot vision feature, unaffected by anything above.

  • A native camera picker (<input type="file" accept="image/*" capture="environment">) — unlike Guide's live getUserMedia, this works fine over plain HTTP, no secure-context requirement.
  • An optional target-object text field.
  • Backend: POST /analyze, model us.anthropic.claude-sonnet-4-5-20250929-v1:0 by default — the one route still on a Claude model rather than Nova Lite, since it's a one-off analysis rather than a several-times-a-second loop and benefits from the stronger reasoning. The response includes a room_guess from the detected objects.
  • Downscaled to 1568px before upload — Anthropic's own server-side downscaling threshold, so anything larger just burns upload time and per-pixel cost for zero quality gain.
  • A single request/response; no loop, no camera left open, nothing to Stop.
03

Sim tab · the grid-world twin

Everything here talks to the robot server (and, for Vision Autopilot, the vision-analyze service directly) plus a JS port of the starter-house grid layout.

  • Top-down canvas + telemetry — room, facing, free space, doorway, visible objects, live safety status, all rendered from the same calls every other panel uses.
  • Manual control (D-pad) — direct POST /action / POST /stop calls. Every move passes through the server's safety veto, the same path an AI decision gets — a human driving over Wi-Fi has the same collision protection.
  • Remote brain — starts a real MissionRunner mission, then this panel becomes a pure observer: step count, last action, rooms searched, a log tail, following the robot on the map. Closing the tab and reopening shows the mission further along or finished — proof it's a service call, not page state. A failsafe drill picker injects exactly one fault (vision errors, vision hangs, or a hung brain loop) so the two guards that can't be provoked by pressing anything can still be watched firing, always ending with the robot stopped. A watchdog readout shows the server's own silence counter. A policy picker chooses between the free rule-based explorer and the vision policy (brain/vision_agent.py) — one paid /navigate call per step, and the policy that will be on the robot. Picking it reveals the Guide tab's model and wording pickers, sends both with the start, and states in words which of each the mission would ask with before you spend anything.
  • Local brain, rule-based (Explore / Find backpack / Reset) — the frontier-preference algorithm from brain/agent.py, re-implemented in JavaScript, driving the same /action calls a human would. Free, no API calls, kept specifically because it needs no brain service and exercises the safety layer without cost.
  • Local brain, Vision Autopilot — the grid-world sim has no real camera, so a raycaster renders a synthetic first-person frame, which is posted to /navigate every ~2.5s and executed through the same safety-veto path. Since phase S2 that render lives in sim/renderer.py and arrives with the frame; the canvas version here is the fallback for a server that predates it, and a “frame source: server / local” readout says which one drew the picture. Never auto-starts; a visible call counter and step cap bound the cost. Both renderers light the ceiling and floor with their own constants rather than the app's dark UI colours — borrowing those painted a room as a black void, and two closed-loop missions spent 80 paid calls being told the frame was “very dark and unclear.”

Remote and Local brains are mutually exclusive, enforced both directions: the twin refuses to start a local loop during a remote mission, and the brain server answers a second /mission/start with 409.

04

Settings tab

  • Robot server connection — URL + optional secret. Auto-fills to the page's own origin when served by the robot server itself; manual entry still works for pointing at a different server (e.g. a teleop deployment).
  • Brain service connection — its own URL and an independently entered secret, never assumed to match the robot's once each is its own deployed service. Needed for Remote brain, recording, and Drive via brain.
  • Cloud endpoint settings — the vision-analyze base URL + secret, shared by Guide, Robot view's default sub-mode, Vision Autopilot, and Camera-tab analysis. Enter the base URL only; each feature appends its own route.
  • Share setup — a QR code encoding every URL and secret above, so a second phone needs no typing. Explicitly flagged: anyone who scans or photographs it gets the same access.
  • Developer — a switch for exact API call counts and the pan-speed meter, for anyone debugging the loop rather than just using it.
  • Debug / support — copies the last 20 unexpected browser-side errors plus basic context to the clipboard, for pasting into a bug report without live-reproducing the issue.

All fields except debug/onboarding flags persist in localStorage so a re-opened install doesn't start from a blank state.

Safety and failsafes

Cross-cutting, not a tab. Applies to every mode that moves anything; Guide me and Robot view's default/recording sub-modes move nothing, so none of this applies to them.

Safety vetorobot/safety.pyA move that would collide, regardless of who or what requested it — enforced on every /action call, on the server
B3.1 · watchdogrobot/server.pyMotors left running because any client went quiet past watchdog_timeout_s

Why CloudFront exists

getUserMedia (Guide me and both live-camera Robot view sub-modes) requires a secure context. A bare NLB/ALB only serves plain HTTP; CloudFront's default domain gives free automatic HTTPS in front of it with no certificate management — what makes any live-camera feature usable from a phone off the deploying machine's own LAN at all.

Why teleop got its own sibling stacks

robot/factory.py picks exactly one backend per process at boot, and the brain server picks exactly one robot_url at start — so running sim-mode and teleop-mode simultaneously needs two robot processes and two brain processes, not a flag flip on the existing ones. Deliberately new files rather than parameterizing the existing templates, so a mistake in the new stack can't touch the already-running one.

Secrets

Each service gets its own generated x-app-secret in Secrets Manager, entered manually into the twin's Settings fields. They are never assumed to match each other once each service is independently deployed — a bug fixed live during teleop testing: the twin was silently sending the robot's secret as the brain's too, which 401s the instant they differ.
